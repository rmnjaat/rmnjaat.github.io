A normalized schema spreads one business fact over several tables. A join gathers the pieces back into the shape one task needs, and gathering scattered pieces is exactly the kind of work that waits on disk latency. Indexing is the cure here too, but the right index depends on how the database runs the join, and there are three algorithms to choose from.

## 1. Two tables at a time

Whatever the algorithm, a join combines two tables. A statement that joins five tables runs four joins: the first produces an intermediate result, the second joins that result to the third table, and so on. The database does not normally store those intermediate results. Each row that comes out of one join is passed straight into the next one, which is called **pipelining**, and it keeps memory use low.

The order in which the tables are joined does not change the result, but it changes the cost a great deal, so the optimizer compares the possible orders and keeps the cheapest. The number of orders grows with the factorial of the number of tables: six tables have 720 orders, ten have more than three million. Planning a complex statement is real work.

<Callout kind="important" title="Bind parameters again">The more tables a statement joins, the more it pays to use [bind parameters](/sql/where-clause/bind-parameters/), because a statement with literal values has to be planned again on every execution. Not using them is like recompiling a program every time you run it.</Callout>

## 2. The nested loops algorithm

Nested loops is the most basic of the three algorithms. The database picks one table as the **driving** (or outer) table and reads its rows one by one. For each row it runs a second query against the other table: find the rows whose join columns hold this row's values. It is a loop inside a loop, and the inner loop is a where-clause search whose value changes on every iteration.

<Joins client:visible n="4.1" mode="nested" switchable={false} />

Step through the figure. The driving table is `sales`. Row s1 refers to employee e2, so the database walks the `employees` primary key tree, finds e2, fetches the row and emits the joined pair. Then s2, then s3, then s4. Every driving row costs one tree traversal and one table access on the inner side.

You could write this algorithm yourself, as a loop in application code that runs one `SELECT` per row. That is a bad idea, because network latency then comes on top of disk latency, and yet it is extremely common, because it is easy to do without noticing. ORM tools are the usual culprit, to the point that the pattern has a name: the **N+1 selects problem**.

## 3. N+1 selects, as three ORMs produce them

The following examples all do the same thing: find the employees whose last name starts with `WIN`, then process each of their sales.

```java
// JPA, using the CriteriaBuilder interface
CriteriaBuilder queryBuilder = em.getCriteriaBuilder();
CriteriaQuery<Employees>
   query = queryBuilder.createQuery(Employees.class);
Root<Employees> r = query.from(Employees.class);
query.where(
  queryBuilder.like(
    queryBuilder.upper(r.get(Employees_.lastName)),
    "WIN%"
  )
);

List<Employees> emp = em.createQuery(query).getResultList();

for (Employees e: emp) {
  // process Employee
  for (Sales s: e.getSales()) {
    // process sale for Employee
  }
}
```


```sql

     and sales0_.employee_id=?
```

None of the three wrote a SQL join. Each one queries `sales` with a nested select per employee. If the driving query returns N rows, the application runs N+1 statements, which is where the name comes from.

<Callout kind="tip" title="Turn on SQL logging">Enable the SQL log in development and read what your ORM sends. DBIx::Class: `export DBIC_TRACE=1` in the shell. Doctrine: only in code, with `$config->setSQLLogger(new \Doctrine\DBAL\Logging\EchoSqlLogger)`, so build a configurable logger and make sure it is off in production. Native Hibernate: `<property name="show_sql">true</property>` in `hibernate.cfg.xml`. JPA: in `persistence.xml`, depending on the provider, `eclipselink.logging.level` = `FINE`, `hibernate.show_sql` = `TRUE`, or `openjpa.Log` = `SQL=TRACE`. Most ORMs can also switch logging on programmatically; the risk is shipping that switch to production by accident.</Callout>

## 4. Indexing for nested loops

The nested selects are an anti-pattern, but they describe the join algorithm accurately: the database runs the join exactly as those ORMs did, just without the network in between. So the indexes a nested loops join needs are the ones those two statements would need on their own. The driving query needs a function-based index for the case-insensitive name search, and the inner query needs a concatenated index on the join columns of `sales`:

```sql
CREATE INDEX emp_up_name ON employees (UPPER(last_name));
CREATE INDEX sales_emp   ON sales (subsidiary_id, employee_id);
```

<KeyIdea>Nested loops is a where-clause search executed many times. Index the driving table for its own where clause, and index the inner table for the join columns, as if `WHERE subsidiary_id = ? AND employee_id = ?` were a query of its own.</KeyIdea>

With the same indexes in place, a SQL join still beats the nested selects, even though it performs the identical index lookups, because it saves the network round trips. It stays ahead even when it transfers more data, which it does, because the employee columns are repeated on every sales row. Performance has two dimensions, response time and throughput, or in network terms latency and bandwidth, and [Unit 3](/sql/testing-scalability/response-time-throughput-scaling-horizontal/) showed that latency is what the user feels. Bandwidth barely moves the response time; the number of round trips moves it a lot.

<KeyIdea title="Remember">Execute joins in the database. The count of round trips matters more than the amount of data they carry.</KeyIdea>

## 5. Taking control of joins in the ORM

Every ORM has a way to produce a SQL join. The best-known one is **eager fetching**, configured once in the entity mapping, for example on the `employee` property of the `Sales` class. From then on every access to `sales` also joins `employees`. That is right only if you always want the employee with the sale. A phone directory screen that shows employee details has no use for their sales, and a static setting cannot tell the two cases apart. For good performance you need to decide per query, at runtime.

**Java.** The JPA `CriteriaBuilder` offers `Root.fetch()` to say when and how to join. The example uses a left join so that employees without sales are still returned.

```java
CriteriaBuilder qb = em.getCriteriaBuilder();
CriteriaQuery<Employees> q = qb.createQuery(Employees.class);
Root<Employees> r = q.from(Employees.class);
q.where(queryBuilder.like(
    queryBuilder.upper(r.get(Employees_.lastName)),
    "WIN%")
);

r.fetch("sales", JoinType.LEFT);
// needed to avoid duplication of Employee records
q.distinct(true);

List<Employees> emp = em.createQuery(q).getResultList();
```

<Callout kind="warning" title="Fetch joins duplicate the parent">JPA and Hibernate return one `Employees` object per joined sales row, so an employee with 30 sales shows up 30 times. Strange as it looks, this is what the specification says (EJB 3.0 persistence, section 4.4.5.3, "Fetch Joins"). Either de-duplicate by hand, for example with a `LinkedHashSet`, or call `distinct()` as above.</Callout>

Hibernate 3.6.0 generates the left join, and an unwanted `distinct` with it:

```sql
select distinct
       employees0_.subsidiary_id as subsidiary1_0_0_
     , employees0_.employee_id as employee2_0_0_
       -- MORE COLUMNS
     , sales1_.sale_id as sale1_0__
  from employees employees0_
  left outer join sales sales1_
          on employees0_.subsidiary_id=sales1_.subsidiary_id
         and employees0_.employee_id=sales1_.employee_id
 where upper(employees0_.last_name) like ?
```

JPA has no way to de-duplicate the parents without also asking the database for distinct rows. The `distinct` is a problem because most databases will really sort and compare the rows; only a few notice that the primary keys make the rows unique anyway. Hibernate's native API avoids it by de-duplicating on the client with a result transformer:

```java
Criteria c = session.createCriteria(Employees.class);
c.add(Restrictions.ilike("lastName", "Win%"));

c.setFetchMode("sales", FetchMode.JOIN);
c.setResultTransformer(Criteria.DISTINCT_ROOT_ENTITY);

List<Employees> result = c.list();
```

```sql
select this_.subsidiary_id as subsidiary1_0_1_
     , this_.employee_id as employee2_0_1_
       -- MORE this_ columns on employees
     , sales2_.sale_id as sale1_3_
       -- MORE sales2_ columns on sales
  from employees this_
  left outer join sales sales2_
          on this_.subsidiary_id=sales2_.subsidiary_id
         and this_.employee_id=sales2_.employee_id
 where lower(this_.last_name) like ?
```

Clean SQL, nothing added. Note one detail: Hibernate's `ilike` becomes `lower()`, not `upper()`. The function-based index has to match the function the ORM emits, or the index is useless.

**Perl.** DBIx::Class joins when asked to `prefetch`:

```perl
my @employees =
   $schema->resultset('Employees')
          ->search({ 'UPPER(last_name)' => {-like => 'WIN%'}
                   , {prefetch => ['sales']}
                   });
```

```sql
SELECT me.employee_id, me.subsidiary_id, me.last_name
       -- MORE COLUMNS
  FROM employees me
  LEFT JOIN sales sales
         ON (sales.employee_id   = me.employee_id
        AND  sales.subsidiary_id = me.subsidiary_id)
 WHERE ( UPPER(last_name) LIKE ? )
 ORDER BY sales.employee_id, sales.subsidiary_id
```

Nobody asked for the `ORDER BY`. The database has to sort the whole result to satisfy it, and for a large result that takes time.

**PHP.** Doctrine joins with `leftJoin` when the select list names both aliases:

```php
$qb = $em->createQueryBuilder();
$qb->select('e,s')
   ->from('Employees', 'e')
   ->leftJoin('e.sales', 's')
   ->where("upper(e.last_name) like :last_name")
   ->setParameter('last_name', 'WIN%');
$r = $qb->getQuery()->getResult();
```

```sql
SELECT e0_.employee_id AS employee_id0
       -- MORE COLUMNS
  FROM employees e0_
  LEFT JOIN sales s1_
         ON e0_.subsidiary_id = s1_.subsidiary_id
        AND e0_.employee_id = s1_.employee_id
 WHERE UPPER(e0_.last_name) LIKE ?
```

## 6. The plan: nested loops outer

All three joins run as a nested loops outer join. The database finds the employees through `emp_up_name` first, then fetches the sales of each one through `sales_emp`.

## 7. When nested loops is the right choice

Nested loops performs well when the driving query returns few rows, because the number of inner lookups equals the number of driving rows. When the driving side is large the optimizer may switch to an entirely different algorithm, the hash join of the next lesson. It can only do that if the statement contains the join. An application that runs nested selects has already decided the algorithm, and the optimizer never gets a say.

## 8. See the two loops

SQLite implements only nested loops, so every join in the playground is one. Read the plan from top to bottom: the first line is the driving table, the `SEARCH` under it is the inner lookup, repeated for every driving row. A `BLOOM FILTER` line between them is a cheap pre-check that skips lookups certain to miss.
