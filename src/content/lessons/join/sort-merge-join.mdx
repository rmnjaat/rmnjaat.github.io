The third algorithm is the oldest one. Like the hash join it processes the two sides independently before combining them; unlike the hash join it needs no lookup structure in memory. What it needs is order: both sides sorted by the join columns, so that they can be closed like a zipper.

## 1. Two sorted lists, one pass

<Joins client:visible n="4.3" mode="merge" switchable={false} />

The database keeps a cursor on each sorted input and compares the two current keys. If they are equal it emits the pair (and, for duplicates on either side, every combination of the matching rows). If they differ, it advances the side with the smaller key. When one side runs out, the join is done. Each input is read once, front to back, and the output arrives sorted by the join columns.

## 2. Absolute symmetry

A nested loops join has a driving side; a hash join has a build side that must fit in memory. The sort-merge join has neither. Swapping the two inputs changes nothing, not even the performance, and that is unique among the three algorithms.

The property matters most for outer joins. With the other algorithms the direction of an outer join, left or right, dictates the join order: the preserved side has to drive. A sort-merge join is free of that constraint, and it can even preserve both sides in the same pass, which is a **full outer join**. The figure above shows the zipper itself; a full outer join adds nothing to the mechanism, it simply emits the unmatched rows on either side, padded with nulls, as the cursors pass them.

<KeyIdea>Sort-merge is the only join algorithm for which the join order is irrelevant. It can run a left outer join, a right outer join, or both at once, in one pass over each input.</KeyIdea>

## 3. Where the indexes go

The indexing strategy is the one from the hash join lesson. Each side is read in one go, so what helps is an index for the independent where conditions, the ones that cut the candidate rows of one table before the join starts. Indexing the join columns for lookups does nothing, because there are no lookups.

```sql
SELECT e.last_name, s.sale_date, s.eur_value
  FROM employees e
  JOIN sales s
    ON s.subsidiary_id = e.subsidiary_id
   AND s.employee_id   = e.employee_id
 ORDER BY e.subsidiary_id, e.employee_id;
```

## 4. Why it is rare, and when it wins

Once both inputs are sorted the merge is very fast. The problem is getting there: sorting a large input means reading all of it into memory or temp space and writing it back in order, and a sort-merge join has to do that for both sides. A hash join prepares only one side, the smaller one. That is why optimizers seldom choose the sort-merge join, and why the hash join is the better algorithm in most situations.

The picture changes when the inputs are already in order. An index on the join columns delivers its entries sorted, so reading it in order replaces the sort entirely, and the same holds for an input that a previous step in the plan already produced sorted. Then the sort-merge join reads each side once and does nothing else. [Unit 6](/sql/sorting-grouping/) is about exactly this trick, using index order so that the database never sorts at all, and it is worth far more than the choice of join algorithm.

<Callout kind="note" title="Equality only">Like the hash join, the sort-merge join needs an equality condition between the join columns to know when two keys match. A range condition in the join predicate leaves the optimizer with nested loops.</Callout>

## 5. See the sort disappear

SQLite cannot show a merge join, but it can show the one thing that makes the merge cheap: an index that delivers rows in the order the statement needs, so that the sort step vanishes from the plan.
