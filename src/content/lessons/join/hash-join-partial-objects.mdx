The hash join goes after the weak point of nested loops: one B-tree traversal for every driving row. Instead of looking rows up one at a time, it loads the candidate rows from one side into a hash table and probes that table for each row of the other side. Tuning it takes a completely different indexing approach, and there is a second lever, selecting fewer columns, that most ORM tools make difficult to pull.

## 1. Build, then probe

<Joins client:visible n="4.2" mode="hash" switchable={false} />

The join has two phases. In the **build** phase the database reads one side of the join and puts every candidate row into an in-memory hash table keyed by the join columns. In the **probe** phase it reads the other side once; for each row it hashes the join columns, looks into the hash table and emits a result for every match.

Each side is read exactly once, and the per-row work on the probe side is a hash lookup in memory rather than a tree traversal on disk. The hash table lives only as long as the statement runs and is filled in a single pass, which is why nothing on the build side has to be fetched one row at a time, and why no index is needed for that.

## 2. Where the indexes go

Consider a report of the last six months of sales with the details of the employee who made each one:

```sql
SELECT *
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND  s.employee_id   = e.employee_id  )
 WHERE s.sale_date > trunc(sysdate) - INTERVAL '6' MONTH
```

The condition on `sale_date` is the only **independent** where condition, meaning it mentions a single table and plays no part in the join. Without any index the plan is two full table scans. The plans in this page come from the book's data volume, 10,000 employees and one million sales.

<Callout kind="important" title="Indexing the join columns does not help">A hash join never searches an index for the join columns; it compares them inside the hash table. That does not mean a hash join cannot be indexed. The independent conditions, the ones applied while each table is read, can be. Here that is the date condition on `sales`.</Callout>

```sql
CREATE INDEX sales_date ON sales (sale_date)
```

Unlike nested loops, indexing a hash join is **symmetric**: the join order does not change which indexes are useful. If the optimizer decided to hash the sales side instead, the same `sales_date` index would be used to load the hash table.

<KeyIdea>Index the independent where conditions of each table, and nothing else, for a hash join. The decision does not depend on which side ends up in the hash table.</KeyIdea>

## 3. A smaller hash table

The other way to speed up a hash join is to make the hash table smaller, because the join is only fast while the whole table fits in memory. The optimizer already puts the smaller side into the hash table; the `Bytes` column of the Oracle plan shows its estimate, nine megabytes for `employees` against ten for the sales rows, so `employees` is the one that gets hashed.

The first way to shrink it is **fewer rows**. Suppose `employees` had a `department` column. Adding `AND e.department = 'Sales'` would keep everyone who cannot have sales out of the hash table, and that helps even without an index on `department`, because the saving is in memory, not in the table access. You then have to be sure that no sales rows belong to employees of other departments; a constraint is the right place to pin that assumption down.

The second way is **fewer columns**. The hash table does not hold rows, it holds the columns the query references, so what matters is not the row count but the memory footprint. The report above selects `*`. Name the four columns it really needs instead:

```sql
SELECT s.sale_date, s.eur_value
     , e.last_name, e.first_name
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND  s.employee_id   = e.employee_id  )
 WHERE s.sale_date > trunc(sysdate) - INTERVAL '6' MONTH
```

<KeyIdea title="Remember">A hash join gets faster when its hash table gets smaller. Cut rows with extra conditions, and cut columns by naming only what the query prints.</KeyIdea>

## 4. Partial objects in ORMs

Removing columns from a hand-written statement is easy. With an ORM that maps whole entities it is a real challenge, because support for **partial objects** is thin. The following are the options.

**Java.** JPA lets you mark a property lazy with `@Basic(fetch=FetchType.LAZY)`:

```java
@Column(name="junk")
@Basic(fetch=FetchType.LAZY)
private String junk;
```

The provider is allowed to ignore it. The specification (EJB 3.0 JPA, section 9.1.18) calls `LAZY` a hint and permits the implementation to fetch the data eagerly anyway. Hibernate 3.6 honours it only with compile-time bytecode instrumentation, which rewrites the compiled classes so that a lazy property is loaded when first accessed. That is transparent to the application and opens a new kind of N+1 problem: one select per row *and property*. It is dangerous because JPA offers no way to say "this time, fetch everything" at runtime.

Hibernate's own query language, HQL, has the `FETCH ALL PROPERTIES` clause for exactly that:

```sql
select s from Sales s FETCH ALL PROPERTIES
 inner join fetch s.employee e FETCH ALL PROPERTIES
 where s.saleDate >:dt
```

It forces the entity to be loaded completely, instrumentation and `LAZY` notwithstanding. The other option, which works the same way in HQL and JPQL, is to select into a data transfer object instead of an entity:

```sql
select new SalesHeadDTO(s.saleDate , s.eurValue
                       ,e.firstName, e.lastName)
  from Sales s
  join s.employee e
 where s.saleDate > :dt
```

The query fetches only the listed columns and returns plain Java objects, not managed entities. Rewriting a lot of existing code to a new class is often unreasonable, but instrumented lazy loading causes N+1 problems that are usually worse than the original slowness. One workable path is a small interface with only the getters, implemented by both the entity and the DTO, so that read-only consumers accept either. That is typically enough, because the big hash joins come from reports that do not write anything. For a new report, fetch DTOs or a plain `Map` from the start.

**Perl.** DBIx::Class is not an entity manager, so it has no identity map and subclassing a result class causes no aliasing problems; the cookbook recommends it. Define `Sales` on two levels, a slim `SalesHead` and a full `Sales` that adds the rest:

```perl
package UseTheIndexLuke::Schema::Result::SalesHead;
use base qw/DBIx::Class::Core/;

__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/sale_id employee_id subsidiary_id
                            sale_date eur_value/);
__PACKAGE__->set_primary_key(qw/sale_id/);
__PACKAGE__->belongs_to('employee', 'Employees',
           {'foreign.employee_id'   => 'self.employee_id'
           ,'foreign.subsidiary_id' => 'self.subsidiary_id'});

package UseTheIndexLuke::Schema::Result::Sales;
use base qw/UseTheIndexLuke::Schema::Result::SalesHead/;

__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/junk/);
```

The derived class has to repeat the `table` setup. Use whichever class fits the job. For the employee side, `prefetch` loads all columns; `+columns` picks a few:

```perl
my @sales =
   $schema->resultset('SalesHead')
          ->search($cond
                  ,{      join => 'employee'
                   ,'+columns' => ['employee.first_name'
                                  ,'employee.last_name']
                   }
                  );
```

The root table's column list cannot be trimmed this way, which is why `SalesHead` exists. DBIx::Class 0.08192 generates:

```sql
SELECT me.sale_id,
       me.employee_id,
       me.subsidiary_id,
       me.sale_date,
       me.eur_value,
       employee.first_name,
       employee.last_name
  FROM sales me
  JOIN employees employee
        ON( employee.employee_id   = me.employee_id
       AND  employee.subsidiary_id = me.subsidiary_id)
 WHERE(sale_date > ?)
```

**PHP.** Doctrine 2 selects attributes at runtime with the `partial` keyword. The documentation warns that partially loaded objects may behave oddly, and the keyword is there to make you acknowledge that. The primary key columns must be listed explicitly:

```php
$qb = $em->createQueryBuilder();
$qb->select('partial s.{sale_id, sale_date, eur_value},'
          . 'partial e.{employee_id, subsidiary_id, '
                     . 'first_name , last_name}')
   ->from('Sales', 's')
   ->join('s.employee', 'e')
   ->where("s.sale_date > :dt")
   ->setParameter('dt', $dt, Type::DATETIME);
```

```sql
SELECT s0_.sale_id       AS sale_id0,
       s0_.sale_date     AS sale_date1,
       s0_.eur_value     AS eur_value2,
       e1_.employee_id   AS employee_id3,
       e1_.subsidiary_id AS subsidiary_id4,
       e1_.first_name    AS first_name5,
       e1_.last_name     AS last_name6,
       s0_.subsidiary_id AS subsidiary_id7,
       s0_.employee_id   AS employee_id8
  FROM sales s0_
 INNER JOIN employees e1_
         ON s0_.subsidiary_id = e1_.subsidiary_id
        AND s0_.employee_id   = e1_.employee_id
 WHERE s0_.sale_date > ?
```

Doctrine adds the `subsidiary_id` and `employee_id` of `sales` once more. The objects it returns look like fully loaded ones, but the columns that were not selected stay uninitialized, and reading them does not raise an error.

<Callout kind="warning" title="Common mistake">`SELECT *` costs little in a nested loops join, where each row is fetched once anyway. In a hash join it inflates the build side by every column nobody asked for, and a hash table that no longer fits in memory is the difference between a fast join and a slow one.</Callout>

## 5. What a hash join cannot do

The hash table is keyed by the join columns, so it can only answer "is there a row with exactly this key". A hash join therefore needs at least one equality condition to hash on. Further range conditions in the join predicate, `s.sale_date BETWEEN e.start_date AND e.end_date` for instance, do not rule it out: the equality is hashed and the range is checked afterwards as a filter on each matching pair. MySQL's `EXPLAIN` even prints such conditions as a filter on the hash join line. What a hash join cannot do in most engines is a join with no equality at all, a pure theta join; that one runs as nested loops. MySQL 8.0.20 and later are the exception and hash it anyway, building over a Cartesian product and filtering every pair.
