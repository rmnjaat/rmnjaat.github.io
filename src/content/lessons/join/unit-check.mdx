<Check

  question="An ORM fetch join returns the same employee object 30 times, once per sale. What does the lesson say about it?"
  options={[
    'It is a Hibernate bug and is fixed by upgrading.',
    'It is the specified JPA behaviour; de-duplicate in the application, or use distinct() and accept that the database may really sort and compare the rows.',
    'It means the join ran as a hash join, which always duplicates the build side.',
  ]}
  answer={1}
  explain="JPA specifies that a fetch join returns the parent per joined child row. distinct() removes the duplicates but puts a DISTINCT into the SQL that most databases execute literally; Hibernate's native API can instead de-duplicate on the client with a result transformer. />

<Check
  client:visible
  question="The six-month sales report runs as a hash join with employees on the build side. The optimizer changes its mind and hashes sales instead. Which indexes does the join need now?"
  options={[
    'A new index on employees (subsidiary_id, employee_id), because the probe side now does the lookups.',
    'The same one as before: sales (sale_date), the only independent where condition. For a hash join the useful indexes do not change with the join order.',
    'None, because a hash join never reads an index.',
  ]}
  answer={1}
  explain="A hash join reads each side once and compares the join columns inside the hash table, so no index on them is ever searched. The only thing an index can speed up is an independent condition applied while a table is read, and that is true whichever side gets hashed: the sales_date index would now be used to fill the hash table instead of to probe it. See Hash join, section 2."
/>

<Check
  client:visible
  question="Why does the hash join lesson warn about JPA's @Basic(fetch = LAZY) on a property?"
  options={[
    'Because the provider may ignore it, and when Hibernate honours it through bytecode instrumentation, each lazy property can trigger one extra select per row, an N+1 problem on the property level, with no way to override it at runtime.',
    'Because lazy properties are stored in a separate table and need an extra join.',
    'Because the database cannot build a hash table over lazy columns.',
  ]}
  answer={0}
  explain="LAZY on a basic property is only a hint. Hibernate implements it with instrumented classes that load the property on first access, one select per row and property. HQL's FETCH ALL PROPERTIES or a DTO constructor expression are the ways out. See Hash join, section 4."
/>

<Check
  client:visible

  options={[

  explain="The sort-merge join is fully symmetric and does not need indexes on the join columns. It is rarely chosen because sorting both sides is expensive; the hash join prepares only one side. It wins when the order comes for free. MySQL does not implement it at all. See Sort-merge join."
