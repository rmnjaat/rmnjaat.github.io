<Check
  client:visible
  question="A plan shows an index range scan with cost 2 delivering 333 rows, then a table access with cost 230 that filters them down to 17. Which change does the lesson recommend?"
  options={[
    'A new index on UPPER(last_name) so that the LIKE becomes an access predicate.',
    'Extending the existing index with the filter column so the LIKE is applied to the index entries and the table is read 17 times instead of 333.',
    'Reordering the table rows to match the index, so that the 333 rows sit in one block.',
  ]}
  answer={1}
  explain="A leading-wildcard LIKE cannot be an access predicate on any index. Adding the column to the existing index moves the filter before the table access, which is where the cost was. Row sequencing is possible but impractical, since a table can follow only one index. See Index filter predicates, sections 2 and 3."
/>

<Check
  client:visible
  question="When does an index-only scan save the least?"
  options={[
    'When the query touches a single row, or when the index already has a good clustering factor, so that there are few table reads to save.',
    'When the query aggregates tens of thousands of rows.',
    'When the index has only two columns.',
  ]}
  answer={0}
  explain="The saving is one table access per row. One row saves one read, which the tree traversal's own reads dwarf, and a well-clustered index finds its rows in few blocks anyway. Aggregates over many rows are the ideal case. See Index-only scan, section 2."
/>

<Check
  client:visible
  question="A query ran as an index-only scan. A developer adds 'AND sale_date > ?' and it gets slower although it returns fewer rows. Why?"
  options={[
    'The database sorts the result by sale_date now.',
    'sale_date is not in the index, so the table has to be read to evaluate the new condition. What counts is how many rows the database inspects, not how many it returns.',
    'The bind parameter disables the index.',
  ]}
  answer={1}
  explain="Any column that is not in the index, in the where clause or the select list, brings the table access back. A new where column may at least open another access path, as sales_date did in the lesson; a new select column never does. Check the plan before extending a query. See Index-only scan, section 3."
/>

<Check
  client:visible
  question="Why does a secondary index on an index-organized table store the clustering key instead of a rowid?"
  options={[
    'Because the clustering key is shorter than a rowid.',
    'Because rows inside a B-tree move when leaf nodes split, so there is no stable address to store. The lookup therefore traverses the clustered index once per row.',
    'Because the database forbids more than one index on such a table.',
  ]}
  answer={1}
  explain="A heap never moves a row once written, so an address works. A clustered index reorders rows to keep the key order, so the secondary index has to store a logical key and pay a full traversal per row, unless it covers the query by itself. The clustering key is usually longer than a rowid, not shorter. See Index-organized tables, section 3."
/>
