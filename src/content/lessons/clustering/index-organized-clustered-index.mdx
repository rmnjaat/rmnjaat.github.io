An index-only scan runs a statement on the copy of the data that lives in the index; the original rows in the heap table are never needed. Push that to its end and put every column into the index, and the question becomes obvious: why keep the heap table at all?

## 1. The heap

The ordinary table is a **heap**. A new row goes into whichever block has free space, and once written it stays there. The row's address, block number plus position inside the block, is its **rowid**, and that is what the leaf entries of every index point to. Because the address never changes, an index entry can point straight at the row and the table access is a single read.

A heap has no order of its own. Two rows with the same `subsidiary_id` are near each other only by coincidence, which is the scattering this whole chapter has been fighting.

## 2. The table inside the index

A few engines let the index itself hold the table. Oracle calls it an **index-organized table** (IOT); others call it a **clustered index**. Both names describe the same thing, a B-tree without a heap underneath, whose leaf nodes hold the complete rows in primary-key order. Use whichever name puts the emphasis where you need it, on the table or on the index.

That promises two things: there is no heap to store, and a lookup through the clustered index is by construction an index-only scan. Both sound attractive and both are hard to get in practice, for one reason: the next index on the table.

<Figure n="5.2" title="Index-based access on a heap table versus a secondary index on an index-organized table">

| | Heap table | Index-organized table |
| --- | --- | --- |
| Row location | anywhere, fixed, addressed by rowid | leaf node of the primary key B-tree, moves on split |
| Primary key lookup | tree traversal + one table read | tree traversal only |
| Primary key range scan | tree + one table read per row | consecutive leaf nodes |
| Secondary index entry | key + rowid | key + clustering key |
| Lookup via secondary index | `INDEX RANGE SCAN` + `TABLE ACCESS BY INDEX ROWID` | `INDEX RANGE SCAN` + `INDEX UNIQUE SCAN` per row |

<p slot="caption">Finding all sales of one day through an index on sale_date. On the heap the second step is one direct read per row; on the IOT it is a full traversal of the primary key tree per row.</p>
</Figure>

## 3. Why secondary indexes have no rowid

A **secondary index** is any further index on the table. On a heap it stores rowids like any other index. On an index-organized table it cannot, because the rows live inside a B-tree that is kept in order, and keeping order means moving rows. An insert that fills a leaf node splits it and moves half the entries to a new block, including rows the insert never touched. A heap never moves anything; a clustered index does it all the time.

So a secondary index on an index-organized table stores a logical key instead: the **clustering key**, usually the primary key. A lookup through it then takes two steps. The `INDEX RANGE SCAN` on the secondary index yields clustering keys, and for each one the database runs an `INDEX UNIQUE SCAN`, a complete traversal of the clustered index, to reach the row. Between the secondary index and the row there is now a whole second B-tree.

<Callout kind="important">A secondary index on an index-organized table pays a full tree traversal for every row it fetches, where a heap would pay one block read.</Callout>

The remedy is the one from the previous page. If the secondary index holds every column the query needs, the second step is skipped, a **secondary-index-only scan**, and the saving is larger than on a heap because what is skipped is a whole tree traversal rather than a single read.

The database uses every redundancy it has. The secondary index stores the clustering key in each entry, so a query that selects only the clustering key is answered from the secondary index alone:

```sql
SELECT sale_id
  FROM sales_iot
 WHERE sale_date = ?
```

```
-------------------------------------------------
| Id | Operation        | Name           | Cost |
-------------------------------------------------
|  0 | SELECT STATEMENT |                |    4 |
|* 1 |  INDEX RANGE SCAN| SALES_IOT_DATE |    4 |
-------------------------------------------------

Predicate Information (identified by operation id):
---------------------------------------------------
   1 - access("SALE_DATE"=:DT)
```

`sales_iot` is an index-organized table clustered on `sale_id`. The index `sales_iot_date` is on `sale_date` only, yet it carries `sale_id` in every entry, so the query never leaves it. Select any other column and the second traversal appears, once per row:

```sql
SELECT eur_value
  FROM sales_iot
 WHERE sale_date = ?
```

```
---------------------------------------------------
| Id  | Operation         | Name           | Cost |
---------------------------------------------------
|   0 | SELECT STATEMENT  |                |   13 |
|*  1 |  INDEX UNIQUE SCAN| SALES_IOT_PK   |   13 |
|*  2 |   INDEX RANGE SCAN| SALES_IOT_DATE |    4 |
---------------------------------------------------

Predicate Information (identified by operation id):
---------------------------------------------------
   1 - access("SALE_DATE"=:DT)
   2 - access("SALE_DATE"=:DT)
```

<KeyIdea>On a clustered table every secondary index entry carries the clustering key, and every lookup through a secondary index walks two trees. The covering techniques of the previous page matter more there, not less.</KeyIdea>

## 4. Which tables to cluster

The promise shrinks on contact with a second index. Whatever the clustered index saved on its own lookups, a secondary index gives back twice over. Space goes the same way: a clustering key is normally wider than a rowid, so each secondary index grows, and the heap that was saved reappears spread across them. The model works best for a table with exactly one index. The heap, for its part, keeps one fixed copy of each row that any index can point at by address.

<Callout kind="important" title="One index: cluster. Several: heap.">One index: the clustered model is a good fit. Several indexes: keep the heap, and add covering columns where a query needs clustered-index speed. That buys the fast reads selectively and leaves the remaining indexes cheap.</Callout>

Where the engine gives no choice, the page is about the primary key: keep it short, so that the secondary indexes stay small, and prefer increasing values, so that new rows land at the end of the tree instead of splitting leaves in the middle.

## 5. What each engine offers

Support is inconsistent, and the same words mean different things.

<EngineTabs>
  <Fragment slot="db2">
  Db2 (LUW) has no index-organized tables, and uses "clustered index" for something else: a heap table whose inserts try to land in the same block as the rows that neighbour them in the chosen index (`CREATE INDEX … CLUSTER`). The index still stores rowids; there is no second traversal.
  </Fragment>
  <Fragment slot="mysql">
  It depends on the storage engine. MyISAM uses heap tables only; InnoDB always uses a clustered index on the primary key (or, without one, on the first `NOT NULL` unique index, or a hidden row id). There is no choice to make, so every InnoDB secondary index carries the primary key columns, and every lookup through one is two traversals.
  </Fragment>
  <Fragment slot="oracle">
  Heap tables by default. An index-organized table is created with the `ORGANIZATION INDEX` clause, and the primary key is always the clustering key:

  ```sql
  CREATE TABLE (
     id    NUMBER NOT NULL PRIMARY KEY,
     [...]
  ) ORGANIZATION INDEX
  ```
  </Fragment>
  <Fragment slot="postgresql">
  PostgreSQL has heap tables only. The `CLUSTER` command rewrites a heap once in the order of a chosen index; rows inserted afterwards go wherever there is space, so the order decays until the next `CLUSTER`. The planner tracks how well the table follows an index as the `correlation` statistic in `pg_stats`.
  </Fragment>
  <Fragment slot="sql-server">
  Clustered by default: the primary key becomes the clustering key, although any columns can be chosen, even non-unique ones. A heap requires `NONCLUSTERED` on the primary key:

  ```sql
  CREATE TABLE (
     id    INT NOT NULL,
     [...]
     CONSTRAINT pk PRIMARY KEY NONCLUSTERED (id)
  )
  ```

  Drop the clustered index and the rows are moved into a heap. The clustered default is a frequent source of performance problems with secondary indexes; the second traversal shows up in plans as a `Key Lookup` (`RID Lookup` on a heap).
  </Fragment>
  <Fragment slot="sqlite">
  Every SQLite table is a B-tree. An ordinary table is keyed by the `rowid`, so `sales`, whose `sale_id INTEGER PRIMARY KEY` is an alias for the rowid, is clustered on `sale_id`; `employees`, with a composite key, keeps a rowid tree plus a separate unique index. A `WITHOUT ROWID` table is clustered on its declared primary key, and its secondary indexes store that key.
  </Fragment>
</EngineTabs>
