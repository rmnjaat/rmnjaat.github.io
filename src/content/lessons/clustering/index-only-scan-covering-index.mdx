The previous page cut the number of table reads by filtering in the index. Take that to its end: if the index holds everything the query needs, there is no reason to read the table at all. This is one of the most powerful tuning techniques there is, and one of the most fragile.

## 1. A query the index can answer alone

To cover a query, the index must contain every column the statement mentions, in particular the ones in the select list:

```sql
CREATE INDEX sales_sub_eur
    ON sales
     ( subsidiary_id, eur_value )
```

```sql
SELECT SUM(eur_value)
  FROM sales
 WHERE subsidiary_id = ?
```

The where clause still comes first when choosing the column order: `subsidiary_id` leads so that it works as an access predicate. `eur_value` is there only so that the database finds the value to sum in the index entry. The plan shows the index scan with no table access after it.

An index that makes this possible is called a **covering index**. The name is slightly off, since it makes covering sound like a fixed attribute of the index. Whether an index covers is decided per query: the same index covers `SUM(eur_value)` and does not cover `SUM(quantity)`. "Index-only scan" says it better, because it names the operation.

## 2. How much it saves

The Oracle and MySQL plans estimate about 40,000 entries, at the book's data volume of a million sales. Either way, without the covering column each of those entries would cost a table read, one per row when every row sits in its own block. Where the index has a good clustering factor and the rows share a few blocks, there is less to save.

The number of rows limits the gain in the other direction too. A query that returns one row saves one table access, and since the tree traversal itself costs a few block reads, that one saved read hardly registers.

<Callout kind="important">Two numbers decide what an index-only scan is worth: how many rows the query touches, and how scattered those rows are, which is the clustering factor.</Callout>

That makes it an aggressive strategy. Do not build covering indexes on suspicion: they use memory and make every `UPDATE` of the covered column slower ([Chapter 8](/sql/dml/)). Index for the where clause first, without looking at the select list, and extend the index only when a plan shows the need.

## 3. How it breaks

Suppose the report is narrowed to recent sales:

```sql
SELECT SUM(eur_value)
  FROM sales
 WHERE subsidiary_id = ?
   AND sale_date > ?
```

Fewer rows, so one would expect it to run faster. But `sale_date` is not in the index, and the database has to read the table to evaluate the new condition.

The query delivers fewer rows and takes longer. The number of rows a query returns says little about its cost; the number of rows the database has to look at on the way is what sets it.

<Callout kind="warning" title="Check the plan before extending a query">Adding a condition to the where clause can make a query slower, which looks illogical until you see the table access come back. Read the plan before and after.</Callout>

When the covering index no longer covers, the optimizer takes the next best plan, which may be something completely different or, as in the Oracle plan, a similar plan on another index. Here it chose `sales_date`, a leftover from the [hash join page](/sql/join/hash-join-partial-objects/), for two reasons. First, it believes the date condition is more selective than the subsidiary (about 10,000 rows against 40,000 in the two plans), although with bind parameters that estimate is arbitrary: the date of the first sale would select the whole table. Second, `sales_date` has a better clustering factor. `sales` grows chronologically and, as long as nothing is deleted, new rows are appended at the end, so the table order roughly follows the date order.

An index with a good clustering factor finds its rows in few table blocks, and the query may be fast enough through `sales_date` without any index-only scan. In that case the extra column in `sales_sub_eur` should go again.

<Callout kind="note">An index whose order already follows the table, as a date index on an append-only table does, gains little from an index-only scan.</Callout>

This example was a lucky one: the extra condition cost the index-only scan but handed the optimizer another access path in return, so it could limit the damage. A column added to the select list never opens a new access path. It only costs.

<KeyIdea title="Maintain your index-only scans">Put a comment next to a query that depends on an index-only scan, saying so and pointing here, so that whoever adds a column next year knows what they are about to break.</KeyIdea>

## 4. Function-based indexes and the original column

Function-based indexes cause a similar surprise. An index on `UPPER(last_name)` stores the uppercase string, not the column, so it cannot cover a query that selects `last_name`. That is the reason the previous page hinted at: the index for the `LIKE` filter would have been more useful on `last_name` itself, because then it also covers queries that select the name.

<KeyIdea>Prefer the column itself over an expression on it. An index on the raw value serves more queries, and a function-based index only earns its place when the expression is an access predicate.</KeyIdea>

## 5. Which queries to cover, and what it costs

Aggregates like the sum above are the ideal case: many rows, few columns, so a slim index covers them. The more columns a query selects, the more the index has to carry, and at some point the index is a second copy of the table. Select only the columns you need. `SELECT *`, the default of every ORM that maps whole entities, rules out an index-only scan on any table with more columns than you would put in an index.

Width is also limited by the engine. Every database caps the number of columns per index and the size of an index entry.

<Callout kind="note" title="INCLUDE: non-key columns">

SQL Server and PostgreSQL 11 and later can add **non-key columns** to a B-tree index. They are stored in the leaf nodes only, not in the branch nodes, so they cannot be access predicates, but they keep the tree narrow and they cover the select list:

```sql
 CREATE INDEX empsubupnam
     ON employees
       (subsidiary_id, last_name)
INCLUDE(phone_number, first_name)
```

</Callout>

  InnoDB caps an index key at 3072 bytes with the `DYNAMIC` or `COMPRESSED` row format, which has been the default since 5.7.9, and at 767 bytes with the older `REDUNDANT` and `COMPACT` formats. The `innodb_large_prefix` switch that used to govern this is gone in 8.0. MyISAM allows 16 columns and 1000 bytes.

  MySQL also has **prefix indexing**, which indexes only the first characters of a column and is unrelated to the partial indexes of [Chapter 2](/sql/where-clause/partial-and-filtered-indexes/). If a column is longer than the key limit allows, MySQL in strict SQL mode, the default since 5.7, refuses the index with error 1071, "Specified key was too long; max key length is … bytes". Only with strict mode off does it shorten the key to a prefix on its own and merely warn. A prefix index holds the first characters of the column, not a copy of it, so selecting that column prevents an index-only scan, just as with a function-based index. The prefix can also be asked for explicitly to stay under the key limit:

  ```sql
  CREATE INDEX .. ON employees (last_name(10))
  ```

  </Fragment>
  <Fragment slot="postgresql">
  A B-tree entry may not exceed 2704 bytes in PostgreSQL 12 and later (2712 before), a hard-coded limit of roughly a third of the page. An index can have up to 32 columns. Index-only scans exist since 9.2, `INCLUDE` since 11.
  </Fragment>

  </Fragment>

<Callout kind="tip" title="Think about it">A query whose select list needs nothing from the table is a natural index-only scan. Can you name one that is useful? One answer: the subquery of an `EXISTS` or `IN`, which only needs to know whether a row is there. `COUNT(*)` with an indexed where clause is another.</Callout>
