The word cluster means different things. A star cluster is a group of stars; a computer cluster is a group of machines that work together, for performance or for failover. In a database conversation "let's use a cluster" could mean either of those or something else entirely: a **data cluster**, which is data that is read together stored together, so that reading it takes fewer I/O operations. This unit is about data clusters, and about the fact that an index is the simplest tool for building one.

## 1. Clusters, from the row up

The smallest cluster in a SQL database is the row. All columns of a row sit in the same block whenever they fit; only oversized rows, for example with LOB columns, spill over. Column stores turn that around and keep each column together instead, which suits data warehouses that read many rows but few columns.

An index clusters too. Its leaf nodes hold the indexed values in sorted order, so rows with similar values end up next to each other in the index even when they are far apart in the table. [Unit 1](/sql/anatomy/) called the B-tree traversal the first power of indexing. This ability to group related data is the **second power of indexing**, and the three lessons of this unit show how to use it.

## 2. Where the time goes

[Unit 2](/sql/where-clause/) drew a line between access predicates, which decide where an index scan starts and stops, and filter predicates, which are checked on every entry inside that range without narrowing it. A filter predicate in the index usually means the column order of a concatenated index is wrong. This lesson is about the case where it is exactly what you want: not to make the range scan faster, but to keep the rows a query needs together.

Conditions that cannot be access predicates are the candidates. A `LIKE` with a leading wildcard is the classic one:

```sql
SELECT first_name, last_name, subsidiary_id, phone_number
  FROM employees
 WHERE subsidiary_id = ?
   AND UPPER(last_name) LIKE '%INA%'
```

The pattern cannot use the tree, so an index on `last_name`, or on `UPPER(last_name)`, would not narrow the scanned range at all. The condition on `subsidiary_id`, on the other hand, is a fine access predicate, and it needs no new index: since [Unit 2](/sql/where-clause/the-equals-operator/concatenated-keys/) swapped the primary key to `(subsidiary_id, employee_id)`, `subsidiary_id` already leads the primary key index.

The cost jumps a hundredfold from the index scan to the table access. That is a common and perfectly normal pattern, but it also says where the time goes: the table access is the biggest contributor to this query's response time.

Whether it is a problem depends on where the rows are. If all 333 rows sat in one table block, one read would fetch them all. If they are spread over 333 blocks, the database reads 333 blocks. What the table access costs is set by where the rows physically are, which is to say by how tightly they are clustered.

<Callout kind="note" title="The index clustering factor">How closely the table order follows the index order is measured by the **index clustering factor**: a number that roughly says how likely it is that the next index entry points into the same table block as the current one. The optimizer uses it to cost the table access by rowid.</Callout>

One could reorder the table so that it follows the index, and some databases offer a tool for that. It is rarely practical: a table can only be stored in one order, so it can match one index only, and the tools are rudimentary. This kind of **row sequencing** is not a general solution.

## 3. Move the filter into the index

The practical solution is the second power of indexing. An index can carry as many columns as you like, and it keeps them in a well-defined order. So extend the index until it holds every column of the where clause, including the one that cannot narrow the range:

```sql
CREATE INDEX empsubupnam ON employees
       (subsidiary_id, UPPER(last_name))
```

`subsidiary_id` comes first, so it still serves as the access predicate. `UPPER(last_name)` serves the `LIKE` as an index filter predicate. Indexing the uppercase form saves a few CPU cycles per comparison; an index on the plain `last_name` would do the same job, and the next lesson gives a reason to prefer it.

Step through the figure. The access predicate confines the scan to a couple of leaf nodes. Most entries inside them fail the filter and cost nothing beyond the comparison. Only the entries that pass trigger the arrow to the table, and that arrow is where the time went.

Read the `Rows` column of the two Oracle plans. Both end at 17. In the first plan the index scan delivered 333 entries and the table was read 333 times to apply the `LIKE`. In the second, the index scan rejects the non-matching entries itself, so the table is read 17 times. The operations are identical; the number of times the expensive one runs is what changed.

<KeyIdea>An index filter predicate does not make the index scan faster. It makes the table access run fewer times, and the table access is where the time goes.</KeyIdea>

<Callout kind="warning" title="Do not add a new index for this">Never create an index just to hold a filter predicate. Extend an existing one instead, so that the maintenance cost on every write ([Unit 8](/sql/dml/)) stays low. A few engines go as far as letting you append non-key columns to the primary key index itself.</Callout>

## 4. When it is worth it

The example looks like a confirmation of the folk rule "index every column in the where clause". It is not. The rule ignores column order, and column order decides which conditions become access predicates, which has a far bigger effect on performance. The equality column goes first so that the scanned range is as small as possible; the filter column goes after it. Put `last_name` first and subsidiary 30 is scattered over the whole index.

An index also grows with every column, text columns in particular. A bigger index is never faster by itself, even if logarithmic scalability keeps the damage small. So do not put all where-clause columns into the index on principle. Add a filter column intentionally, when the access predicate already narrows the scan to a few leaves, the filter rejects most of the entries in them, and the query runs often enough to pay for the wider index.

## 5. See the filter run in the index

The playground creates `employees_sub_name` on `(subsidiary_id, last_name)`; the playground's primary key still has `employee_id` first, so the index supplies the leading `subsidiary_id`. SQLite does not print filter predicates in its plan, so use the select list to prove where the filter runs. With only `last_name` selected, the plan says `COVERING INDEX`: the `LIKE` is checked on the index entries and the table is never touched. Of the 200 employees in subsidiary 30, 33 match.
