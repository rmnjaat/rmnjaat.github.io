Performance complaints are as old as SQL. In the early years there was something to them; today the engines are fast, and yet slow statements are still an everyday sight. The reason is not the database. It is the division of labour around it, which quietly hands the one task that matters most to the people least equipped to do it.

## 1. What SQL hides

SQL is probably the most successful fourth-generation language there is. Its whole appeal is that a statement describes the result and leaves the method to the database.

```sql
SELECT date_of_birth
  FROM employees
 WHERE last_name = 'Winand';
```

You can read that aloud as a sentence. Nothing in it says which file to open, which blocks to read or how to find the matching rows, and nothing needs to. A developer can write SQL for ten years without ever learning what happens between the semicolon and the result set, and many do.

## 2. Where the abstraction stops

The separation of "what" from "how" is one of the best ideas in computing, and in SQL it works almost perfectly. The exception is performance. Because the author of a statement does not say how it should run, it is tempting to conclude that the author is not responsible when it runs slowly. Experience says the opposite. The statements that end up in the slow query log were written by people who, through no fault of their own, had never seen what the database did with them.

The good news is how little is needed to close that gap. The developer does not have to learn storage configuration, memory tuning or the file layout of the engine. The developer has to learn how to index.

## 3. Why indexing is a development task

An index is only as good as its fit to the queries that use it. The information that decides whether an index fits is the **access path**: which columns the application filters on, which it compares with equality and which with a range, what it sorts by, how many rows a call typically returns. None of that is in the hardware setup or the storage configuration. All of it is in the application code, and often in code an ORM generated.

<KeyIdea>The most important input for a good index is how the application queries the data. Development already has that information. Everyone else has to reconstruct it from the outside.</KeyIdea>

A database administrator or an outside consultant can get at the access path only by reverse-engineering the application, statement by statement, and that takes a long time. The developer who wrote the query already knows it. That asymmetry is the whole argument: indexing belongs with development, not because administrators cannot create indexes, but because they cannot know which ones to create.

## 4. What the book covers

Everything a developer needs to know about indexes, and nothing beyond that. In practice that means one index type, the **B-tree index**, because it is the default everywhere and the one that decides most of query performance. Hash indexes, bitmap indexes and full-text indexes are not covered.

B-tree indexes behave almost identically from one database to the next, so the same pages apply to Oracle, MySQL, PostgreSQL, SQL Server and Db2. The terminology, operation names such as `INDEX RANGE SCAN` and `TABLE ACCESS BY INDEX ROWID`, follows the Oracle database, with the other engines' names given where they differ. Vendor differences sit in tabs; pick your engine in the header and the matching tab opens first on every page.


## 5. How it is organised

The chapters follow the parts of an SQL statement, in the order a developer meets them. Read them in sequence the first time; each one relies on the vocabulary of the one before.

- [Chapter 1, Anatomy of an Index](/sql/anatomy/), is the only chapter that is not about SQL. It explains the structure of an index, and it is deliberately short, about eight printed pages in the book. Do not skip it: by the end of it you can already explain why an index can be slow.
- [Chapter 2, The Where Clause](/sql/where-clause/), is the main body of the book. It goes from a single-column equality lookup to ranges, `LIKE`, functions and the special cases, and it is where most of the speed-up comes from.
- [Chapter 3, Testing and Scalability](/sql/testing-scalability/), is a detour into measurement: what data volume and system load do to response time, and why more hardware is rarely the answer to a slow query.
- [Chapter 4, The Join Operation](/sql/join/), returns to SQL and shows how indexes make each join algorithm fast.
- [Chapter 5, Clustering Data](/sql/clustering/), answers whether it matters if you select one column or all of them, and shows a trick that goes further.
- [Chapter 6, Sorting and Grouping](/sql/sorting-grouping/), shows that `ORDER BY` and `GROUP BY` can use an index too.
- [Chapter 7, Partial Results](/sql/partial-results/), is about pipelined execution: stopping early when you only need the first rows.
- [Chapter 8, Insert, Delete and Update](/sql/dml/), measures what every index costs on writes. Indexes are not free.

The reference pages support the chapters: [Execution Plans](/sql/explain-plan/) shows how to ask each database what it did with a statement, the [Myth Directory](/sql/myth-directory/) collects advice that sounds right and is not, the [Example Schema](/sql/example-schema/) has the `CREATE` and `INSERT` statements behind every example, each term is explained in the chapter that introduces it, and [About](/sql/about/) says where this site comes from.
