There is a third way to fetch a page, and it is the most portable one: number the sorted rows with a window function and filter on the number. It is flexible and it is standard SQL. The catch is execution. Three engines stop once the page is full, SQL Server, Oracle and PostgreSQL from release 15; MySQL, MariaDB and Db2 LUW keep reading the index after the page is complete and pay for every row in the table.

## 1. Numbering the rows

`ROW_NUMBER()` assigns consecutive numbers to the rows in the order given by its `OVER` clause. Put it in a subquery and filter on the number outside. The second page of ten:

```sql
SELECT *
  FROM ( SELECT sales.*
              , ROW_NUMBER() OVER (ORDER BY sale_date DESC
                                          , sale_id   DESC) rn
           FROM sales
       ) tmp
 WHERE rn between 11 and 20
 ORDER BY sale_date DESC, sale_id DESC
```

The window's `ORDER BY` is a sort like any other, and the same index that makes a top-N query pipelined, `sl_dtid` on `(sale_date, sale_id)`, feeds the numbering in order without a sort. The open question is what happens after row 20. The outer filter can never match row 21 or anything later, because row numbers only go up. An optimizer that knows this stops the scan. One that does not numbers all million rows and then discards all but ten.

<KeyIdea>The index removes the sort on every engine. Stopping after row 20 is a separate optimisation, and not every engine has it.</KeyIdea>

## 2. Who stops and who does not

<EngineTabs>
  <Fragment slot="oracle">
  Oracle sees that nothing past row 20 can pass the filter and runs the statement as a pipelined top-N query over the index.
  ```
  ---------------------------------------------------------------
  |Id | Operation                      | Name    | Rows |  Cost |
  ---------------------------------------------------------------
  | 0 | SELECT STATEMENT               |         | 1004K| 36877 |
  |*1 |  VIEW                          |         | 1004K| 36877 |
  |*2 |   WINDOW NOSORT STOPKEY        |         | 1004K| 36877 |
  | 3 |    TABLE ACCESS BY INDEX ROWID | SALES   | 1004K| 36877 |
  | 4 |     INDEX FULL SCAN DESCENDING | SL_DTID | 1004K|  2955 |
  ---------------------------------------------------------------

  Predicate Information (identified by operation id):
  ---------------------------------------------------
  1 - filter("RN">=11 AND "RN"<=20)
  2 - filter(ROW_NUMBER() OVER (
             ORDER BY "SALE_DATE" DESC, "SALE_ID" DESC )<=20)
  ```
  `WINDOW NOSORT STOPKEY` says two things: there is no sort (`NOSORT`) and the execution aborts at the upper threshold (`STOPKEY`). Everything below the stop point is pipelined, so this costs the same as `OFFSET` paging in the previous lesson, no more and no less.
  </Fragment>
  <Fragment slot="db2">
  Db2 LUW 10.5 avoids the sort but does not execute the query as a top-N query. It reads the entire index and filters afterwards.
  ```
  Explain Plan
  -------------------------------------------------------------
  ID | Operation                   |               Rows |  Cost
   1 | RETURN                      |                    | 65658
   2 |  FILTER                     |  100933 of 1009326 | 65658
   3 |   FETCH SALES               | 1009326 of 1009326 | 65295
   4 |    IXSCAN (REVERSE) SL_DTID | 1009326 of 1009326 |  5679

  Predicate Information
   2 - RESID (11 <= Q3.$C8)
       RESID (Q3.$C8 <= 20)
  ```
  To get a proper abort after 20 rows, wrap the query twice: the inner query applies the top-N condition `rn <= 20`, the outer one removes the first ten.
  ```sql
  SELECT *
    FROM (SELECT *
            FROM (SELECT sales.*
                       , ROW_NUMBER() OVER (ORDER BY sale_date DESC
                                                   , sale_id   DESC) rn
                   FROM sales
                 ) tmp
           WHERE rn <= 20
         ) tmp2
   WHERE rn > 10
   ORDER BY sale_date DESC, sale_id DESC;
  ```
  ```
  Explain Plan
  -----------------------------------------------------------------
  ID | Operation                       |               Rows |  Cost
   1 | RETURN                          |                    |    21
   2 |  FILTER                         |            7 of 20 |    21
   3 |   FETCH SALES                   |      20 of 1009326 | 65352
   4 |    IXSCAN (REVERSE) SL_DTID     | 1009326 of 1009326 |  5736

  Predicate Information
   2 - RESID (10 < Q3.$C8)
  ```
  The filter `rn <= 20` is not listed in the predicate section, yet the row estimate of 20 shows it is applied.
  </Fragment>
  <Fragment slot="postgresql">
  Since version 15 the plan shows a **run condition**, which lets the window node stop the scan below it once the condition can no longer be met.
  ```
                       QUERY PLAN
  -------------------------------------------------------
   Subquery Scan on tmp
      (cost=0.42..141724.98 rows=334751 width=249)
      (actual time=0.040..0.052 rows=10 loops=1)
   Filter: (tmp.rn >= 11)
   Rows Removed by Filter: 10
   Buffers: shared hit=5
   -> WindowAgg
         (cost=0.42..129171.80 rows=1004254 width=249)
         (actual time=0.028..0.049 rows=20 loops=1)
      Run Condition: (row_number() OVER (?) <= 20)
      Buffers: shared hit=5
      -> Index Scan Backward using sl_dtid on sales
             (cost=0.42..111597.36 rows=1004254 width=241)
             (actual time=0.018..0.025 rows=22 loops=1)
         Buffers: shared hit=5
  ```
  The index scan actually returned 22 rows and the window 20, from a table of a million. Releases before 15 have no run condition and number every row.
  </Fragment>
  <Fragment slot="sql-server">
  SQL Server reads the index in order, computes the numbers, and stops once the page is complete, provided the function is `ROW_NUMBER()`. Since 2012, `OFFSET ... FETCH` expresses the same thing natively.
  </Fragment>
  <Fragment slot="mysql">
  MySQL has window functions since 8.0 and MariaDB since 10.2. Neither aborts the index scan after the page: the window runs to the end of the table before the outer filter is applied. Use `LIMIT` with the seek method instead.
  </Fragment>
  <Fragment slot="sqlite">
  SQLite has window functions since 3.25. The plan shows a co-routine that scans the whole index; the filter on `rn` is applied afterwards, so there is no early abort.
  </Fragment>
</EngineTabs>

## 3. Support across products

The optimisation is far from universal, and it has arrived at different times.

<Figure n="7.5" title="Pipelined top-N with window functions, by product and release">

| Product | Releases | Status |
| --- | --- | --- |
| SQL Server | 2008 R2 to 2025 | partial, only with ROW_NUMBER() |
| Oracle | 11gR1 to 11gR2 | partial |
| Oracle | 12cR1 to 23 | partial, not with PARTITION BY |
| PostgreSQL | 9.0 to 14 | none |
| PostgreSQL | 15 to 16 | partial, not with PARTITION BY |
| PostgreSQL | 17 to 18 | full |
| MySQL | 8.0.18 onwards | none |
| MariaDB | 10.2 onwards | none |

<p slot="caption">"Partial" means the abort works for some functions or clauses only; see the two tables below.</p>
</Figure>

In principle the optimisation could work with any monotonic function, but the implementations concentrate on `ROW_NUMBER`.

<Figure n="7.6" title="Which functions keep the early abort">

| | MariaDB | MySQL | Oracle | PostgreSQL | SQL Server |
| --- | --- | --- | --- | --- | --- |
| ROW_NUMBER() | no | no | yes | yes | yes |
| RANK() | no | no | only with a where clause on the partition | yes | no |
| DENSE_RANK() | no | no | no | yes | no |
| COUNT(...) | no | no | no | yes | no |

<p slot="caption">Latest releases at the time of the original survey: MariaDB 12.3, MySQL 26.7, Oracle 23, PostgreSQL 18, SQL Server 2025.</p>
</Figure>

`PARTITION BY` deserves extra care. In some products its mere presence disables the optimisation, even when the where clause restricts the rows to a single partition. That happens easily when the partitioned window function lives in a view and the outer query filters the view down to one partition.

<Figure n="7.7" title="Which clauses keep the early abort">

| | MariaDB | MySQL | Oracle | PostgreSQL | SQL Server |
| --- | --- | --- | --- | --- | --- |
| OVER(ORDER BY ...) | no | no | partial | yes | yes |
| OVER(ORDER BY ...) + WHERE x = ? | no | no | yes | yes | yes |
| OVER(PARTITION BY x ORDER BY ...) + WHERE x = ? | no | no | no | yes | yes |

<p slot="caption">For Oracle, "partial" means not every function that works with a where clause also works without one.</p>
</Figure>

<Callout kind="warning" title="Common mistake">Expecting the window function to behave like `FETCH FIRST` because the plan shows no sort. The absence of a sort only says the index supplied the order. Whether the scan stops after the page is a separate question, and on MySQL, MariaDB and Db2 the answer is no.</Callout>

## 4. Where window functions belong

Pagination is not what window functions are good at. Their strength is analytical calculation, running totals, rankings within groups, comparisons with the previous row, and if you have never used them it is worth a few hours with the documentation: [Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Analytic-Functions.html), [PostgreSQL](https://www.postgresql.org/docs/current/tutorial-window.html), [SQL Server](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-over-clause-transact-sql?view=sql-server-ver16). For paging, reach for `FETCH FIRST` and the [seek method](/sql/partial-results/fetch-next-page/) first, and for `ROW_NUMBER` when the same SQL has to run on an engine without them.

<Callout kind="note">A `ROW_NUMBER` range filter is still an offset in disguise. Page 500 is rows 4,991 to 5,000, and even an engine that stops early numbers the first 4,990. Combine the window function with a seek condition in the where clause to avoid that.</Callout>
