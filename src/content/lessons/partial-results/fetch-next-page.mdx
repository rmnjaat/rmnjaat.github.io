The [previous page](/sql/partial-results/top-n-queries/) fetched the first page with a pipelined top-N query. Then the user clicks "next", and a second query has to deliver the rows after the ones already shown. The hard part is skipping them. Two approaches exist. With the **offset method** the database counts rows from the start of the result and discards the ones before the page. With the **seek method** the query names the last row the user saw and asks for what sorts after it.

## 1. The offset method

Offset paging is the version in every tutorial, and most engines have a keyword for it. `OFFSET` is even in the SQL standard now, alongside `FETCH FIRST`. The examples fetch the second page of ten.

  </Fragment>

  MySQL and PostgreSQL append `OFFSET` to the `LIMIT` clause. The offset discards rows from the start of the top-N result, and the limit is applied after it.
  ```sql

    FROM sales
   ORDER BY sale_date DESC
   LIMIT 10 OFFSET 10
  ```
  </Fragment>
  <Fragment slot="oracle">
  Oracle supports `OFFSET` since 12c. Earlier releases have `ROWNUM`, but a greater-than-or-equal filter cannot be applied to the pseudo column directly. The row numbers first have to be materialized under an alias in a nested query.

    FROM ( SELECT tmp.*, rownum rn
             FROM ( SELECT *

  </Fragment>

The method is simple, and any page can be fetched from its offset alone. The price is that the database has to count from the beginning every time. An index tells it where a *value* lives, not where the eleventh entry lives, so the scan starts at the top of the index for every page and runs past all the rows of the pages before it.

<Pagination client:visible n="7.2" />

That has two consequences. First, the pages **drift**: insert a new sale between two requests and the numbering starts from scratch, so the last row of page one shows up again at the top of page two and one row is never shown. Second, the response time **grows** the further back the user browses, because more rows have to be counted and discarded.

## 2. The seek method

The seek method sidesteps both problems. Instead of a row count it takes the last row of the previous page and asks, in an ordinary where clause, for everything that sorts after it. Rows the user has already seen are excluded by the condition itself.

Start with a simplifying assumption: one sale per day, so `sale_date` is unique. The rows that come after a given date in descending order are the ones with a smaller date, so the condition is `<`. For an ascending order it would be `>`. The `FETCH FIRST` clause only limits the page size.

```sql
SELECT *
  FROM sales
 WHERE sale_date < ?
 ORDER BY sale_date DESC
 FETCH FIRST 10 ROWS ONLY
```

Where the offset method had a number, this query has a value: the last date the previous page showed. The gain is large: `sale_date < ?` is an access predicate, so the database traverses the tree to the boundary and starts reading there. The skipped rows are truly skipped. And because the boundary is a value, an inserted row cannot shift the page.

### The order has to be deterministic

The assumption does not survive contact with real data. Several sales share a date, and `sale_date < 'yesterday'` skips *all* of yesterday's rows, not only the ones page one showed. The root cause is that `ORDER BY sale_date DESC` does not define a unique row sequence, and a range condition on the page boundary needs one.

An `ORDER BY` that leaves ties is, by definition, not deterministic. You usually get the same sequence every time because the database usually runs the query the same way, but it is allowed to shuffle the rows of equal date and still satisfy the `ORDER BY`. With parallel execution it may actually do so: the same plan can return a different sequence on each run because the worker threads finish in a different order.

<Callout kind="important">Paging requires a deterministic sort order.</Callout>

Even when the specification only says "newest first", you as the developer have to make the `ORDER BY` deterministic. If the index that serves the pipelined `ORDER BY` has further columns, add those first, so the index stays usable. If ties remain, append a column that is unique, and put the same column at the end of the index. Here the primary key `sale_id` does the job.

```sql
CREATE INDEX sl_dtid ON sales (sale_date, sale_id)
```

```sql
SELECT *
  FROM sales
 WHERE (sale_date, sale_id) < (?, ?)
 ORDER BY sale_date DESC, sale_id DESC
 FETCH FIRST 10 ROWS ONLY
```

The where clause compares two columns at once, which is the point: "comes after" has to be applied to the pair, not to each column separately.

## 3. Row values

The parenthesised pair is a **row value**, a construct the SQL standard has had since SQL:92 (§7.1, "row value constructor"): an ordered list of values treated as one unit. Everyone knows the syntax from `INSERT ... VALUES (...)`; using it in a where clause is less common but just as valid, and the standard defines every comparison operator for it. Less-than is defined like this: `X < Y` is true when, for some position n, all value pairs before n are equal and the pair at n has `Xn < Yn`. In words, a row value is smaller than another if the first position where they differ is smaller. That is precisely "X sorts before Y", which is the logic the seek method needs.

<KeyIdea>`(sale_date, sale_id) < (?, ?)` means "earlier date, or the same date and a smaller id". With descending order, that is "comes after the boundary row". With an index on both columns it is an access predicate, and the query is a pipelined top-N query with a starting point.</KeyIdea>

Standard or not, support is thin.

## 4. The approximation

Where row values are not usable, the same logic can be written with ordinary comparisons. It is less elegant and not quite as efficient, but it keeps the index access. The Oracle version uses the `ROWNUM` form of the top-N query:

```sql
SELECT *
  FROM ( SELECT *
           FROM sales
          WHERE sale_date <= ?
            AND NOT (sale_date = ? AND sale_id >= ?)
          ORDER BY sale_date DESC, sale_id DESC
       )
 WHERE rownum <= 10
```

The where clause has two parts. The first, `sale_date <= ?`, looks at the date only and selects slightly more than needed. It is simple enough that every database can use it as an access predicate. The second part removes the rows of the boundary date that the previous page already showed.

<Callout kind="note" title="Indexing equivalent logic">

The same condition can be written with inclusive branches, which most people find easier to read:

```sql
WHERE (
         (sale_date < ?)
       OR
         (sale_date = ? AND sale_id < ?)
      )
```

Databases see it differently. None of them notices that both branches start at the same `sale_date`, so none of them factors `sale_date <= ?` out of the `OR`, and the whole clause becomes a filter predicate over a full index read. You can add the redundant condition yourself:

```sql
WHERE sale_date <= ?
  AND (
         (sale_date < ?)
       OR
         (sale_date = ? AND sale_id < ?)
      )
```

Now every database can use the first line as an access predicate, but the clause is harder to grasp than the `NOT` version, and the "redundant" line is at risk of being tidied away by the next person who edits the query. The `NOT` form avoids that risk.

</Callout>

The access predicate on `sale_date` lets the scan skip every day that previous pages showed completely. The filter then inspects a few entries from the boundary day again and drops them at once. The seek side of Figure 7.2 shows the access path.

## 5. What the seek method cannot do

The seek method is harder to handle, and that is its main drawback. The where clause has to be phrased with care. You cannot fetch an arbitrary page, because there is no row count to jump to. And to browse backwards you have to reverse every comparison and every sort direction: the boundary becomes the first row of the current page, `<` becomes `>`, `DESC` becomes `ASC`, and the ten rows come back in reverse. Precisely those two functions, jumping to a page and browsing back, are the ones an infinite-scrolling interface never needs, which makes it the natural fit.

<Figure n="7.4" title="Database and feature matrix for row values">

| | Db2 | MySQL | Oracle | PostgreSQL | SQLite | SQL Server |
| --- | --- | --- | --- | --- | --- | --- |
| Supported in where clause | yes | yes | yes | yes | yes | no |
| Range operators (&lt;, &gt;) | yes | yes | no | yes | yes | no |
| Optimal index usage | yes | no | yes | yes | yes | no |

<p slot="caption">Oracle's "optimal index usage" refers to the approximated form, since range operators on row values raise ORA-01796.</p>
</Figure>

<Callout kind="warning" title="Common mistake">Seeking on the sort column alone. If the sort column is not unique, the boundary skips or repeats rows at the page break. Add a unique column to both the `ORDER BY` and the comparison, and put it in the index.</Callout>
