Everybody accepts that a query gets slower as the table grows. The useful questions are how much slower it gets when the data doubles, and what you can do about that ratio. Those two questions are what database scalability is about, and the answer turns out to depend on something most people never look at in an execution plan.

## 1. What scalability means

Wikipedia [defines scalability](https://en.wikipedia.org/wiki/Scalability) as "the ability of a system, network, or process to handle a growing amount of work in a capable manner or its ability to be enlarged to accommodate that growth." The definition has two halves, and the second one gets almost all the attention. When people talk about scalability they usually mean more hardware: scaling up to a bigger machine, scaling out to more machines, or whatever the current buzzword for a very large cluster is.

The first half is the one this unit takes seriously. In the broad sense, scalability describes how performance changes when the environment changes, and hardware is only one thing in the environment that can change. The amount of data is another, and so is the number of users hammering the system at the same time. This lesson is about data volume; the [next one](/sql/testing-scalability/system-load/) is about load; the [third](/sql/testing-scalability/response-time-throughput-scaling-horizontal/) comes back to hardware.

## 2. The experiment

Take one query and run it with two different indexes. For the moment the index definitions stay hidden; by the end of the lesson you will be able to work them out from the plans alone.

```sql
SELECT count(*)
  FROM scale_data
 WHERE section = ?
   AND id2 = ?
```

The `section` column is the knob. The higher the section number, the more rows the query selects, so it stands in for a growing data volume. First, one measurement at a small section.

<p slot="caption">A clear difference, and both well under a tenth of a second.</p>

One index is almost twice as fast as the other. It is also true that both are quick enough for most purposes, so on this evidence nobody would bother. But this is one test point. To talk about scalability you have to vary something in the environment and watch what the response time does.

<Callout kind="important">Scalability is the dependency of performance on an environmental factor such as the data volume. A single performance figure is one point on that curve, nothing more.</Callout>

Now the same query across sections 1 to 100, which is a hundredfold growth in the number of rows selected.

<ScaleChart client:visible n="3.2" />

Both lines rise, as expected. What is not expected is the gap. At a hundred times the volume, the fast query takes a bit more than twice what it took at the start. The slow query takes twenty times as much, more than a full second. The chart also marks where a typical development database sits: at the far left, where the two lines are indistinguishable.

<Callout kind="tip">The [example schema](/sql/example-schema/) appendix has the scripts to build `scale_data` and repeat this measurement on Oracle, PostgreSQL or SQL Server.</Callout>

Response time depends on many things, and data volume is only one of them. The lesson of the chart is that a query being fast enough under test conditions says nothing about production, particularly when the test database holds a fraction of the production data. The further lesson is that "slower with more data" is not one thing: two queries can be on curves of entirely different shape.

The two plans in each pair are the same shape and use the same operations; the only visible difference is the index name. The cost columns do reflect that one is cheaper, but a number is not an explanation. Nothing in these plans says why.

This looks like the slow index experience from [unit 1](/sql/anatomy/slow-indexes/): the query uses an index and is slow anyway. You no longer believe in [broken indexes](/sql/myth-directory/indexes-can-degenerate/), so you go back to the two ingredients that make an index lookup slow: fetching rows from the table, and scanning a wide range of the index. Neither plan contains a `TABLE ACCESS BY INDEX ROWID` or its equivalent, so the table is not the problem. That leaves the range. One of these scans must be walking a much wider stretch of the index than the other. And the width of the scanned range is shown in one specific place in the plan: the predicate information.

## 4. The predicate information

<Callout kind="tip" title="Pay attention to the predicate information">A plan without its predicate information is incomplete. Leaving it out, as the plans above did, is exactly what hides this class of problem.</Callout>

Here are the complete plans. The structure is unchanged; the predicate section underneath is where everything happens.

<EngineTabs>
  <Fragment slot="db2">
  ```
  Explain Plan
  -------------------------------------------------------------
  ID | Operation           |                        Rows | Cost
   1 | RETURN              |                             |  208
   2 |  GRPBY (COMPLETE)   |         1 of 4456 (   .02%) |  208
   3 |   IXSCAN SCALE_SLOW | 4456 of 135449700 (   .00%) |  208

  Predicate Information
   3 - START (Q1.SECTION = ?)
        STOP (Q1.SECTION = ?)
        SARG (Q1.ID2 = ?)
  ```

  ```
  Explain Plan
  -------------------------------------------------------------
  ID | Operation           |                        Rows | Cost
   1 | RETURN              |                             |  296
   2 |  GRPBY (COMPLETE)   |         1 of 4456 (   .02%) |  296
   3 |   IXSCAN SCALE_FAST | 4456 of 135449700 (   .00%) |  296

  Predicate Information
   3 - START (Q1.SECTION = ?)
       START (Q1.ID2 = ?)
        STOP (Q1.SECTION = ?)
        STOP (Q1.ID2 = ?)
  ```

  `START` and `STOP` conditions bound the scan; a `SARG` is applied to each entry as the scan passes. With `scale_slow` only `section` starts and stops the scan and `id2` is a `SARG`. With `scale_fast` both columns bound it.

  Look at the costs too. The better index has the *higher* estimated cost, 296 against 208. If both indexes exist, Db2's optimizer picks the worse one.
  </Fragment>
  <Fragment slot="mysql">
  ```
  +------+------------+---------+-------+------+-----------------------+
  | type | key        | key_len | ref   | rows | Extra                 |
  +------+------------+---------+-------+------+-----------------------+
  | ref  | scale_slow | 6       | const |    1 | Using index condition |
  +------+------------+---------+-------+------+-----------------------+
  ```

  ```
  +------+------------+---------+-------------+------+-------+
  | type | key        | key_len | ref         | rows | Extra |
  +------+------------+---------+-------------+------+-------+
  | ref  | scale_fast | 12      | const,const |    1 |       |
  +------+------------+---------+-------------+------+-------+
  ```

  MySQL has no separate predicate section; the clues are in the columns. `ref` lists one constant for `scale_slow` and two for `scale_fast`, so only one condition was used to position the scan in the first case. `key_len` says how many bytes of the key were used: 6 against 12. And `Using index condition` in `Extra` means a condition was checked against index entries after the scan was positioned, which is the filter predicate.
  </Fragment>
  <Fragment slot="oracle">
  ```
  ------------------------------------------------------
  | Id | Operation         | Name       | Rows  | Cost |
  ------------------------------------------------------
  |  0 | SELECT STATEMENT  |            |     1 |  972 |

  Predicate Information (identified by operation id):
     2 - access("SECTION"=TO_NUMBER(:A))
         filter("ID2"=TO_NUMBER(:B))
  ```

  ```
  ------------------------------------------------------
  | Id   Operation         | Name       | Rows  | Cost |
  ------------------------------------------------------
  |  0 | SELECT STATEMENT  |            |     1 |   13 |
  |  1 |  SORT AGGREGATE   |            |     1 |      |
  |* 2 |   INDEX RANGE SCAN| SCALE_FAST |  3000 |   13 |

  Predicate Information (identified by operation id):
     2 - access("SECTION"=TO_NUMBER(:A) AND "ID2"=TO_NUMBER(:B))
  ```

  Oracle labels each condition `access` or `filter`. With `scale_slow`, `section` is an access predicate and `id2` is a filter. With `scale_fast` both are access predicates. The plans here are simplified; the [Oracle execution plan reference](/sql/explain-plan/oracle/) explains the full predicate section.
  </Fragment>
  <Fragment slot="sql-server">
  ```
  |--Compute Scalar
     |--Stream Aggregate(Count(*))
        |--Index Seek(OBJECT:scale_slow),
           SEEK:(scale_data.section=1),
           WHERE:(scale_data.id2=1234) ORDERED FORWARD)
  ```

  ```
  |--Compute Scalar
     |--Stream Aggregate(Count(*))
        |--Index Seek(OBJECT:(scale_data.scale_fast),
           SEEK:(scale_data.section=1)
            AND  scale_data.id2=1234) ORDERED FORWARD)
  ```

  `SEEK` is SQL Server's word for access predicates. A `WHERE` on an index operation is a filter applied to the entries the seek produces, and it does not narrow the scanned range. In the graphical plan the same information is only visible when you hover over the `Index Seek` operator: look for "Seek Predicates" versus plain "Predicate".
  </Fragment>
  <Fragment slot="postgresql">
  PostgreSQL does not label the two kinds. Any condition the index can evaluate goes into `Index Cond`, whether it bounds the scan or is checked on every entry; `Filter` is mostly for conditions the index cannot evaluate at all. To tell them apart, compare the columns in `Index Cond` with the column order of the index: conditions on the leading columns bound the scan, a condition on a later column with no condition on the column before it is a filter. The [PostgreSQL execution plan reference](/sql/explain-plan/postgresql/) has the details.
  </Fragment>
</EngineTabs>

Now the difference is plain. With `scale_slow`, only the condition on `section` is an **access predicate**: it tells the scan where to start and where to stop. The database reads every index entry in that section and throws away the ones whose `id2` does not match. The work grows with the number of rows in the section. With `scale_fast`, both conditions are access predicates, the scan starts and stops exactly around the matching entries, and the work grows only with the number of rows actually selected.

<KeyIdea>An access predicate narrows the range the index scan reads. A filter predicate only narrows the result. The index is "used" either way; only the first is fast at volume.</KeyIdea>

<Callout kind="important">A filter predicate is a time bomb: harmless at today's volume, and nothing in the plan says when it goes off. Usually that is months later, once the data has grown enough.</Callout>

## 5. Reading the index definitions back

The last piece of the puzzle is the two index definitions, and the predicate information is enough to reconstruct them.

`scale_slow` must begin with `section`, otherwise `section` could not be an access predicate. `id2` is not an access predicate, so it cannot be the second column either: if it were, the tree could use it. So `scale_slow` has at least three columns, with `section` first and `id2` somewhere after the second position. That is exactly what it is:

```sql
CREATE INDEX scale_slow ON scale_data (section, id1, id2)
```

The `id1` column in the middle is what stops `id2` from being an access predicate. The query says nothing about `id1`, so after positioning on `section` the tree has no way to narrow further.

`scale_fast` must have `section` and `id2` in its first two positions, in some order, because both are access predicates. The plans cannot say which comes first. The index used in the test starts with `section`, and carries `id1` as a third column:

```sql
CREATE INDEX scale_fast ON scale_data (section, id2, id1)
```

`id1` is there only so that both indexes have the same size and the same number of columns. Without it, you might suspect the smaller index wins because it is smaller. It does not; it wins because of column order.

<Callout kind="warning" title="Common mistake">"The index has all three columns, so the query can use all three conditions." Column order is not a detail. A condition can only be an access predicate if every column before it in the index also has an equality condition in the query. Unit 2's lesson on [concatenated indexes](/sql/where-clause/the-equals-operator/concatenated-keys/) goes through this in full.</Callout>
