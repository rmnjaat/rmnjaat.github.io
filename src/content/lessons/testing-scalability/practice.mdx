  - Read the access predicates off a SQLite plan and name the filter predicates by their absence
  - Predict which of two queries with identical timings will scale and which will not
  - Explain why a query's work can grow with the table while its result stays the same size
recap:
  - In SQLite the conditions in parentheses after the index name are the access predicates. A condition on an indexed column that is missing there is a filter.
  - "A SCAN of a covering index is still a scan: every entry is read and checked."
  - What scales is the number of entries the scan visits, not the number of rows the query returns.

Every query in these exercises returns in a fraction of a millisecond on the thousand-row playground. Ignore the timings. For each one, decide from the plan alone whether the work grows with the table or with the result, and then check your reasoning against the hints.

## Exercise 1: one index, two queries

The playground creates an index on `employees (subsidiary_id, last_name)`. The two queries below both count Winands and both use that index. Only one of them is bounded.

Expected result: the first query counts 66 rows with a `SCAN ... USING COVERING INDEX`, the second counts 33 with a `SEARCH` that lists both columns.

<TryIt id="p3.1" tasks={[
  { text: 'Run the query. The plan is <code>SCAN employees USING COVERING INDEX emp_sub_name</code>. Used, yes; but a SCAN reads the whole index and checks <code>last_name</code> on every one of a thousand entries.', sql: 'last_name\\s*=', plan: '^SCAN employees USING COVERING INDEX emp_sub_name' },
  { text: 'Add <code>subsidiary_id = 20 AND</code> in front of the name condition. The plan becomes a <code>SEARCH</code> with both columns in the parentheses: the walk starts and stops at the Winands of subsidiary 20.', sql: 'subsidiary_id\\s*=\\s*20', plan: 'SEARCH employees USING COVERING INDEX emp_sub_name \\(subsidiary_id=\\? AND last_name=\\?\\)' },
]} setup={`CREATE INDEX emp_sub_name ON employees (subsidiary_id, last_name);`} sql={`SELECT COUNT(*)
  FROM employees
 WHERE last_name = 'Winand';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Which one scales?</summary><div class="d">The first query's work is the size of the index: ten million employees means ten million entries read. The second query's work is the number of Winands in one subsidiary, however big the company gets.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>SELECT COUNT(&#42;)
  FROM employees
 WHERE subsidiary&#95;id = 20
   AND last&#95;name = 'Winand';
-- plan: SEARCH employees USING COVERING INDEX emp&#95;sub&#95;name (subsidiary&#95;id=? AND last&#95;name=?)
-- 33</pre></div></details>
  </Fragment>
</TryIt>

## Exercise 2: the condition that vanishes

Same index. This time the query filters on `subsidiary_id` and on `date_of_birth`, which is not in the index at all.

Expected result: 147 employees of subsidiary 20 born before 1970. The plan says `SEARCH employees USING INDEX emp_sub_name (subsidiary_id=?)`: one access predicate, and the date condition nowhere to be seen.

<TryIt id="p3.2" tasks={[
  { text: 'Run the query and find the parentheses. Only <code>subsidiary_id</code> is there. The date condition is checked on each of the 500 rows of subsidiary 20 after the table access.', sql: 'date_of_birth\\s*<', plan: 'SEARCH employees USING INDEX emp_sub_name \\(subsidiary_id=\\?\\)' },
  { text: 'Now count the whole subsidiary instead: remove the date condition. The plan says <code>COVERING INDEX</code> and still <code>(subsidiary_id=?)</code>. Same access path, but no table access at all this time.', sql: 'subsidiary_id\\s*=\\s*20', plan: 'SEARCH employees USING COVERING INDEX emp_sub_name \\(subsidiary_id=\\?\\)' },
]} setup={`CREATE INDEX emp_sub_name ON employees (subsidiary_id, last_name);`} sql={`SELECT COUNT(*)
  FROM employees
 WHERE subsidiary_id = 20
   AND date_of_birth < '1970-01-01';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>What would make the date an access predicate?</summary><div class="d">An index on <code>(subsidiary_id, date_of_birth)</code>. Then the scan would start at the first employee of subsidiary 20 and stop at the first one born in 1970. With the current index the scan covers the whole subsidiary and the table access runs 500 times to find 147.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>SELECT COUNT(&#42;)
  FROM employees
 WHERE subsidiary&#95;id = 20;
-- plan: SEARCH employees USING COVERING INDEX emp&#95;sub&#95;name (subsidiary&#95;id=?)
-- 500</pre></div></details>
  </Fragment>
</TryIt>

## Exercise 3: a count over a date range

No index on `sales` beyond the primary key this time. Count the sales of one month, then build the index and count again, then widen the range.

Expected result: 938 sales in June 2024, with a `SCAN sales` before the index and a `SEARCH ... COVERING INDEX` after. The whole of 2024 has 11,442 sales and the plan does not change.

<TryIt id="p3.3" tasks={[
  { text: 'Run the count. <code>SCAN sales</code>: twenty thousand rows read to count 938. The work is the size of the table.', sql: 'count\\(\\*\\)', plan: '^SCAN sales$' },
  { text: 'Create an index <code>sales_date</code> on <code>sales (sale_date)</code> and run the count again. <code>SEARCH sales USING COVERING INDEX sales_date (sale_date>? AND sale_date<?)</code>: both bounds are access predicates and the work is the size of the result.', sql: 'count\\(\\*\\)', plan: 'SEARCH sales USING COVERING INDEX sales_date' },
  { text: 'Widen the range to all of 2024 (<code>2024-01-01</code> to <code>2025-01-01</code>). The plan is identical and the count is 11,442. The plan says which path; the range says how far.', sql: '2025-01-01', plan: 'SEARCH sales USING COVERING INDEX sales_date' },
]} sql={`SELECT COUNT(*)
  FROM sales
 WHERE sale_date >= '2024-06-01'
   AND sale_date <  '2024-07-01';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Which of the three scales with the table?</summary><div class="d">Only the first. After the index exists, the work of both counts grows with the number of sales in the range, not with the number of sales in the table. The year-long count does twelve times the work of the month-long count, and that stays true at any table size.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>CREATE INDEX sales&#95;date ON sales (sale&#95;date);
SELECT COUNT(&#42;)
  FROM sales
 WHERE sale&#95;date &gt;= '2024-01-01'
   AND sale&#95;date &lt;  '2025-01-01';
-- plan: SEARCH sales USING COVERING INDEX sales&#95;date (sale&#95;date&gt;? AND sale&#95;date&lt;?)
-- 11442</pre></div></details>
  </Fragment>
</TryIt>

<Callout kind="tip">A habit worth keeping from these three: before trusting a fast timing, find the parentheses in the plan and ask what is missing from them.</Callout>
