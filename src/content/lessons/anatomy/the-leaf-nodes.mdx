"An index makes the query fast" is the shortest explanation of an index there is, and it is true. It is also useless for deciding which index to create, or for understanding why a query with an index is still slow. This chapter opens the index up far enough to answer those questions and no further: the structure, not the implementation details.

## 1. A separate, redundant structure

An index is built with one statement and lives apart from the table it describes.

```sql
CREATE INDEX sales_date ON sales (sale_date);
```

After this runs, the `sales` table is exactly what it was. Not one row moved, not one byte changed. What exists now, in addition, is a second structure on its own disk space that holds a copy of the `sale_date` column for every row, together with a pointer back to that row. Everything in the index already exists in the table; the index is pure redundancy, kept because it is in a different, more useful order.

The comparison with the index at the back of a book is accurate as far as it goes. The book index also takes its own pages, repeats words that already appear in the text, and exists only to point at the place where the real content is.

<Callout kind="note" title="Clustered indexes and index-organized tables">SQL Server and MySQL's InnoDB engine stretch the word "index" a little further. A table whose rows are themselves stored inside an index structure is called a **clustered index** there; Oracle calls the same thing an **index-organized table**. For this chapter, think of the table and the index as two separate things. [Chapter 5](/sql/clustering/) covers the clustered variants and their trade-offs.</Callout>

## 2. Sorted, and under constant change

Looking something up in an index is like looking something up in a printed telephone directory. The entries are in a well-defined order, and because the order is known, the position of any entry can be found quickly without reading the ones before it. Sorted order is the entire source of the speed.

The difference is that a printed directory never changes between printings. There is no room between two printed lines for a new name, so new entries wait for the next edition. A database cannot wait. It has to apply every `INSERT`, `DELETE` and `UPDATE` as it arrives, keep the index in order afterwards, and do so without rewriting the index each time.

Think about what a naive sorted array would cost. Inserting a sale dated 2024-03-15 into a contiguous array of twenty thousand entries means shifting every later entry one place along. That is most of the index, copied, for one row. Storing the entries physically in sorted order is out of the question.

<KeyIdea>The index keeps a **logical** order that is independent of where the entries physically sit. That is the only way to stay sorted while taking inserts at full speed.</KeyIdea>

## 3. The doubly linked list

The logical order comes from a **doubly linked list**. Each node in the list holds a reference to the node before it and the node after it, like links in a chain. To insert a new node between two neighbours, the database changes the two neighbours' references to point at the newcomer and gives the newcomer references back to them. Where the new node physically lands is irrelevant; the links carry the order.

Because every node knows both neighbours, the list can be walked in either direction. The database can read an index from the smallest key upwards or from the largest downwards, which [chapter 6](/sql/sorting-grouping/) relies on for `ORDER BY ... DESC`.

The structure is not exotic. Most standard libraries ship one.

## 4. Leaf nodes and blocks

A database does not link individual entries. It links **leaf nodes**, and each leaf node is one **database block** (PostgreSQL and SQL Server say **page**), the smallest unit the storage layer reads and writes. All index blocks have the same size, typically a few kilobytes, and the database packs as many entries into each one as will fit, often a few hundred.

So the order is kept at two levels. Inside a leaf node the entries are sorted. Between leaf nodes, the doubly linked list says which node holds the next larger keys. A node can sit anywhere on disk, wherever there was space when it was written, and the links tie it into the right place in the sequence.

Step through the figure. The top row is the logical order: four leaves, each sorted, linked in both directions. The bottom row is the same four leaves in disk order, which has nothing to do with the key order. An insert into a leaf that still has room shifts a few hundred bytes inside one block. An insert into a full leaf takes a fresh block from anywhere, moves half the entries over, and fixes two links. Nothing else in the index moves.

## 5. What an index entry contains, and what the table looks like

Each entry in a leaf node is two things: the values of the indexed columns, which serve as the key, and a **ROWID** (Oracle's term; SQL Server says RID, PostgreSQL `ctid`, the tuple identifier) that is the physical address of the row the values came from. Nothing else is copied. For `sales_date` the entry is `(sale_date, ROWID)`; `eur_value`, `quantity` and every other column still exist only in the table.

The table side of that picture is as important as the index side. The table is a **heap**: rows are stored wherever a block had room when they were inserted, there is no ordering among the rows inside a block, and there is no relationship between one block and the next. Every order the database can exploit lives in an index, and only there.

<Callout kind="warning" title="Common mistake">"Creating an index sorts the table." It does not. The table stays an unsorted heap; the index is a sorted copy of a few columns beside it. This is why a query that needs columns the index does not hold must still fetch each row from the table, one block at a time, and why that fetch is in index order rather than disk order.</Callout>

## 6. What the list cannot do

A linked list has one weakness, and it is the reason this page is not the whole story. To reach the leaf that holds 2024-06-15 by following links, the database would have to start at the first leaf and read every one before it. On a small index that is a few blocks. On a large one it is a scan of the whole index, which is no better than a scan of the table. The [next page](/sql/anatomy/the-tree/) adds the second structure, a balanced search tree, that jumps to the right leaf in a handful of reads and leaves the chain to do the one thing it is good at.
