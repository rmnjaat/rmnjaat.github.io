A `GROUP BY` has to bring together every row that shares a key before it can produce a single aggregate. Databases do that in one of two ways, and only one of the two can take advantage of an index. This lesson shows how that one becomes a pipeline, using the same index as the previous two lessons.

## 1. Two ways to group

The **hash algorithm** builds a temporary hash table with one entry per group. Each input row is looked up by its grouping key and folded into that entry. When the last input row has been processed, the hash table *is* the result and gets returned.

The **sort/group algorithm** begins by ordering the input on the grouping key. Rows with the same key are now adjacent, so a single pass aggregates each run of equal keys and emits a group whenever the key changes.

Both algorithms materialize an intermediate state. The hash table cannot be returned before the last row has been seen, and the sort cannot emit its first row before the last one has gone in. Neither is pipelined as such. But the sort/group algorithm has a way out: if an index delivers the rows in grouping-key order, the sort is unnecessary, and what remains is a **pipelined group by**.

<Callout kind="note" title="MySQL">MySQL has no hash aggregate operator as such. It groups through an internal temporary table (`Using temporary`) or, when an index delivers the rows in group order, with a `Group aggregate`. The index optimization described below works all the same.</Callout>

## 2. The pipelined group by

Yesterday's revenue per product.

```sql
SELECT product_id, sum(eur_value)
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 GROUP BY product_id
```

The index `sales_dt_pr` on `(sale_date, product_id)` from the [previous lesson](/sql/sorting-grouping/order-by-asc-desc-nulls-last/) finds the day with a range scan, and inside that day the entries are in product order. That is exactly the order the sort/group algorithm needs, so the database can skip the sort and the materialization that comes with it.

Except for Oracle's `NOSORT` marker, the plans simply do not mention a sort. The absence is the evidence.

<KeyIdea>A pipelined `GROUP BY` has the same prerequisites as a pipelined `ORDER BY`: the index that serves the where clause must deliver the scanned range in grouping-key order. The only difference is that `GROUP BY` has no `ASC` and `DESC`.</KeyIdea>

Because grouping has no direction, an index defined with `ASC` and `DESC` modifiers should serve a pipelined group by just as well, and the same goes for `NULLS FIRST` and `NULLS LAST`. Should. Not every engine gets this right.

<Callout kind="warning" title="Engine traps">

On PostgreSQL an index that was built with `NULLS FIRST` on an ascending column may fail to deliver a pipelined group by on its own; adding an `ORDER BY` that names the index columns in index order gets it back.

Oracle will not combine a backward index read with a pipelined group by when an `ORDER BY` follows; the sort comes back.

</Callout>

## 3. Where it breaks

Widen the where clause to every sale since yesterday, as the first lesson did for `ORDER BY`.

```sql
SELECT product_id, sum(eur_value)
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 GROUP BY product_id
```

The range scan now covers several days, and the entries are in product order within each day, not across the whole range (compare [Figure 6.1](/sql/sorting-grouping/indexed-order-by/)). The index no longer delivers the grouping key in order, so the pipelined group by is gone.

<Callout kind="warning" title="Common mistake">Expecting the index to keep the group by pipelined after changing `=` to `>=`. The where clause still uses the index. What changed is the order of the scanned range, and that is what the grouping depends on.</Callout>

## 4. What the hash algorithm does better

Oracle's choice above is not a mistake. The hash algorithm only has to buffer the aggregated result, one entry per group, while the sort/group algorithm has to materialize the complete input before it can aggregate anything. When the index cannot supply the order, hashing needs far less memory than sorting, and the optimizer is right to pick it.

That puts the pipelined group by in perspective. Its point is not that it is the fastest way to compute a sum. Its point is that it delivers the first group before it has read the whole input, the same property the pipelined `ORDER BY` has. That is the precondition for everything in [Unit 7](/sql/partial-results/), where the query stops after a few rows.

<KeyIdea title="Remember">Fast execution is the lesser benefit. The pipelined group by matters because the first result leaves before the last row is read.</KeyIdea>
