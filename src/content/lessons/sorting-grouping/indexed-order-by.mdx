Sorting is the kind of work a database cannot hide. It burns CPU, but the real problem is memory: a sort must read its whole input before it can emit a single row, so the entire intermediate result has to be buffered somewhere. Nothing about a sort is pipelined, and for a large result that is exactly the wrong property. An index, on the other hand, stores its entries presorted. Reading the index in order gives the database a sorted result for free, and this lesson is about making that happen.

## 1. The third power of indexing

An index is sorted exactly as if you had written its column list into an `ORDER BY` clause. [Unit 1](/sql/anatomy/) showed the leaf nodes as a sorted, doubly linked chain. If the leaves are already in the order the query wants, the database can walk the chain and skip the sort operation entirely.

Skipping the sort is the smaller half of the gain. The larger half is that the first row leaves the database as soon as it has been found, without waiting for the last one. The `ORDER BY` executes as a pipeline. [Unit 7](/sql/partial-results/) builds efficient paging on that property, which is why it earns a name of its own.

<Callout kind="note" title="The three powers of indexing">The [B-tree traversal](/sql/anatomy/the-tree/) is the first power. [Clustering](/sql/clustering/) is the second. The pipelined `ORDER BY` is the third.</Callout>

There is a catch the optimizer has to weigh. An index range scan followed by a table access per row gets expensive for large results, and that can eat the saving from the avoided sort. A full table scan with an explicit sort is sometimes the faster plan. Choosing between them is the optimizer's job; yours is to make the pipelined plan possible.

## 2. The sort shows up in the plan

Take yesterday's sales, ordered by date and product.

```sql
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY sale_date, product_id
```

There is an index on `sale_date`, and the where clause uses it. The `ORDER BY` is another matter: the rows come out of the index in date order, but within the day they are in no particular product order, so the database has to sort them.

## 3. Extend the index to match the ORDER BY

A range scan already returns entries in index order. The only thing missing is that the index order and the `ORDER BY` do not agree past the first column. Make them agree.

```sql
DROP INDEX sales_date;

CREATE INDEX sales_dt_pr ON sales (sale_date, product_id);
```

Same query, new plans.

The query still has its `ORDER BY`, but the sort operation has left the plan. The database reads the entries in index order and passes them straight through.

<KeyIdea>When the index order matches the `ORDER BY`, the database can leave out the sort. The index that finds the rows must be the same index that orders them.</KeyIdea>

### The cost went up

Look at the Oracle cost column: 18 with the sort, 300 without it. Fewer operations, higher estimate. The reason is the clustering factor of the new index, and it is worth a short detour because it shows that cost is not a stopwatch.

<Callout kind="note" title="The clustering factor and the ROWID">Oracle keeps the clustering factor as low as it can by using the `ROWID` as a final tie-breaker in the index order. Entries with equal key values are ordered by their physical address, so the index follows the table order wherever the keys allow it. Adding `product_id` to the index inserts a new sort criterion ahead of the `ROWID`. The index has fewer ties left to break by address, so its order can only drift further from the table order; the clustering factor cannot improve, and the cost estimate rises with it. In practice the sales of one day are probably still stored close together. The scan reads the same table blocks as before, only in a different sequence and more than once, and with those blocks in cache the real cost is far below what the estimate suggests.</Callout>

## 4. Only the scanned range has to be in order

The requirement is narrower than "the index is sorted like the ORDER BY". It is enough that the part of the index the query scans is in the required order. Sort yesterday's sales by product alone, and the index still works.

```sql
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY product_id
```

Inside the range for one day every entry has the same `sale_date`, so `product_id` is the only thing that varies. Within that range the index is in product order, and that is all the `ORDER BY` asks for.

| --- | --- | --- |
| 3 days ago | 12 | |
| 3 days ago | 47 | |
| 2 days ago | 5 | |
| 2 days ago | 88 | |

| yesterday | 23 | scanned |
| yesterday | 61 | scanned |
| today | 3 | |
| today | 77 | |

<p slot="caption">The index on (sale_date, product_id). With an equality on sale_date the scanned range is one day, and inside that day the entries are in product order.</p>
</Figure>

Now widen the range by a single character.

```sql
SELECT sale_date, product_id, quantity
  FROM sales
 WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
 ORDER BY product_id
```

This is no longer yesterday's sales but every sale since yesterday. Extend the scanned range in the figure down into today and the product numbers start over at 3. The entries are in product order per day, not overall, so the database has to sort again.

<Callout kind="warning" title="Common mistake">Treating `=` and `>=` as interchangeable for the index. Both use the same index for the where clause, but only the equality leaves the scanned range in the order of the next column. Any range, `IN` list, `LIKE` or inequality on a column ahead of the sort column brings the sort back.</Callout>

## 5. Why is the sort still there?

When you expected a pipelined plan and got a sort, there are exactly two possible reasons. Either the optimizer found the plan with the sort cheaper by its cost estimate, or the index order in the scanned range does not match the `ORDER BY`.

There is a quick way to tell them apart. Rewrite the `ORDER BY` so it lists the full index definition, column for column. That removes the second reason by construction. If the sort is still in the plan, the optimizer prefers it for cost. If the sort has gone, the original `ORDER BY` did not match the index, and you have just seen what the index can deliver.

<KeyIdea title="Remember">Spell the whole index column list out as the `ORDER BY` to find out why the database sorts. Run it and look at the rows too: the index order is often not what you pictured.</KeyIdea>

When the optimizer chose the sort for its cost, it is usually because it plans for the whole result. It picks the plan that gets to the *last* row fastest, and for a large result that may well be the full scan with a sort. If the database knows that the application will only fetch the first few rows, the calculation changes and the pipelined plan wins. Telling it so is what [Unit 7](/sql/partial-results/) is about.
