outcomes:
  - Measure how three indexes change the time of a bulk insert
  - Make a delete find its rows through an index instead of a scan
  - Tell an update that moves index entries from one that does not
recap:
  - Every index adds a tree insert per row. Three indexes make a bulk insert several times slower.
  - A delete's where clause is planned like a select's. Index it the same way.
  - An update touches only the indexes that contain a changed column.

Each playground starts from a fresh copy of the schema. Timings in the browser are noisy; run each statement two or three times and compare the typical value, not the first one.

## Exercise 1: insert with zero and three indexes

The statement inserts 20,000 rows. `sales` starts with only its primary key.

## Exercise 2: a delete that uses an index

All sales of product 17 are to be removed. Without an index the select half scans the table. The count is 66 rows.

<TryIt id="8.p2" tasks={[
  { text: 'Run the count. The plan is <code>SCAN sales</code>: a delete with this where clause would read the whole table.', sql: 'count\\s*\\(\\s*\\*\\s*\\)[\\s\\S]*product_id\\s*=\\s*17', plan: '^SCAN sales' },
  { text: 'Create an index on <code>product_id</code> and run the count again. The plan becomes <code>SEARCH sales USING COVERING INDEX</code>.', sql: 'create\\s+index[\\s\\S]*\\(\\s*product_id\\s*\\)' },
  { text: 'Run <code>DELETE FROM sales WHERE product_id = 17</code>. The status line should report 66 rows affected.', sql: 'delete\\s+from\\s+sales\\s+where\\s+product_id\\s*=\\s*17' },
]} sql={`SELECT count(*)
  FROM sales
 WHERE product_id = 17;`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>CREATE INDEX sales&#95;product ON sales (product&#95;id);
SELECT count(&#42;) FROM sales WHERE product&#95;id = 17;
-- plan: SEARCH sales USING COVERING INDEX sales&#95;product (product&#95;id=?)
DELETE FROM sales WHERE product&#95;id = 17;
-- status: done · 66 rows affected</pre></div></details>
  </Fragment>
</TryIt>

## Exercise 3: unindexed versus indexed column

The playground has an index on `sale_date`. The first update changes `quantity`, which no index contains. The second changes `sale_date`, which moves an entry in `sales_date` for every row touched.

<TryIt id="8.p3" setup={`CREATE INDEX sales_date ON sales (sale_date);`} tasks={[
  { text: 'Run the update as given: 20,000 rows, no index entry moves. Note the time.', sql: 'set\\s+quantity\\s*=\\s*quantity\\s*\\+\\s*1' },
  { text: "Change the SET clause to <code>sale_date = date(sale_date, '+1 day')</code>. Every row's entry in <code>sales_date</code> is removed and re-inserted. Compare the time.", sql: "set\\s+sale_date\\s*=\\s*date\\s*\\(\\s*sale_date" },
  { text: 'Now set both columns in one statement. The time is close to the second run, not the sum: the table rewrite is shared, and only one index moves.', sql: 'set\\s+quantity[\\s\\S]*sale_date\\s*=\\s*date|set\\s+sale_date\\s*=\\s*date[\\s\\S]*quantity\\s*=' },
]} sql={`UPDATE sales
   SET quantity = quantity + 1;`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>UPDATE sales SET sale&#95;date = date(sale&#95;date, '+1 day');
UPDATE sales SET quantity = quantity + 1, sale&#95;date = date(sale&#95;date, '+1 day');</pre></div></details>
  </Fragment>
</TryIt>
