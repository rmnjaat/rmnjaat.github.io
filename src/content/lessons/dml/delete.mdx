Unlike an insert, a delete has a where clause, and that changes the picture. Finding the rows to remove is a query, and every indexing technique from [Unit 2](/sql/where-clause/) applies to it. A `DELETE` is in effect a `SELECT` with an extra step that removes the rows it identified. The select half can use indexes. The removal half has to maintain them.

## 1. Finding the rows

The where clause of a `DELETE` goes through the same optimizer as the where clause of a `SELECT` and gets the same kind of plan: an index unique scan for a delete by primary key, an index range scan for a date range when `sale_date` is indexed, a full table scan when nothing fits. Access predicates, filter predicates, column order in a concatenated index, functions on the indexed column, all of it behaves exactly as it does for a query.

```sql
DELETE FROM sales
 WHERE sale_date < '2024-02-01';
```

<Callout kind="tip">`DELETE` and `UPDATE` statements have [execution plans](/sql/explain-plan/) too. Look at them the same way you look at a select's.</Callout>

## 2. Removing the rows

Taking a row out is much like putting one in, especially for the indexes. The database removes the row's reference from each index, which means a tree traversal to the right leaf and a change to that leaf, and it keeps the trees balanced while it does so. Every index on the table is involved, not only the one that found the rows: an index that still points at a deleted row would be wrong.

The measured curve therefore looks very much like the insert curve.

<Figure n="8.3" title="Delete performance by number of indexes">

| Indexes | Execution time |
| --- | --- |
| 1 | about 0.03 s |
| 2 | about 0.05 s |
| 3 | about 0.07 s |
| 4 | about 0.09 s |
| 5 | about 0.12 s |

<p slot="caption">Read off the original chart, whose axis runs from 0 to 0.12 seconds and whose index count starts at one. The zero-index case is deliberately absent.</p>
</Figure>

Why does the chart start at one? In theory a table without indexes should be the fastest to delete from, as it is for insert. But without an index the database has to read the whole table to find the rows, so the removal would be fast and the finding very slow. The measurement leaves that case out.

<KeyIdea>The where clause decides how cheaply the rows are found. The number of indexes decides how expensive it is to remove them.</KeyIdea>

A delete without a usable index is not always wrong, though. When the delete removes a large share of the table, the full scan is the better plan for the same reason it is for a select of that share: sequential reads beat one lookup per row.

## 3. No where clause at all

A `DELETE` without a where clause is the obvious case where no index can help. It is also a case with its own command: `TRUNCATE TABLE`. It has the same effect as a delete of every row, but it removes them in one step instead of one by one, and it is very fast. Two side effects come with it. It commits implicitly, with PostgreSQL and SQL Server as the exceptions where it is transactional. And it fires no triggers.

## 4. MVCC changes the picture

Multiversion concurrency control, MVCC, is how databases let readers and writers work on the same data without blocking each other while each transaction sees a consistent state. Every engine has it in some form, but the implementations differ, and the differences can be large enough to show up in performance.

<Callout kind="note" title="PostgreSQL">PostgreSQL stores the visibility information that decides which transaction sees which row version in the table alone, never in the indexes. A delete therefore only marks the row as gone in its table block; the index entries stay where they are. How many indexes the table has makes no difference to the delete's response time. The row and its index entries are physically removed later, by `VACUUM`.</Callout>

<Callout kind="warning" title="Common mistake">Forgetting the other side of a foreign key. Deleting from a parent table makes the database check the child table for references, and with `ON DELETE CASCADE` it deletes there too. Without an index on the child's foreign key columns, that check is a full scan of the child table for every parent row removed.</Callout>
