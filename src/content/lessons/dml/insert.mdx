Everything up to here has been about queries, but SQL also changes data. `INSERT`, `DELETE` and `UPDATE` form the data manipulation language, DML, and indexes mostly make them slower. The reason is simple. An index is pure redundancy: it holds nothing that is not also in the table. Whenever the table changes, the database has to keep every copy consistent, so each write touches the table and every index that holds a copy of the affected data. This unit measures what that costs, starting with the statement that gets nothing in return.

## 1. Nothing to gain, everything to maintain

Nothing affects insert speed as much as how many indexes the table carries. More indexes, slower inserts. `INSERT` is the only statement that cannot benefit from an index directly, because it has no where clause: there is nothing to look up, only things to write.

Adding a row takes a few steps. First the database needs a place for it. In a regular heap table, which keeps its rows in no particular order, any block with enough free space will do. Finding one is quick and happens mostly in main memory. Then the row is written into that block, and as far as the table is concerned the insert is finished.

If the table has indexes, the new row must also be reachable through each of them. So the database adds an entry to every index on the table, one after the other, and each index multiplies the work once more.

## 2. What one index entry costs

An index entry is far more expensive than a heap row because the index has an order and a balance to maintain. There is exactly one [leaf node](/sql/anatomy/the-leaf-nodes/) where the entry may go, and no other. The database finds that leaf with the [tree](/sql/anatomy/the-tree/) itself, which means reading a few index blocks on the way down.

In the leaf, the database checks for free space. If there is none, it splits the leaf: it takes a fresh block and moves half of the entries across to it. The branch node above now needs a reference to the new leaf, so the split also writes the branch node, and if the branch node is full it splits as well. In the worst case every node on the path up to the root splits. That is the only event that adds a layer to the tree and makes it deeper. Press play to watch a leaf split.

<KeyIdea>An insert spends its time in the indexes, not in the table. The heap write is cheap; each index adds a tree traversal, an ordered insert into a specific leaf, and sometimes a split.</KeyIdea>

## 3. The curve

The original measurement inserted rows into the same table with zero to five indexes. With no index the bar is too small to read off the chart, well under a millisecond. A single index raises that by roughly a factor of a hundred, and each further index pushes it up again.

| Indexes | Execution time |
| --- | --- |
| 0 | below the chart's resolution |
| 1 | about 0.03 s |
| 2 | about 0.05 s |
| 3 | about 0.06 s |
| 4 | about 0.08 s |
| 5 | about 0.10 s |

</Figure>

<Callout kind="note">Going from zero to one index is the big step. After that each index adds its share, so a table that is written often should carry as few as it can.</Callout>

<Callout kind="tip">Add an index only for a query that needs it, and drop the ones another index already covers. The same discipline pays off for `DELETE` and `UPDATE`, which the next two lessons cover.</Callout>

<Callout kind="warning" title="Common mistake">Adding an index "just in case" and never checking whether a query uses it. Every such index is paid for on every insert and earns nothing back. Each database can report index usage; look before adding, and look again a few months later.</Callout>

## 4. Bulk loads

Looking at inserts alone, the best table has no indexes at all. Real tables are not like that: the data has to be read back, and that needs indexes. Even a write-only log table usually has a primary key and therefore an index.

Still, the no-index speed is so much better that it can be worth dropping all indexes before a large load and recreating them afterwards. Building an index from scratch reads the table once, sorts the keys, and writes the leaves in order, which is far cheaper than a million separate tree inserts with their splits. The condition is that no other statement needs those indexes while they are gone. Data warehouses do this routinely.

On an [index-organized table or clustered index](/sql/clustering/index-organized-clustered-index/) the table is itself a B-tree: where would the zero-index bar of Figure 8.2 go? And can you construct a situation where an `INSERT` runs faster *because* of an index, through some roundabout route?</KeyIdea>
