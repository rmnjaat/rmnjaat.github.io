The index on `last_name` from the previous lesson made the directory query fast. It also left a restriction in place: the search term has to be spelled with the same capitalisation as the stored name, or the lookup finds nothing. This group of lessons removes that restriction without giving the speed back.

## 1. The index sees a different column

A condition such as `UPPER(last_name) = 'WINAND'` does not search `last_name`. It searches the output of a function, and that output is not in the index. The database cannot reason about what `UPPER` does to the sort order, so the index on `last_name` is of no use and the table is scanned. The same happens with any function or expression wrapped around a column: a date truncated to the day, a number rounded, two columns added together.

Every database has an answer, though the answers differ in shape. Some index the expression directly. Others index a column whose value is defined by the expression. The oldest releases need a real column that a trigger or the application keeps in step.

<KeyIdea>The remedy is a **function-based index**: an index whose entries hold the result of the expression rather than the raw column. The where clause then matches what the index contains.</KeyIdea>

## 2. What each database offers

<EngineTabs>
  <Fragment slot="db2">
  Db2 for z/OS has supported indexes on expressions for a long time; Db2 for LUW only since version 10.5. User-defined functions are not allowed in an index definition on either.

  On older releases the fallback is a real column that holds the result of the expression, kept current by a trigger or by the application, whichever fits better. That column can be indexed like any other, and the where clause has to name the column instead of the expression.
  </Fragment>
  <Fragment slot="mysql">
  MySQL compares strings case-insensitively by default, and the behaviour can be set per column through its collation. Since version 5.7 an index can be built on a generated column. MySQL 8.0.13 and later can also index the expression directly, `CREATE INDEX emp_up_name ON employees ((UPPER(last_name)))`, with the extra pair of parentheses; the server implements such a functional key part as a hidden generated column.

  On older releases the fallback is a real column that holds the result of the expression, kept current by a trigger or by the application. That column can be indexed, and the where clause has to name the column instead of the expression.
  </Fragment>
  <Fragment slot="oracle">
  Function-based indexes have been available since release 8i. Release 11g added virtual columns as a second way to expose an expression.
  </Fragment>
  <Fragment slot="postgresql">
  Indexes on expressions are fully supported since release 7.4, and were partially supported from 7.2.
  </Fragment>
  <Fragment slot="sql-server">
  SQL Server has had computed columns that can be indexed since the 2000 release.
  </Fragment>
</EngineTabs>

Three lessons cover it.

[Case-Insensitive Search](/sql/where-clause/functions/case-insensitive-search/) is the classic example. An `UPPER(last_name)` search goes from a full table scan to an index lookup, and the lesson shows the index definition and the plan in each database.

[User-Defined Functions](/sql/where-clause/functions/user-defined-functions/) explains why an indexed function has to be deterministic, why that rules out anything involving the current date, and how to still use an index for an age condition.

[Over-Indexing](/sql/where-clause/functions/over-indexing/) is the caution. Each function-based index is one more B-tree to maintain, and it is easy to end up with two indexes doing the job of one.
