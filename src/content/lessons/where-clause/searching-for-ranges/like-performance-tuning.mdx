`LIKE` is a frequent source of surprises. The same statement is fast for one search term and slow for the next, because some terms can use an index and others cannot. What makes the difference is where the wildcard characters sit.

## 1. A wildcard in the middle

Start with a pattern that has the `%` wildcard in the middle of the term, against a function-based index on `UPPER(last_name)`.

```sql
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE UPPER(last_name) LIKE 'WIN%D'
```

## 2. Two predicates in one expression

Only the characters before the first wildcard can steer the tree traversal. Whatever follows the wildcard cannot narrow the scanned index range; it can only reject entries as the leaf traversal passes them. A single `LIKE` expression therefore contains two kinds of predicate at once: the part before the first wildcard is an access predicate, and the remaining characters are a filter predicate.

<Callout kind="warning" title="Collations">`LIKE` compares character by character, while some collations treat several characters as one sorting unit. Such collations can prevent `LIKE` from using an index at all. Laurenz Albe's article "Indexing LIKE in PostgreSQL and Oracle" covers the details.</Callout>

The more selective the prefix, the smaller the scanned range, and the faster the lookup. The figure shows three patterns that all find the same single row with very different amounts of work.

<p slot="caption">Eighteen entries start with WI, two start with WIN, one starts with WINA. Each pattern scans exactly the entries that match its prefix and filters the rest of the pattern on them.</p>

The first pattern has a two-character prefix, which limits the scan to 18 entries. Only one of them matches the whole pattern; the other 17 are read and thrown away. The second pattern's longer prefix narrows the scan to two entries, so only one is wasted. The third pattern has no filter predicate at all: the prefix alone selects exactly the matching entry.

<KeyIdea>The index can only use the characters in front of the first wildcard to bound the scan. Everything after it is checked entry by entry and does not shrink the range.</KeyIdea>

## 3. Leading wildcards

The opposite extreme is a pattern that begins with a wildcard. There is no prefix, so there is nothing to traverse to and the expression cannot be an access predicate. If no other condition in the where clause provides one, the database has to scan the whole table.

<Callout kind="tip">A pattern that starts with a wildcard, such as `'%TERM'`, cannot be an access predicate. Keep the wildcard out of the first position wherever you can.</Callout>

One special case has a way out. When the wildcard sits only at the front, `'%TERM'`, the pattern is a prefix search on the string read backwards. A function-based index on `REVERSE(column)` together with the condition `REVERSE(column) LIKE 'MRET%'` gives the index a prefix again. A pattern with wildcards at both ends leaves nothing to reverse.

## 4. Bind parameters and the generic plan

In theory the wildcard position decides index usage. In practice the search term usually arrives as a bind parameter, and the optimizer builds one generic plan without seeing it. It then has to guess whether most executions will have a leading wildcard or not.

Most databases assume there is no leading wildcard when they optimize a `LIKE` with a bind parameter. That assumption is wrong when the `LIKE` is really a full-text search, and there is no direct way to mark a condition as such. Separating the wildcards from the term looks like it should work, but it does not:

```sql
WHERE text_column LIKE '%' || ? || '%'
```

Writing the term into the statement as a literal is the obvious alternative, but it raises the optimization overhead and opens the door to SQL injection. A secure and portable answer is to obfuscate the condition on purpose so that the index is not considered. [Combining Columns](/sql/where-clause/obfuscation/concatenation/) shows how.

PostgreSQL once took the opposite view, assumed a leading wildcard for a parameterized `LIKE` and left the index alone, and older advice still says so. Since release 9.2 the server plans the first five executions of a prepared statement with the actual parameter values, so `LIKE $1` with `'WIN%'` gets the range scan. Only then does it consider a generic plan, which cannot assume a prefix, and it adopts that plan only if it is estimated to be no more expensive than the custom ones. Since release 12, `plan_cache_mode = force_custom_plan` keeps the value-specific plans for a statement where that matters.

Even a plan that is correctly built for a leading wildcard can be too slow. Then another part of the where clause has to provide the access path; [Index Filter Predicates Used Intentionally](/sql/clustering/index-filter-predicates/) looks at that. If there is no other access path, the database's full-text features are the way out.

## 5. Full-text search instead of LIKE

<EngineTabs>
  <Fragment slot="db2">
  Db2 Text Search adds a `CONTAINS` predicate that reads a text index instead of scanning the column: `WHERE CONTAINS(description, 'index') = 1`. The Db2 documentation describes it with the other search functions of Db2 Text Search.
  </Fragment>
  <Fragment slot="mysql">
  MySQL has a `FULLTEXT` index type, queried with `MATCH ... AGAINST`: `WHERE MATCH(description) AGAINST('index')`. InnoDB tables can carry such an index since 5.6; before that it was a MyISAM-only feature.
  </Fragment>
  <Fragment slot="oracle">
  Oracle Text provides the `CONTAINS` operator over a `CONTEXT` index: `WHERE CONTAINS(description, 'index') > 0`. The Oracle Text Application Developer's Guide covers the index types and the query syntax.
  </Fragment>
  <Fragment slot="postgresql">
  PostgreSQL's full-text search matches a `tsvector` against a `tsquery` with the `@@` operator, backed by a GIN index: `WHERE to_tsvector('english', description) @@ to_tsquery('index')`.

  If what you really need is `LIKE '%term%'` on short strings, the `pg_trgm` extension is the simpler answer. It indexes three-character fragments, and a GIN or GiST trigram index serves `LIKE` and `ILIKE` with wildcards anywhere in the pattern:

  ```sql
  CREATE EXTENSION pg_trgm;
  CREATE INDEX emp_name_trgm ON employees USING gin (last_name gin_trgm_ops);
  ```
  </Fragment>
  <Fragment slot="sql-server">
  SQL Server's full-text search uses `CONTAINS`, or `FREETEXT` for a looser match, on a full-text index: `WHERE CONTAINS(description, 'index')`. The Full-Text Search chapter of the SQL Server documentation has the setup.
  </Fragment>
  <Fragment slot="sqlite">
  The FTS5 extension provides a virtual table that answers `MATCH` queries: `SELECT * FROM docs WHERE docs MATCH 'index'`. For the prefix case note that SQLite's `LIKE` ignores case for ASCII letters, so the planner does not turn it into a range scan on a case-sensitive index. Use `GLOB`, an explicit range, or `PRAGMA case_sensitive_like = 1`, after which `LIKE 'Win%'` becomes a range scan on the plain index.
  </Fragment>
</EngineTabs>
