One of the most common indexing questions is whether to create one index per column of the where clause or a single index over all of them. In most cases the answer is short: one index with several columns, a concatenated index, as described in [Concatenated Keys](/sql/where-clause/the-equals-operator/concatenated-keys/). This page is about the cases where that is not quite enough, and about what the alternative costs.

## 1. Two independent range conditions

There are queries no single index can serve perfectly, however you define it. Two or more independent range conditions are the typical case.

```sql
SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE UPPER(last_name) < ?
   AND date_of_birth    < ?
```

No B-tree index can support this query without a filter predicate. To see why, remember that an index is a linked list. Define it as `UPPER(LAST_NAME), DATE_OF_BIRTH` and the list runs from A to Z; the date only orders employees who share a name. Define it the other way round and the list runs from the oldest employee to the youngest, with the name barely affecting the order.

However you arrange it, the entries form one chain with small values at one end and large ones at the other. That chain can serve one range condition as an access predicate, and only one. Two independent ranges would need a second axis, like the squares of a chessboard, where the query would select everything from one corner. An index is not a chessboard. It is a chain, and a chain has no corner.

<Figure n="2.8" title="A chain has one axis, a chessboard has two">

```
index (UPPER(last_name), date_of_birth)     what the query wants
------------------------------------         --------------------
ABEL     1962  <- scan starts                         date_of_birth
ABEL     1988     name < ?  ok, date < ?  no          ^
BAKER    1959     both ok                             |  . . . . .
BAKER    1991     name ok, date no                    |  x x . . .
CHEN     1960     name ok, date no  (name < 'C'?)     |  x x . . .
...                                                   +----------> name
```

<p slot="caption">The index can stop at the first name that fails the name condition. Inside that range it must read every entry and test the date, because the date order is scattered along the chain.</p>
</Figure>

## 2. Accept the filter predicate

The simplest option is to accept the filter predicate and use a multi-column index anyway. In many cases that is the best solution. The index should then start with the more selective column, so that the column with the better selectivity gets the access predicate and the other does the filtering.

This may be where the "most selective first" myth came from. The rule is right only when a filter predicate cannot be avoided; whenever every condition can be an access predicate, the operators decide the column order, as the previous pages showed.

## 3. Two indexes and the cost of combining them

The other option is two separate indexes, one per column. The database then scans both indexes and combines the intermediate results. That is more work on two counts. The lookup itself is done twice, with two tree traversals instead of one. And the merge needs a lot of memory and CPU time to match the two result sets against each other.

<KeyIdea>Two traversals and a merge always cost more than one scan of the right index.</KeyIdea>

Databases combine indexes in two ways. The first is an index join, using the join algorithms that [Chapter 4](/sql/join/) explains. The second borrows a technique from data warehousing.

## 4. Bitmap indexes

A data warehouse is the home of the ad-hoc query. A few clicks combine any conditions into a new query, and nobody can predict which columns will turn up together in the where clause. Indexing as described so far, with a tailored index per query, becomes nearly impossible.

Data warehouses use a special index type for this: the bitmap index. Its strength is that bitmap indexes can be combined cheaply, so indexing every column on its own gives acceptable performance for arbitrary combinations. If you do know the query in advance, a multi-column B-tree index made for it is still faster than combining several bitmap indexes.

The great weakness of bitmap indexes is their write scalability. Insert, update and delete performance is dreadful, and concurrent writes are practically impossible. A warehouse does not mind, because its load jobs run one after another. That rules them out for most online applications.

<Callout kind="important">Bitmap indexes do not survive concurrent writes, which rules them out for transactional (OLTP) tables.</Callout>

Many databases offer a hybrid. When no better access path exists, they run several B-tree scans and convert each result into an in-memory bitmap. Those bitmaps are combined efficiently and thrown away after the statement, so the write scalability problem of persistent bitmap indexes never arises. The price is memory and CPU time. It is, in the end, an optimizer's act of desperation, and when you see it in the plan of a frequent query, that query is asking for a better index.

  ```
  Bitmap Heap Scan on employees
    Recheck Cond: ((upper(last_name) < 'C') AND (date_of_birth < '1965-01-01'))
    ->  BitmapAnd
          ->  Bitmap Index Scan on emp_up_name
                Index Cond: (upper(last_name) < 'C')
          ->  Bitmap Index Scan on emp_dob
                Index Cond: (date_of_birth < '1965-01-01')
  ```
  Each `Bitmap Index Scan` reads one index completely for its range and builds a bitmap; `BitmapAnd` intersects them before the table is touched.
  </Fragment>

  TABLE ACCESS BY INDEX ROWID      | EMPLOYEES
    BITMAP CONVERSION TO ROWIDS    |
      BITMAP AND                   |

          INDEX RANGE SCAN         | EMP_UP_NAME
        BITMAP CONVERSION FROM ROWIDS
          INDEX RANGE SCAN         | EMP_DOB
  ```
  `BITMAP CONVERSION FROM ROWIDS` is the in-memory bitmap built from an ordinary B-tree scan. Oracle also has persistent bitmap indexes, the data warehouse kind.
  </Fragment>

  Hash Match (Inner Join)
    Index Seek (emp_up_name)  SEEK: upper_name < 'C'

  ```
  SQL Server calls it index intersection: two seeks on the same table joined by a hash match on the row locator.
  </Fragment>
  <Fragment slot="mysql">
  MySQL's Index Merge intersection only applies when every condition on a secondary index is an equality over all of its key parts; a range qualifies only on the InnoDB primary key. For the two range conditions above MySQL therefore picks one index and filters the other condition on the rows. An index on `UPPER(last_name)` would also need a functional key part, which exists only since 8.0.13. With two single-column indexes and two equalities, `subsidiary_id = 20 AND date_of_birth = '1971-01-09'`, the merge shows up:

  ```
  type: index_merge   key: emp_sub,emp_dob   Extra: Using intersect(emp_sub,emp_dob); Using where
  ```

  The `index_merge` access type with `Using intersect` means both indexes were scanned and their row sets intersected.
