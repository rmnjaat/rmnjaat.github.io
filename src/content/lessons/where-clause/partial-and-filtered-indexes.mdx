Until now every decision was about which columns go into an index. Partial indexes, as PostgreSQL calls them, or filtered indexes in SQL Server terms, add a second decision: which rows go in.

<Callout kind="warning" title="Oracle and Db2">Oracle has no where clause on `CREATE INDEX`; since 12c it can leave whole partitions out of an index, and for conditions on individual rows the [NULL group](/sql/where-clause/null/partial-index/) explains its own route, building on this lesson. Db2 (LUW) has no partial indexes either, but they can be [emulated the Oracle way](/sql/where-clause/null/partial-index/) with the `EXCLUDE NULL KEYS` feature.</Callout>

## 1. The queue query

A partial index pays off for a where clause that is used often and compares a column with a constant, like the status code here.

```sql
SELECT message
  FROM messages
 WHERE processed = 'N'
   AND receiver  = ?
```

Queuing systems run this kind of query all day: fetch the unprocessed messages for one receiver. Messages that are already processed are rarely needed, and when they are, they are usually fetched by a more specific key such as the primary key.

A two-column index makes the query fast. Since there is no range condition, the column order makes no difference for this query.

```sql
CREATE INDEX messages_todo
          ON messages (receiver, processed)
```

It does its job, but it carries a great many rows that nobody ever searches for: every message that has already been processed. Thanks to logarithmic scalability the query is still fast; the index just wastes a lot of space.

## 2. A where clause on the index

With partial indexing you restrict the index to the unprocessed messages. The syntax could hardly be simpler: a where clause on the index definition.

```sql
CREATE INDEX messages_todo
          ON messages (receiver)
       WHERE processed = 'N'
```

Only rows that satisfy the where clause get an index entry. And since every entry now has `processed = 'N'`, the `processed` column no longer needs to be in the index at all. The index shrinks in two dimensions: vertically, because it has fewer rows, and horizontally, because it has one column less.

<Figure n="2.9" title="Full index versus partial index on the messages table">

| | `(receiver, processed)` | `(receiver) WHERE processed = 'N'` |
| --- | --- | --- |
| Rows indexed | every message | unprocessed messages only |
| Columns per entry | 2 | 1 |
| Growth | with the table | with the backlog |
| Updated when a message is marked processed | yes, entry rewritten | yes, entry removed |
| Updated by writes to processed messages | yes | no |

<p slot="caption">The partial index loses one column and all the rows that are never searched for. For a queue, its size depends on the backlog, not on the history.</p>
</Figure>

<KeyIdea>For a queue, the partial index can stay the same size while the table grows without bound. It holds the unprocessed messages, not all of them.</KeyIdea>

## 3. What the index predicate may contain

There is hardly a limit on what the index predicate may contain. The one restriction it shares with every other part of an index definition is determinism: a function in the predicate must always return the same result for the same input. SQL Server is stricter and allows neither functions nor the `OR` operator in a filtered index predicate.

<EngineTabs>
  <Fragment slot="postgresql">
  ```sql
  CREATE INDEX messages_todo ON messages (receiver) WHERE processed = 'N';
  ```
  Any predicate built from deterministic (immutable) functions is allowed. The planner uses the index when it can prove the query's where clause implies the index predicate.
  </Fragment>
  <Fragment slot="sql-server">
  ```sql
  CREATE INDEX messages_todo ON messages (receiver) WHERE processed = 'N';
  ```
  Called a filtered index. The predicate is limited to simple comparisons with constants: no functions and no `OR`.
  </Fragment>
  <Fragment slot="sqlite">
  ```sql
  CREATE INDEX messages_todo ON messages (receiver) WHERE processed = 'N';
  ```
  Supported since 3.8.0. The query must contain a term identical to the index predicate, or one of the few implications SQLite recognises, for the index to be considered.
  </Fragment>
  <Fragment slot="oracle">
  No `WHERE` clause on `CREATE INDEX`. Since 12c a partitioned table can declare `INDEXING OFF` per partition, and `CREATE INDEX ... INDEXING PARTIAL` leaves those partitions out of the index. For a condition on individual rows, Oracle leaves rows out of an index when all indexed values are `NULL`, and a function-based index can exploit that; see [Emulating Partial Indexes](/sql/where-clause/null/partial-index/).
  </Fragment>
  <Fragment slot="db2">
  No partial indexes. Create the index with `EXCLUDE NULL KEYS` and index an expression that returns `NULL` for unwanted rows, the same technique as in Oracle.
  </Fragment>
</EngineTabs>

The optimizer may pick a partial index only when the query's where clause lets it prove that every wanted row is in the index. The simplest proof is the index condition repeated in the query, as the queue query does with `processed = 'N'`.

<Callout kind="warning" title="Common mistake">Leaving the index condition out of the query because "the index only has those rows anyway". The optimizer has to prove at planning time that every row the query wants is in the index. If the query does not say `processed = 'N'`, it also wants processed messages, and the partial index cannot be used.</Callout>
