Oracle does not store an index entry for a row if all of the indexed columns are NULL. In effect, every Oracle index is a [partial index](/sql/where-clause/partial-and-filtered-indexes/) with an implied where clause:

```sql
CREATE INDEX idx
    ON tbl (A, B, C, ...)
 WHERE A IS NOT NULL
    OR B IS NOT NULL
    OR C IS NOT NULL
   ...
```

## 1. A row that is not in the index

Take the `EMP_DOB` index, which has a single column, `DATE_OF_BIRTH`. A row without a birth date never enters it. This insert does not set the column, so it defaults to NULL:

```sql
INSERT INTO employees ( subsidiary_id, employee_id
                      , first_name   , last_name
                      , phone_number)
               VALUES ( ?, ?, ?, ?, ? )
```

The new row exists in the table and is absent from `EMP_DOB`. As a consequence the index cannot support a search for exactly those rows:

```sql
SELECT first_name, last_name
  FROM employees
 WHERE date_of_birth IS NULL
```

The rows the query wants are precisely the rows the index does not have. Oracle has no choice but a full table scan.

## 2. A concatenated index keeps the row

The rule says *all* indexed columns. A concatenated index gets an entry for the row as soon as one of its columns has a value:

```sql
CREATE INDEX demo_null
    ON employees (subsidiary_id, date_of_birth)
```

The row from above is in this index because its `SUBSIDIARY_ID` is not NULL. The index can therefore serve a query for the employees of one subsidiary who have no birth date:

```sql
SELECT first_name, last_name
  FROM employees
 WHERE subsidiary_id  = ?
   AND date_of_birth IS NULL
```

Note that the index covers the whole where clause: both conditions are access predicates of the `INDEX RANGE SCAN`. NULL is just one more key value inside the range for the subsidiary.

## 3. Indexing NULL like any value

The same idea rescues the original query, the one for all employees without a birth date. `DATE_OF_BIRTH` must be the leftmost column so that `IS NULL` can be an access predicate. The query itself needs no second column, but we add one anyway, chosen so that it can never be NULL, which guarantees that every row has an index entry. Any column with a `NOT NULL` constraint will do, `SUBSIDIARY_ID` for example.

A constant expression that cannot be NULL works just as well:

```sql
DROP   INDEX emp_dob
```

```sql
CREATE INDEX emp_dob ON employees (date_of_birth, 'X')
```

Strictly speaking that makes it a [function-based index](/sql/where-clause/functions/). The query does not have to mention the constant. The NULL entries of `DATE_OF_BIRTH` sit together at one end of the index, and `WHERE date_of_birth IS NULL` becomes an index range scan over exactly those entries.

<KeyIdea title="Tip">Pair the nullable column with one that never is, and NULL becomes an ordinary key.</KeyIdea>

This example also disproves the belief that Oracle cannot index NULL. It can; it just needs one indexed column that has a value. The [myth directory](/sql/myth-directory/null-cannot-be-indexed/) keeps the longer answer.

<Callout kind="warning" title="Common mistake">Picking the second column because it happens to contain no NULLs today. The optimizer decides from what it can prove, not from the data. The extra column must be declared `NOT NULL` or be a constant; the [next lesson](/sql/where-clause/null/not-null-constraint/) shows what happens otherwise.</Callout>
