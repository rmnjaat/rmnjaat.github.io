prereqs: "You should have read <a href='/sql/where-clause/searching-for-ranges/'>Searching for ranges</a>, <a href='/sql/where-clause/partial-and-filtered-indexes/'>Partial indexes</a>, <a href='/sql/where-clause/null/'>NULL in indexes</a> and <a href='/sql/where-clause/obfuscation/'>Obfuscated conditions</a>."
outcomes:
  - Replace a function on a date column with a half-open range and watch the plan flip from SCAN to SEARCH
  - See the difference between a filter predicate and an access predicate in a concatenated index with a range
  - Turn a prefix search into an index range scan, and see why a suffix search cannot be one
  - Match a partial index with the exact condition it was built on, and get it back with a redundant condition
  - Confirm that IS NULL is an ordinary index lookup in SQLite, and that = NULL is a bug rather than a slow query
recap:
  - A function on the column side hides the column from its index. Move the work to the other side; for dates that means start inclusive, end exclusive.
  - With a range condition, the equality column goes first in the index. SQLite's plan lists only access predicates, so a missing column is the filter predicate.
  - LIKE 'Win%' is a range scan in most databases. In SQLite use GLOB or an explicit range, because LIKE is case-insensitive there. A leading wildcard is a scan everywhere.
  - A partial index is used only when the query repeats the index predicate. A stricter condition can be combined with the original one to get the index back.
  - SQLite stores NULL in the index, so IS NULL is a SEARCH. WHERE col = NULL also searches, and finds nothing, because NULL equals nothing.

## 1. A month of sales

The `sales` table has an index on `sale_date` in this exercise. The query asks for June 2024 by formatting the date with `strftime`, SQLite's date function, and the plan is `SCAN sales`: 20,000 rows read to count 938. Rewrite the condition so that the column stands alone and the function disappears. The count stays 938 and the sum stays 435,416.10.

<TryIt id="1" setup={`CREATE INDEX sales_date ON sales (sale_date);`} tasks={[
  { text: 'Run the query. 938 sales worth 435,416.10, and the plan is <code>SCAN sales</code> despite the index on <code>sale_date</code>.', sql: 'strftime', plan: '^SCAN sales' },
  { text: 'Rewrite the condition as a half-open range: <code>sale_date &gt;= \'2024-06-01\' AND sale_date &lt; \'2024-07-01\'</code>. Same numbers, and the plan becomes <code>SEARCH sales USING INDEX sales_date (sale_date&gt;? AND sale_date&lt;?)</code>.', sql: "sale_date\\s*>=\\s*'2024-06-01'\\s+and\\s+sale_date\\s*<\\s*'2024-07-01'", plan: 'SEARCH sales USING INDEX sales_date \\(sale_date>\\? AND sale_date<\\?\\)' },
  { text: 'Narrow it to a single day with the same shape: from <code>\'2024-06-15\'</code> up to but not including <code>\'2024-06-16\'</code>. 31 sales, same plan.', sql: "sale_date\\s*>=\\s*'2024-06-15'\\s+and\\s+sale_date\\s*<\\s*'2024-06-16'", plan: 'SEARCH sales USING INDEX sales_date' },
]} sql={`SELECT count(*), sum(eur_value)
  FROM sales
 WHERE strftime('%Y-%m', sale_date) = '2024-06';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Hint for task 2</summary><div class="d">Every sale in June has a date on or after the first of June and before the first of July. Write those two comparisons on the bare column. The end of the range is the start of the next month, not the last day of this one.</div></details>
    <details class="hint"><summary>Hint for task 3</summary><div class="d">A day is a range too. Its end is the start of the next day. <code>date(sale_date) = '2024-06-15'</code> would find the same 31 rows with a full scan.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>-- task 1: SCAN sales

SELECT count(&#42;), sum(eur&#95;value) FROM sales
 WHERE sale&#95;date &gt;= '2024-06-15' AND sale&#95;date &lt; '2024-06-16';
-- SEARCH sales USING INDEX sales&#95;date (sale&#95;date&gt;? AND sale&#95;date&lt;?)</pre></div></details>

## 2. The range column in the wrong place

This exercise starts with an index on `(date_of_birth, subsidiary_id)`: the range column first, the equality column second. The query wants the employees of subsidiary 30 born in the seventies, 58 rows. The index is used, but read the plan closely. SQLite prints only the conditions that bound the scan, and `subsidiary_id` is not among them. The scan covers all 297 employees born in that decade and discards four out of five.

Create the same two columns in the other order and run the query again.

<TryIt id="2" setup={`CREATE INDEX emp_dob_sub ON employees (date_of_birth, subsidiary_id); ANALYZE;`} tasks={[
  { text: 'Run the query. 58 rows. The plan is <code>SEARCH employees USING INDEX emp_dob_sub (date_of_birth&gt;? AND date_of_birth&lt;?)</code>. <code>subsidiary_id</code> is in the index and absent from the plan: it is a filter predicate.', sql: 'subsidiary_id\\s*=\\s*30', plan: 'emp_dob_sub \\(date_of_birth>\\? AND date_of_birth<\\?\\)' },
  { text: 'Create an index named <code>emp_sub_dob</code> on <code>(subsidiary_id, date_of_birth)</code>.', sql: 'create\\s+index\\s+emp_sub_dob\\s+on\\s+employees\\s*\\(\\s*subsidiary_id\\s*,\\s*date_of_birth\\s*\\)' },
  { text: 'Run the query again. Same 58 rows, and the plan lists all three conditions: <code>emp_sub_dob (subsidiary_id=? AND date_of_birth&gt;? AND date_of_birth&lt;?)</code>. The scan reads 58 entries instead of 297.', sql: 'subsidiary_id\\s*=\\s*30', plan: 'emp_sub_dob \\(subsidiary_id=\\? AND date_of_birth>\\? AND date_of_birth<\\?\\)' },
]} sql={`SELECT first_name, last_name, date_of_birth
  FROM employees
 WHERE subsidiary_id = 30
   AND date_of_birth BETWEEN '1970-01-01' AND '1979-12-31';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Hint for task 1</summary><div class="d">The index is sorted by date. Within one date it is sorted by subsidiary, which is no help when the dates are all different. The traversal can start at 1970 and stop at 1980, and that is all it can do.</div></details>
    <details class="hint"><summary>Hint for task 3</summary><div class="d">The old index is still there. The optimizer picks the new one on its own, because with the equality first it can start at subsidiary 30 and 1970 and stop at subsidiary 30 and 1980.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>-- task 1
-- SEARCH employees USING INDEX emp&#95;dob&#95;sub (date&#95;of&#95;birth&gt;? AND date&#95;of&#95;birth&lt;?)
-- task 2
CREATE INDEX emp&#95;sub&#95;dob ON employees (subsidiary&#95;id, date&#95;of&#95;birth);
-- task 3
SELECT first&#95;name, last&#95;name, date&#95;of&#95;birth FROM employees
 WHERE subsidiary&#95;id = 30
   AND date&#95;of&#95;birth BETWEEN '1970-01-01' AND '1979-12-31';
-- SEARCH employees USING INDEX emp&#95;sub&#95;dob (subsidiary&#95;id=? AND date&#95;of&#95;birth&gt;? AND date&#95;of&#95;birth&lt;?)</pre></div></details>
  </Fragment>
</TryIt>

## 3. A prefix is a range, a suffix is not

This exercise has an index on `last_name`. The query looks for names starting with `Win` using `LIKE`, and the plan is `SCAN employees`. In most databases that pattern would be a range scan. SQLite's `LIKE` is case-insensitive by default, and a case-insensitive pattern cannot be mapped onto a case-sensitive index, so SQLite scans. Use `GLOB`, SQLite's case-sensitive pattern operator, or spell the range out, and the index comes back. Then try a pattern that starts with the wildcard.

<TryIt id="3" setup={`CREATE INDEX emp_last_name ON employees (last_name);`} tasks={[
  { text: 'Run the query. 66 rows, all of them Winand, and the plan is <code>SCAN employees</code>.', sql: "like\\s*'Win%'", plan: '^SCAN employees' },
  { text: 'Replace the condition with <code>last_name GLOB \'Win*\'</code>, or with <code>last_name &gt;= \'Win\' AND last_name &lt; \'Wio\'</code>. Same 66 rows, and the plan is <code>SEARCH employees USING INDEX emp_last_name (last_name&gt;? AND last_name&lt;?)</code>.', sql: "glob\\s*'Win\\*'|last_name\\s*>=\\s*'Win'\\s+and\\s+last_name\\s*<\\s*'Wio'", plan: 'SEARCH employees USING INDEX emp_last_name \\(last_name>\\? AND last_name<\\?\\)' },
  { text: 'Now find the names that end in <code>and</code>: <code>last_name GLOB \'*and\'</code>. The same 66 rows come back, and the plan is <code>SCAN employees</code> again.', sql: "glob\\s*'\\*and'|like\\s*'%and'", plan: '^SCAN employees' },
]} sql={`SELECT first_name, last_name
  FROM employees
 WHERE last_name LIKE 'Win%';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Hint for task 2</summary><div class="d">The explicit range is what the optimizer makes of a prefix pattern: every string that starts with <code>Win</code> sorts at or after <code>Win</code> and before <code>Wio</code>. <code>GLOB</code> lets SQLite derive that range itself.</div></details>
    <details class="hint"><summary>Hint for task 3</summary><div class="d">A sorted list of surnames tells you nothing about which ones end in <code>and</code>. Without a prefix there is nowhere to start the scan and nowhere to stop it.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>-- task 1: SCAN employees
-- task 2: 66 rows
SELECT first&#95;name, last&#95;name FROM employees WHERE last&#95;name GLOB 'Win&#42;';
-- or
SELECT first&#95;name, last&#95;name FROM employees
 WHERE last&#95;name &gt;= 'Win' AND last&#95;name &lt; 'Wio';
-- SEARCH employees USING INDEX emp&#95;last&#95;name (last&#95;name&gt;? AND last&#95;name&lt;?)
-- task 3: 66 rows
SELECT first&#95;name, last&#95;name FROM employees WHERE last&#95;name GLOB '&#42;and';
-- SCAN employees</pre></div></details>
  </Fragment>
</TryIt>

<Callout kind="note" title="Outside SQLite">PostgreSQL, MySQL, Oracle, SQL Server and Db2 all turn <code>LIKE 'Win%'</code> into a range scan on an ordinary index, with the caveat that PostgreSQL needs the <code>C</code> collation or <code>text_pattern_ops</code>. The leading-wildcard result is the same everywhere: a scan of the index or the table, and a full-text index if the search matters.</Callout>

## 4. The partial index has to be asked for

The `sales` table has a partial index for this exercise: `sales_big_by_date` on `sale_date`, restricted to `WHERE eur_value > 800`. It holds 2,439 entries instead of 20,000. The query repeats that condition word for word and adds a date range, and the plan uses the index. Then make the condition stricter and watch SQLite give up on it, because it cannot prove that a sale above 850 is in an index built for sales above 800. Finally get the index back without changing the result.

<TryIt id="4" setup={`CREATE INDEX sales_big_by_date ON sales (sale_date) WHERE eur_value > 800; ANALYZE;`} tasks={[
  { text: 'Run the query. 122 rows, and the plan is <code>SEARCH sales USING INDEX sales_big_by_date (sale_date&gt;? AND sale_date&lt;?)</code>. The <code>eur_value</code> condition is not in the plan because the index already guarantees it.', sql: 'eur_value\\s*>\\s*800', plan: 'sales_big_by_date \\(sale_date>\\? AND sale_date<\\?\\)' },
  { text: 'Change <code>800</code> to <code>850</code>. 65 rows, a subset of the same sales, and the plan is <code>SCAN sales</code>.', sql: 'eur_value\\s*>\\s*850', plan: '^SCAN sales' },
  { text: 'Keep <code>eur_value &gt; 850</code> and add <code>AND eur_value &gt; 800</code> next to it. The second condition changes nothing about the result and brings the index back: 65 rows through <code>sales_big_by_date</code>.', sql: 'eur_value\\s*>\\s*850\\s+and\\s+eur_value\\s*>\\s*800|eur_value\\s*>\\s*800\\s+and\\s+eur_value\\s*>\\s*850', plan: 'SEARCH sales USING INDEX sales_big_by_date' },
]} sql={`SELECT sale_id, employee_id, eur_value
  FROM sales
 WHERE eur_value > 800
   AND sale_date >= '2024-06-01'
   AND sale_date <  '2024-07-01';`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Hint for task 2</summary><div class="d">SQLite needs a term of the where clause that is identical to the index predicate, or one of the few implications it knows, such as <code>x = ?</code> for <code>x IS NOT NULL</code>. <code>eur_value &gt; 850</code> is logically covered by <code>eur_value &gt; 800</code>, but that is not one of them.</div></details>
    <details class="hint"><summary>Hint for task 3</summary><div class="d">Give the planner the term it is looking for. <code>eur_value &gt; 800</code> is implied by <code>eur_value &gt; 850</code>, so adding it is free for correctness, and it is the exact text stored with the index.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>-- task 1: 122 rows
-- SEARCH sales USING INDEX sales&#95;big&#95;by&#95;date (sale&#95;date&gt;? AND sale&#95;date&lt;?)
-- task 2: 65 rows
SELECT sale&#95;id, employee&#95;id, eur&#95;value FROM sales
 WHERE eur&#95;value &gt; 850
   AND sale&#95;date &gt;= '2024-06-01' AND sale&#95;date &lt; '2024-07-01';
-- SCAN sales
-- task 3: 65 rows
SELECT sale&#95;id, employee&#95;id, eur&#95;value FROM sales
 WHERE eur&#95;value &gt; 850 AND eur&#95;value &gt; 800
   AND sale&#95;date &gt;= '2024-06-01' AND sale&#95;date &lt; '2024-07-01';
-- SEARCH sales USING INDEX sales&#95;big&#95;by&#95;date (sale&#95;date&gt;? AND sale&#95;date&lt;?)</pre></div></details>
  </Fragment>
</TryIt>

The index definition is stored with the catalog entry. `SELECT sql FROM sqlite_master WHERE name = 'sales_big_by_date'` shows the `WHERE eur_value > 800` that the query has to match.

## 5. NULL in the index

For this exercise the setup adds a nullable `manager_id` column to `employees`, fills it for most rows and leaves it empty for every twenty-fifth employee, 40 rows in all, then indexes it. SQLite stores NULL in the index like any other key, so the `IS NULL` query is a `SEARCH`. Compare it with an equality on a real value, and then with the comparison people write by mistake.

<TryIt id="5" setup={`ALTER TABLE employees ADD COLUMN manager_id INTEGER;
UPDATE employees SET manager_id = employee_id % 25 WHERE employee_id % 25 <> 0;
CREATE INDEX emp_manager ON employees (manager_id);`} tasks={[
  { text: 'Run the query. 40 rows, and the plan is <code>SEARCH employees USING INDEX emp_manager (manager_id=?)</code>: to SQLite, <code>IS NULL</code> is a lookup for one more key value.', sql: 'manager_id\\s+is\\s+null', plan: 'emp_manager \\(manager_id=\\?\\)' },
  { text: 'Change the condition to <code>manager_id = 7</code>. Also 40 rows, and the plan line is identical.', sql: 'manager_id\\s*=\\s*7', plan: 'emp_manager \\(manager_id=\\?\\)' },
  { text: 'Now write <code>manager_id = NULL</code>. The plan still says <code>SEARCH</code>, and the result is empty. Nothing is equal to NULL, not even NULL.', sql: 'manager_id\\s*=\\s*null', plan: 'emp_manager' },
]} sql={`SELECT employee_id, first_name, last_name
  FROM employees
 WHERE manager_id IS NULL;`}>
  <Fragment slot="hints">
    <details class="hint"><summary>Hint for task 3</summary><div class="d">The comparison <code>x = NULL</code> is neither true nor false for any <code>x</code>, so no row passes the where clause. The index is consulted and finds nothing. This is a correctness bug that happens to be fast.</div></details>
    <details class="hint"><summary>Show solution</summary><div class="d"><pre>-- task 1: 40 rows
SELECT employee&#95;id, first&#95;name, last&#95;name FROM employees WHERE manager&#95;id IS NULL;
-- SEARCH employees USING INDEX emp&#95;manager (manager&#95;id=?)
-- task 2: 40 rows
SELECT employee&#95;id, first&#95;name, last&#95;name FROM employees WHERE manager&#95;id = 7;
-- SEARCH employees USING INDEX emp&#95;manager (manager&#95;id=?)
-- task 3: 0 rows
SELECT employee&#95;id, first&#95;name, last&#95;name FROM employees WHERE manager&#95;id = NULL;
-- SEARCH employees USING INDEX emp&#95;manager (manager&#95;id=?)</pre></div></details>
  </Fragment>
</TryIt>

<Callout kind="important" title="The same query in Oracle">Oracle writes no index entry for a row whose indexed columns are all NULL, so the single-column index above would not serve <code>IS NULL</code> there, and the plan would be a full table scan. An index on <code>(manager_id, subsidiary_id)</code>, with the <code>NOT NULL</code> column second, puts every row into the index and makes the lookup possible.</Callout>
