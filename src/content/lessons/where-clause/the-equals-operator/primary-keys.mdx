The simplest where clause is also the most common one: fetch one row by its primary key. It is the right place to learn how to check whether an index is used at all, because here the answer is easy to read and the mechanism is easy to picture.

## 1. The table and its automatic index

Every example in this unit uses the `employees` table. At this point in the story its primary key is `employee_id` alone.

```sql
CREATE TABLE employees (
   employee_id   NUMBER        NOT NULL,
   first_name    VARCHAR(1000) NOT NULL,
   last_name     VARCHAR(1000) NOT NULL,
   date_of_birth DATE          NOT NULL,
   phone_number  VARCHAR(1000) NOT NULL,
   CONSTRAINT employees_pk PRIMARY KEY (employee_id)
)
```

There is no `CREATE INDEX` statement here, and there does not need to be one. The database cannot enforce uniqueness without a fast way to check whether a value already exists, and a B-tree is exactly that. So it builds an index on `employee_id` the moment the constraint is declared.

<Callout kind="tip">The [example schema](/sql/example-schema/) has scripts that create and fill the table so you can repeat every example on your own database. For reading along it is enough to know that the table holds 1,000 rows.</Callout>

## 2. One tree traversal, no leaf chain

The query looks up one employee's name.

```sql
SELECT first_name, last_name
  FROM employees
 WHERE employee_id = 123
```

Because `employee_id` is the primary key, this condition can match one row at most. That changes what the index has to do. The tree traversal from unit 1 lands on the leaf node that would hold 123, and either the entry is there or it is not. There is no reason to follow the leaf chain to the next node, because a second entry for 123 cannot exist. Step through the lookup in the figure.

This is the operation that makes full use of the logarithmic scalability of the tree. Three or four node reads find the entry, and that number is almost independent of how large the table is.

## 3. Reading the execution plan

Believing that a query uses an index is not the same as knowing it. The evidence is the **execution plan**, the database's own description of the steps it takes to run a statement. Here is the plan for the query above in each database.

<EngineTabs>
  <Fragment slot="db2">
  The plan was taken from the `last_explained` view described in the [Db2 reference](/sql/explain-plan/db2/).

  ```
  Explain Plan
  -------------------------------------------------------
  ID | Operation             |                Rows | Cost
   1 | RETURN                |                     |   13
   2 |  FETCH EMPLOYEES      |    1 of 1 (100.00%) |   13
   3 |   IXSCAN EMPLOYEES_PK | 1 of 1000 (   .10%) |    6

  Predicate Information
   3 - START (Q1.EMPLOYEE_ID = +00123.)
        STOP (Q1.EMPLOYEE_ID = +00123.)
  ```

  `IXSCAN` stands for both of Oracle's `INDEX UNIQUE SCAN` and `INDEX RANGE SCAN`; the plan alone does not say which one it is. `FETCH` is the table access, the counterpart of `TABLE ACCESS BY INDEX ROWID`. The start and stop keys show the condition the index resolved.
  </Fragment>
  <Fragment slot="mysql">
  ```
  +----+-----------+-------+---------+---------+------+-------+
  | id | table     | type  | key     | key_len | rows | Extra |
  +----+-----------+-------+---------+---------+------+-------+
  |  1 | employees | const | PRIMARY | 5       |    1 |       |
  +----+-----------+-------+---------+---------+------+-------+
  ```

  The access type `const` is MySQL's name for a unique lookup, the counterpart of Oracle's `INDEX UNIQUE SCAN`. `key` names the index that was used.
  </Fragment>
  <Fragment slot="oracle">
  ```
  ---------------------------------------------------------------
  |Id |Operation                   | Name         | Rows | Cost |
  ---------------------------------------------------------------
  | 0 |SELECT STATEMENT            |              |    1 |    2 |
  | 1 | TABLE ACCESS BY INDEX ROWID| EMPLOYEES    |    1 |    2 |
  |*2 |  INDEX UNIQUE SCAN         | EMPLOYEES_PK |    1 |    1 |
  ---------------------------------------------------------------

  Predicate Information (identified by operation id):
  ---------------------------------------------------
     2 - access("EMPLOYEE_ID"=123)
  ```

  Read it from the innermost operation outwards. `INDEX UNIQUE SCAN` is the tree traversal and nothing more. `TABLE ACCESS BY INDEX ROWID` fetches the row. The predicate section records that the condition was used to `access` the index rather than to filter rows afterwards.
  </Fragment>
  <Fragment slot="postgresql">
  ```
                  QUERY PLAN
  -------------------------------------------
   Index Scan using employees_pk on employees
     (cost=0.00..8.27 rows=1 width=14)
     Index Cond: (employee_id = 123::numeric)
  ```

  A PostgreSQL `Index Scan` is one operation that covers both of Oracle's steps, the index access and the table access. The plan does not say whether the index lookup could return more than one row; `rows=1` is only the planner's estimate.
  </Fragment>
  <Fragment slot="sql-server">
  ```
  |--Nested Loops(Inner Join)
     |--Index Seek(OBJECT:employees_pk,
     |               SEEK:employees.employee_id=@1
     |            ORDERED FORWARD)
     |--RID Lookup(OBJECT:employees,
                     SEEK:Bmk1000=Bmk1000
                   LOOKUP ORDERED FORWARD)
  ```

  `Index Seek` corresponds to Oracle's `INDEX RANGE SCAN` and `RID Lookup` to `TABLE ACCESS BY INDEX ROWID`. Unlike Oracle, SQL Server shows the `Nested Loops` join that feeds each ROWID from the seek into the lookup as an operation of its own. The `RID Lookup` appears because the book's test table is a heap; with the default clustered primary key the whole lookup is one `Clustered Index Seek`, as [Slow Indexes, Part I](/sql/anatomy/slow-indexes/) showed.
  </Fragment>
</EngineTabs>

Whatever the vocabulary, look for the same two things: the name of the index, and the condition attached to the index operation. If the condition hangs off the index step, the index did the work.

<Callout kind="tip">The execution plan goes by other names too: explain plan, query plan. The [execution plans reference](/sql/explain-plan/) explains how to obtain and read one in each database.</Callout>

## 4. The table access that cannot hurt

The index entry carries a ROWID, not the name. So after the index step there is one more: the `TABLE ACCESS BY INDEX ROWID` operation reads the row and copies out `first_name` and `last_name`. [Slow Indexes, Part I](/sql/anatomy/slow-indexes/) showed that this step is where index lookups go wrong, because every matching entry costs one more table read.

An `INDEX UNIQUE SCAN` cannot run into that problem. It delivers at most one entry, so it can trigger at most one table access. Neither a wide range scan nor a long series of row fetches is possible here.

<KeyIdea>A unique scan has none of the ingredients of a slow index. It reads one path through the tree and one row from the table, and that is all it can ever read.</KeyIdea>

## 5. Primary keys without a unique index

A primary key does not strictly require a unique index. The constraint can be enforced on top of a non-unique index, and in that case Oracle reports an `INDEX RANGE SCAN` instead of a unique scan. The lookup still delivers at most one entry, because the constraint keeps the key values distinct; only the operation name changes.

The usual reason for such a setup is a **deferrable constraint**. A regular constraint is checked while the statement runs. A deferrable one is checked when the transaction commits, which is what makes it possible to insert rows into tables that reference each other in a circle.
