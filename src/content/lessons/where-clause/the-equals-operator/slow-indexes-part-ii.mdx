The previous lesson reversed the column order of the primary key index and checked two statements against it. But an index belongs to the table, not to a query, and changing it can affect every statement that touches that table. This lesson shows how a database picks an index when it has a choice, and what happens when a well-meant change gives it a bad one.

## 1. An index change touches every query

The reversed `EMPLOYEES_PK` helps every query that searches by subsidiary alone. It is also usable by every query that searches by `subsidiary_id` together with anything else, because `subsidiary_id` is now the leading column. That includes queries that used to be served by a different index on a different part of their where clause, or by no index at all. When several access paths are available, choosing between them is the optimizer's job.

<Callout kind="note" title="The query optimizer">The optimizer, or query planner, is the component that turns an SQL statement into an execution plan. The process is also called compiling or parsing. A **cost-based optimizer** (CBO) generates many candidate plans, assigns each a cost derived from the operations involved and the estimated row counts, and picks the plan with the lowest cost. A **rule-based optimizer** (RBO) applies a fixed set of rules instead. Hardly any current database still ships a rule-based optimizer.</Callout>

## 2. The telephone directory query

The side effect in our story: since the merger, the company's internal phone directory has become slow. The first analysis points at this query.

```sql
SELECT first_name, last_name, subsidiary_id, phone_number
  FROM employees
 WHERE last_name  = 'WINAND'
   AND subsidiary_id = 30
```

Its plan, the one the book calls Example 2.1:

```
---------------------------------------------------------------
|Id |Operation                   | Name         | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT            |              |    1 |   30 |
|*1 | TABLE ACCESS BY INDEX ROWID| EMPLOYEES    |    1 |   30 |
|*2 |  INDEX RANGE SCAN          | EMPLOYEES_PK |   40 |    2 |
---------------------------------------------------------------

Predicate Information (identified by operation id):
  1 - filter("LAST_NAME"='WINAND')
  2 - access("SUBSIDIARY_ID"=30)
```

An index is used and the total cost is 30. Nothing looks wrong. What is suspicious is which index: the one we just changed. Before the change it began with `employee_id`, a column this query does not mention, so the query could not have used it. The index change is the prime suspect.

## 3. Comparing with the old plan

To compare, we want the plan from before the change. We could restore the old index definition, but most databases have a cheaper way to keep the optimizer away from one index for one query. In Oracle it is a hint:

```sql
SELECT /*+ NO_INDEX(EMPLOYEES EMPLOYEES_PK) */
       first_name, last_name, subsidiary_id, phone_number
  FROM employees
 WHERE last_name  = 'WINAND'
   AND subsidiary_id = 30
```

The plan that was presumably in use before used no index at all.

```
----------------------------------------------------
| Id | Operation         | Name      | Rows | Cost |
----------------------------------------------------
|  0 | SELECT STATEMENT  |           |    1 |  477 |
|* 1 |  TABLE ACCESS FULL| EMPLOYEES |    1 |  477 |
----------------------------------------------------

Predicate Information (identified by operation id):
   1 - filter("LAST_NAME"='WINAND' AND "SUBSIDIARY_ID"=30)
```

A full table scan reads and tests every row, and yet in this case it is faster than the indexed plan. That is odd. The query returns a single row, and finding a single row is exactly what an index is supposed to do better than a scan. Here the index seems to be slow.

## 4. Step by step through the plan

When a plan surprises you, walk through its operations one at a time. The first step in Example 2.1 is the `INDEX RANGE SCAN` on `EMPLOYEES_PK`. That index does not contain `last_name`, so the scan can only apply the `subsidiary_id` condition. Oracle says so in the predicate section: operation 2 has `access("SUBSIDIARY_ID"=30)` and nothing else.

<Callout kind="tip">The [execution plans reference](/sql/explain-plan/) shows where the other databases print their predicate information.</Callout>

So the range scan traverses the tree to the first entry for subsidiary 30 and then follows the leaf chain through every entry for that subsidiary. Its output is a list of ROWIDs that satisfy the `subsidiary_id` condition. Depending on the subsidiary that is a handful, or many hundreds.

The second step, `TABLE ACCESS BY INDEX ROWID`, takes each ROWID and fetches the row with all its columns from the table. Only now is `last_name` available, so only now can the rest of the where clause be checked: the `filter("LAST_NAME"='WINAND')` on operation 1. Every row of subsidiary 30 has to be fetched before the name condition can throw it away.

<IndexAccess client:visible n="2.3" leaves={4} rows={8} />

<KeyIdea>The response time does not depend on the size of the result. It depends on the number of employees in the subsidiary, because every one of them is read from the table.</KeyIdea>

For a small subsidiary the range scan is the better plan. For a huge one the full table scan wins, because it reads the table in large chunks instead of one row at a time (see the [full table scan note](/sql/where-clause/the-equals-operator/concatenated-keys/) in the previous lesson). In our story the range scan returns one ROWID for every employee of the original company, and each of those rows is fetched individually. That is both ingredients of a slow index at once: a wide index range, and many single-row table accesses.

## 5. Statistics and the estimate

Which plan is best depends on the data, so the optimizer keeps **statistics** about the contents of the database. Here a histogram of how employees are spread over subsidiaries lets it estimate how many ROWIDs the range scan will return, and that estimate feeds the cost.

<Callout kind="note" title="Statistics">A cost-based optimizer uses statistics on tables, columns and indexes. Most are kept per column: the number of distinct values, the smallest and largest value, the number of NULLs, and the histogram of the value distribution. The most important table statistic is its size in rows and blocks. For an index it is the tree depth, the number of leaf nodes, the number of distinct keys and the clustering factor, which [unit 5](/sql/clustering/) explains. From these the optimizer estimates how selective each predicate is.</Callout>

When statistics are missing, for example because they were deleted, the optimizer falls back on defaults. Oracle's defaults assume a small index of medium selectivity, which is where the estimate of 40 rows for the range scan in Example 2.1 came from. In reality the subsidiary has 1,000 employees. The estimate is off by a factor of 25.

With correct statistics the optimizer expects 1,000 rows from the index and prices the table access accordingly:

```
---------------------------------------------------------------
|Id |Operation                   | Name         | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT            |              |    1 |  680 |
|*1 | TABLE ACCESS BY INDEX ROWID| EMPLOYEES    |    1 |  680 |
|*2 |  INDEX RANGE SCAN          | EMPLOYEES_PK | 1000 |    4 |
---------------------------------------------------------------

Predicate Information (identified by operation id):
  1 - filter("LAST_NAME"='WINAND')
  2 - access("SUBSIDIARY_ID"=30)
```

A cost of 680 is higher than the 477 of the full table scan, so with good statistics the optimizer chooses the scan on its own. The slow plan was a statistics problem as much as an index problem.

<Callout kind="warning" title="Common mistake">Reading "cost 30" as "fast". A cost is an estimate built on statistics. When the statistics are defaults or stale, the number describes a table that does not exist.</Callout>

## 6. The proper index

None of this means the full table scan is the answer. The query searches by name, and a search by name is best served by an index on the name.

```sql
CREATE INDEX emp_name ON employees (last_name)
```

With it the optimizer arrives at a cost of 3, the book's Example 2.2:

```
--------------------------------------------------------------
| Id | Operation                   | Name      | Rows | Cost |
--------------------------------------------------------------
|  0 | SELECT STATEMENT            |           |    1 |    3 |
|* 1 |  TABLE ACCESS BY INDEX ROWID| EMPLOYEES |    1 |    3 |
|* 2 |   INDEX RANGE SCAN          | EMP_NAME  |    1 |    1 |
--------------------------------------------------------------

Predicate Information (identified by operation id):
   1 - filter("SUBSIDIARY_ID"=30)
   2 - access("LAST_NAME"='WINAND')
```

The index scan is expected to deliver one row, so the database fetches one row, which is far cheaper than scanning the table. The `subsidiary_id` condition has become the filter now, but a filter applied to one row costs nothing. A properly chosen index beats the original full scan as well.

Put Example 2.1 and Example 2.2 side by side. Same operations, similar cost figures, and yet the second plan is dramatically faster. The efficiency of an `INDEX RANGE SCAN` spans a huge range, especially when a table access follows it.

<KeyIdea title="Remember">Using an index does not mean a statement runs the best way it could. It only means an index was used.</KeyIdea>
