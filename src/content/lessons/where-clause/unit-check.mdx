<Check
  client:visible
  question="A query looks up one row by its full primary key. The plan shows an index unique scan followed by a table access by ROWID. Which of the two slow-index ingredients from Unit 1 is involved?"
  options={[
    'Following the leaf chain, because the index has to be read until the key is found.',
    'Table access per entry, because every index hit costs a block read.',
    'Neither. A unique scan stops at the first entry, and there is exactly one row to fetch.',
  ]}
  answer={2}
  explain="A unique index holds at most one entry per key, so the traversal ends in the leaf it lands on; no neighbouring leaves are read. That one entry leads to one table block. The cost is the tree depth plus one, and it stays that way when the table grows a thousandfold. The leaf chain matters for range scans, and per-entry table access matters when a range returns many entries. A primary key lookup has neither."
/>

<Check
  client:visible
  question="After the merger the primary key of employees is (employee_id, subsidiary_id). Which of these where clauses cannot use the primary key index?"
  options={[
    'WHERE employee_id = ?',
    'WHERE subsidiary_id = ?',
    'WHERE employee_id = ? AND subsidiary_id = ?',
  ]}
  answer={1}
  explain="The index is sorted by employee_id first, so every query that supplies employee_id has a place to start: the full key and the employee_id prefix both work. The entries for one subsidiary are spread across the whole index, one under each employee_id, so subsidiary_id alone gives the traversal nothing to steer by and the optimizer reads the table. Defining the key as (subsidiary_id, employee_id) would serve all three."
/>

<Check
  client:visible
  question="There is an index on (subsidiary_id). The plan for WHERE subsidiary_id = 20 AND last_name = 'Winand' shows an index range scan with subsidiary_id as access predicate and last_name as a filter on the table access. What does the database read to return the Winands?"
  options={[
    'Only the index entries and table rows of the Winands, because the index was used.',
    'Every index entry and every table row of subsidiary 20, then it throws away all but the Winands.',
    'The whole index, because a filter predicate disables the tree traversal.',
  ]}
  answer={1}
  explain="The access predicate bounds the scan to subsidiary 20, which is correct and cheap for the traversal. But the index knows nothing about last_name, so each of the 500 entries in that range is read and each of the 500 rows is fetched before the filter can reject it, to keep 33. The plan says the index was used, and it was; it just resolved half the where clause. The whole index is not read, because the traversal still works. An index on (subsidiary_id, last_name) makes both conditions access predicates."
/>

<Check
  client:visible
  question="employees has an index on last_name. The query WHERE UPPER(last_name) = UPPER(?) does a full table scan. Why?"
  options={[
    'UPPER on the parameter side forces a conversion of every row.',
    'The index holds the stored names, and the optimizer cannot map UPPER(last_name) onto that order. It treats the function as a black box.',
    'Any function anywhere in a where clause switches off every index on the table.',
  ]}
  answer={1}
  explain="The problem is UPPER(last_name) on the column side. The index is sorted by the values as written, and the database does not know how the output of UPPER relates to that order, so it cannot traverse the tree for 'WINAND'. UPPER(?) on the other side is harmless: it has no column in it, is evaluated once, and behaves like a constant. The fix is an index on UPPER(last_name), spelled exactly as the query spells it; an index on LOWER(last_name) would not help this query."
/>

<Check
  client:visible
  question="Bind parameters are the default. In which of these cases is a literal in the SQL text the better choice?"
  options={[
    'A search term typed by a user into a name field.',
    'A status column with three possible values of very different frequency, where the best plan differs by value.',
    'An employee_id looked up on every page view.',
  ]}
  answer={1}
  explain="A literal lets the optimizer read the histogram for that value and choose between an index scan and a full scan accordingly. That only pays when the column has a few values, the distribution is skewed, and the right plan actually changes from value to value; three status values produce three cached plans, which is fine. User input must always be bound, because a literal built from it is an injection hole. An employee_id has thousands of distinct values; literals there would flood the plan cache with near-identical plans and gain nothing, since every value matches one row."
/>

<Check
  client:visible
  question="A screen runs WHERE subsidiary_id = ? AND last_name LIKE 'Win%'. Which index serves it with the narrowest scan?"
  options={[
    '(last_name, subsidiary_id), because the name prefix is more selective than the subsidiary.',
    '(subsidiary_id, last_name): the equality column first, the range condition last.',
    'Two single-column indexes, on subsidiary_id and on last_name, which the optimizer combines.',
  ]}
  answer={1}
  explain="LIKE 'Win%' is a range condition: the characters before the wildcard give the scan a start and an end. With subsidiary_id first, the scan starts at that subsidiary's first Win and stops at its last; every entry read is a hit. With last_name first the scan covers every Win in every subsidiary and filters on subsidiary_id. Selectivity does not change this; the operators decide the order. Combining two single-column indexes means two complete range scans and an intersection, which costs more than one concatenated index for a query this predictable."
/>

<Check
  client:visible
  question="A PostgreSQL partial index WHERE status = 'open' and an Oracle function-based index on CASE WHEN status = 'open' THEN sale_id END solve the same problem. What do they have in common?"
  options={[
    'Both store an entry for every row, so neither is smaller than a full index.',
    'Both leave the unwanted rows out of the index, and both need the query to state a condition the optimizer can match against the index definition.',
    'Both work only with bind parameters, because the status value must not appear in the SQL text.',
  ]}
  answer={1}
  explain="A partial index keeps only the rows that satisfy its where clause. Oracle writes no entry when the indexed expression is NULL, so a CASE that yields NULL for closed rows leaves them out too; both indexes are as small as the subset. In both cases the optimizer must prove at planning time that the query wants only indexed rows: a literal status = 'open' for the partial index, the identical CASE expression for Oracle. A generic plan built without the value can use neither index; PostgreSQL's custom plans and Oracle's bind peeking help only while the value is visible at the moment the plan is built."
/>

<Check
  client:visible
  question="A search statement reads WHERE (:sub IS NULL OR subsidiary_id = :sub) AND (:name IS NULL OR last_name = :name). There is an index on (subsidiary_id, last_name), and the plan is a full table scan even when both values are supplied. What is the right fix?"
  options={[
    'Put the values into the SQL text as literals so that the optimizer can see them.',
    'Build the where clause from the conditions that are actually supplied, and keep bind parameters for the values.',
    'Add a second index on (last_name, subsidiary_id) so that either column can lead.',
  ]}
  answer={1}
  explain="The plan is built once and reused for every execution, so it has to be correct when both parameters are NULL and every row qualifies. Only a full scan can do that, and the same plan then serves the selective searches. Generating the statement from the supplied filters gives each combination its own statement and its own plan, with the index used whenever a condition is present, and the values stay bound. Literals would let the optimizer see the values but flood the plan cache and open the door to injection. A second index changes nothing, because the OR-NULL shape cannot use any index."
/>
