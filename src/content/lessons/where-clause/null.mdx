NULL causes confusion wherever SQL is used. The basic idea is simple enough: NULL stands for data that is missing. The details are not. You have to write `IS NULL` instead of `= NULL`, for one thing. Oracle then adds two peculiarities of its own, one because it does not always follow the standard, and one because of how it handles NULL in indexes.

## 1. Not a value

In the SQL standard, NULL is not a value at all. It is a marker that stands in for a value that is missing or unknown, from which it follows that no actual value can be NULL. Oracle breaks that rule for the empty string:

```sql
SELECT     '0 IS NULL???' AS "what is NULL?" FROM dual
 WHERE      0 IS NULL
UNION ALL
SELECT    '0 is not null' FROM dual
 WHERE     0 IS NOT NULL
UNION ALL
SELECT ''''' IS NULL???'  FROM dual
 WHERE    '' IS NULL
UNION ALL
SELECT ''''' is not null' FROM dual
 WHERE    '' IS NOT NULL
```

Zero is not null, as expected. The empty string, however, is.

## 2. And sometimes the other way round

To make it worse, there is a case where Oracle treats NULL like an empty string:

```sql
SELECT dummy
     , dummy || ''
     , dummy || NULL
  FROM dual
```

Concatenating the `DUMMY` column, which always holds `'X'`, with NULL should give NULL. Oracle returns `'X'`.

Every programming language that has both keeps the empty string and null apart. Oracle does not: a `VARCHAR2` column cannot hold an empty string, and whatever you insert as `''` comes back as NULL. This is not only odd, it is dangerous. And the oddities do not end here; they carry on into indexing.

<KeyIdea>In Oracle, NULL is not a value, and the empty string is NULL.</KeyIdea>

<Callout kind="note" title="Elsewhere">PostgreSQL, SQL Server, MySQL, Db2 and SQLite keep NULL and the empty string apart, and they store NULL in B-tree indexes like any other key. The next three pages are about Oracle, with the other databases as contrast.</Callout>
