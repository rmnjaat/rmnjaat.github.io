An index can only be searched by the values it stores. A condition that compares something derived from the column, rather than the column itself, asks a question the index cannot answer. The [functions](/sql/where-clause/functions/) group showed the obvious form, `UPPER(last_name) = ?`. The forms in this group are harder to spot.

## 1. What obfuscation means here

An obfuscated condition is one that hides the indexed column from the optimizer, so the index that should serve the query is never considered. Nobody writes one on purpose, apart from the two deliberate cases this group covers, in [Combining Columns](/sql/where-clause/obfuscation/concatenation/) and [Math](/sql/where-clause/obfuscation/math/). They happen because the derived value looks like the column, because the database inserted a conversion silently, or because a piece of logic seemed clever. The lessons that follow are a catalogue of anti-patterns every developer should know and avoid.

<KeyIdea>If the column does not stand on its own in the condition, the index on it is not used.</KeyIdea>

## 2. The five patterns

[Date Types](/sql/where-clause/obfuscation/dates/): pay special attention to `DATE` types. Functions that strip a time or format a date hide the column; a range condition does not.

[Numeric Strings](/sql/where-clause/obfuscation/numeric-strings/): do not mix types. A number compared with a text column makes the database convert the column, not the number.

[Combining Columns](/sql/where-clause/obfuscation/concatenation/): use redundant where clauses. A range over a combination of columns needs an extra condition on the leading column to get an access predicate.

[Smart Logic](/sql/where-clause/obfuscation/smart-logic/): the smartest way to make SQL slow. One statement with `OR :param IS NULL` for every optional filter gets a full table scan for all of them.

[Math](/sql/where-clause/obfuscation/math/): databases do not solve equations. Arithmetic on the column side of a comparison has to be moved or indexed.
