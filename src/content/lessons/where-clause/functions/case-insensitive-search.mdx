Ignoring case in a comparison is easy to write. Convert both sides to the same case and compare the results.

```sql
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE UPPER(last_name) = UPPER('winand')
```

Whatever capitalisation the user typed and whatever is stored in `last_name`, the two `UPPER` calls make them agree. The logic is sound. The execution plan is not.

<Callout kind="note">Case-insensitive matching can also come from a **collation**. The default collations of SQL Server and MySQL do not distinguish upper from lower case, so on those databases a plain `=` already ignores case.</Callout>

The index on `last_name` exists and is ignored. It is unusable because the query does not search `last_name`; it searches `UPPER(last_name)`, and from the database's point of view that is a different thing altogether.

## 2. The optimizer sees a black box

This is an easy trap to fall into. We see the connection between `last_name` and `UPPER(last_name)` at a glance and assume the database sees it too. What the optimizer actually sees is closer to this:

```sql
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE BLACKBOX(...) = 'WINAND'
```

`UPPER` is a black box. Its arguments do not matter, because in general there is no relationship between what goes into a function and what comes out. The optimizer cannot assume that the output is sorted like the input, so an index on the input is of no help.

<Callout kind="tip">When in doubt, rewrite the function name as `BLACKBOX` in your head. That is the optimizer's view of the condition.</Callout>

<Callout kind="note" title="Compile-time evaluation">The right-hand side, `UPPER('winand')`, is a different matter. All of its inputs are known when the statement is compiled, so the optimizer can evaluate it once, before any row is read. That is why Oracle's predicate information shows only `'WINAND'`, the upper-case constant. It is the same thing a compiler does when it folds constant expressions at compile time.</Callout>

## 3. Index the expression

If the index must contain what the query searches for, then the index must not be on `last_name` but on `UPPER(last_name)`.

```sql
CREATE INDEX emp_up_name
    ON employees (UPPER(last_name))
```

An index whose definition contains a function or expression is a **function-based index** (FBI). Instead of copying the column value into the index, the database applies the function first and stores the result. This index stores every name in capitals.

The database can use a function-based index when the exact expression from the index definition appears in the statement, as it does here. The plans confirm it.

This is a plain `INDEX RANGE SCAN` as unit 1 described it: traverse the tree, follow the leaf chain. There is no special operation and no keyword that marks a function-based index in a plan.

<Callout kind="warning" title="Common mistake">Letting the ORM choose the function. Some persistence frameworks add `UPPER` or `LOWER` to a case-insensitive search without telling you; Hibernate, for example, injects an [implicit `LOWER`](/sql/myth-directory/dynamic-sql-is-slow/). Check the generated SQL and index the expression that is actually sent.</Callout>

## 4. Check the estimates

The Oracle plan is not yet what we had before `UPPER` entered the picture: the row estimates are too high. Stranger still, they contradict each other. The table access expects to fetch 100 rows, but the index scan that feeds it only delivers 40. It cannot fetch rows it was never given. Contradictory estimates like this usually mean a problem with the statistics, and here the cause is specific: Oracle does not refresh the table statistics when a new index is created.

<Callout kind="note" title="Oracle statistics for function-based indexes">Oracle keeps the number of distinct values per column as part of the table statistics, where several indexes can share them. For a function-based index those figures live in the table statistics as well, attached to a hidden virtual column. Since release 10g Oracle gathers the statistics of a new index automatically, but it leaves the table statistics alone. The Oracle documentation therefore advises collecting statistics on both the index and its base table with `DBMS_STATS` after creating a function-based index, so that the optimizer can judge when to use it. A stricter habit is to refresh the statistics of the table and all its indexes after every index change. That can have side effects of its own, so agree it with the DBAs and keep a backup of the previous statistics.</Callout>

With refreshed statistics the estimates become realistic.

  <Fragment slot="postgresql">
  ```
                        QUERY PLAN
  ----------------------------------------------------------
   Index Scan using emp_up_name on employees
     (cost=0.00..8.28 rows=1 width=17)
     Index Cond: (upper((last_name)::text) = 'WINAND'::text)
  ```

  The estimate fell from 50 rows to 1, and with so few rows the planner drops the bitmap pair in favour of the simpler `Index Scan`.
  </Fragment>
</EngineTabs>

<Callout kind="note">Oracle 11g introduced **extended statistics** on expressions and on groups of columns, which cover this case more generally.</Callout>

In this example the fresh statistics did not change the speed; the index was used either way. Checking the optimizer's estimates is still worth the habit. The estimated row count per operation, the **cardinality estimate**, is one of the most telling numbers in a plan, and SQL Server and PostgreSQL print it too.

<Callout kind="tip">The [execution plans reference](/sql/explain-plan/) shows where each database prints its row estimates.</Callout>

## 5. Computed and generated columns

SQL Server, and MySQL before 8.0.13, do not index an expression directly. Both reach the same result through a column that is defined by an expression: add the column, then index it.

<EngineTabs>
  <Fragment slot="mysql">
  Since MySQL 5.7 a generated column can be indexed. From 8.0.13 the expression can be indexed directly as well, `CREATE INDEX emp_up_name ON employees ((UPPER(last_name)))`, with the double parentheses; MySQL then creates the hidden generated column for you.

  ```sql
  ALTER TABLE employees
    ADD COLUMN last_name_up VARCHAR(255) AS (UPPER(last_name));
  ```

  ```sql
  CREATE INDEX emp_up_name ON employees (last_name_up);
  ```
  </Fragment>
  <Fragment slot="sql-server">
  ```sql
  ALTER TABLE employees ADD last_name_up AS UPPER(last_name)
  ```

  ```sql
  CREATE INDEX emp_up_name ON employees (last_name_up)
  ```
  </Fragment>
</EngineTabs>

Both databases can use the index when the indexed expression appears in the statement, and in simple cases the original query works unchanged. In other cases the query has to name the new column, `last_name_up`, before the index is picked up. When in doubt, look at the plan.

<KeyIdea>The expression in the index and the expression in the where clause have to match. Whatever form that takes, computed column or indexed expression, the plan is the only proof that they do.</KeyIdea>
