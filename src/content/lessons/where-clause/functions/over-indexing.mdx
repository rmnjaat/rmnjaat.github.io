Once you know that any expression can be indexed, it is tempting to index all of them. Do not. Every index you add is a tree the database has to keep in step with the table, for as long as it exists, and function-based indexes are especially prone to one problem: they make it very easy to create two indexes that store the same information.

## 1. UPPER or LOWER, not both

The case-insensitive search from the previous page can just as well be written with `LOWER`.

```sql
SELECT first_name, last_name, phone_number
  FROM employees
 WHERE LOWER(last_name) = LOWER('winand')
```

Same question, same result, different expression. One index cannot serve both spellings: the index on `UPPER(last_name)` holds names in capitals and knows nothing about `LOWER(last_name)`. We could create a second index on `LOWER(last_name)`, but then every `INSERT`, `UPDATE` and `DELETE` on `employees` maintains two B-trees for what is, to the application, one search. [Chapter 8](/sql/dml/) measures that cost. The way to get by with one index is to pick one function and use it everywhere.

<KeyIdea>Unify the access path. When every query spells the condition the same way, one index serves them all.</KeyIdea>

<Callout kind="warning" title="Common mistake">Assuming you know which function your queries use. ORM tools sometimes add `UPPER` or `LOWER` on their own; Hibernate, for instance, injects an [implicit `LOWER`](/sql/myth-directory/dynamic-sql-is-slow/) into case-insensitive searches. If your hand-written SQL says `UPPER` and the ORM says `LOWER`, you are already maintaining two indexes or missing one.</Callout>

## 2. Index the original data

Before indexing an expression, ask whether the plain column would do. An index on the original data is usually the most useful one, because it serves exact lookups, ranges and sorting on that column, not just one function of it. A function-based index is the right tool when the application genuinely has to search the transformed value and cannot be changed to search the raw one.

<Callout kind="tip" title="Also redundant: a prefix of a concatenated index">An index on `(subsidiary_id)` next to an index on `(subsidiary_id, last_name)` is the same mistake without a function. The second index serves every query the first one does, because `subsidiary_id` is its leading column.</Callout>

## 3. Finding what is unused

Guessing which indexes earn their keep is as unreliable as guessing whether a query uses an index. Every database keeps counters.

<EngineTabs>
  <Fragment slot="postgresql">
  ```sql
  SELECT indexrelname, idx_scan
    FROM pg_stat_user_indexes
   WHERE relname = 'employees';
  ```

  `idx_scan` counts how often each index has been scanned since the statistics were last reset. An index that stays at zero through a representative period of production use is a candidate for dropping; a primary key or unique index stays regardless, because it enforces a constraint.
  </Fragment>
  <Fragment slot="mysql">
  ```sql
  SELECT * FROM sys.schema_unused_indexes
   WHERE object_name = 'employees';
  ```

  The `sys` schema view is built on `performance_schema` counters, which reset when the server restarts, so give it time before trusting an empty result.
  </Fragment>
  <Fragment slot="oracle">
  ```sql
  SELECT name, total_access_count, last_used
    FROM dba_index_usage
   WHERE owner = USER AND name LIKE 'EMP%';
  ```

  `DBA_INDEX_USAGE` is available from Oracle 12.2 and is sampled, so low counts are approximate. Older releases need `ALTER INDEX ... MONITORING USAGE` and `V$OBJECT_USAGE`.
  </Fragment>
  <Fragment slot="sql-server">
  ```sql
  SELECT i.name, s.user_seeks, s.user_scans, s.user_lookups, s.user_updates
    FROM sys.indexes i
    LEFT JOIN sys.dm_db_index_usage_stats s
      ON s.object_id = i.object_id AND s.index_id = i.index_id
   WHERE i.object_id = OBJECT_ID('employees');
  ```

  Zero seeks and scans next to a large `user_updates` is the signature of an index that only costs. The counters reset on restart.
  </Fragment>
  <Fragment slot="db2">
  ```sql
  SELECT indname, lastused
    FROM syscat.indexes
   WHERE tabname = 'EMPLOYEES';
  ```

  `LASTUSED` records the last day the index was used by a statement. `MON_GET_INDEX` gives finer-grained counters for the current activation of the database.
  </Fragment>
</EngineTabs>
