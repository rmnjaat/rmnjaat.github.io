Function-based indexing is a general mechanism. `UPPER` was only the first example. You can index an arithmetic expression such as `A + B`, and you can index a call to a function you wrote yourself. There is one restriction, and it follows directly from how the index is built.

## 1. The function that reads the clock

The restriction is this: an index definition cannot depend on the current time, neither directly nor through a function that does. Here is a function that does.

```sql
CREATE FUNCTION get_age(date_of_birth DATE)
RETURN NUMBER
AS
BEGIN
  RETURN
    TRUNC(MONTHS_BETWEEN(SYSDATE, date_of_birth)/12);
END
```

`GET_AGE` takes a date of birth and works out the age from today's date, `SYSDATE`. It can be used anywhere in a query, in the select list and in the where clause alike.

```sql
SELECT first_name, last_name, get_age(date_of_birth)
  FROM employees
 WHERE get_age(date_of_birth) = 42
```

The query lists every employee who is 42. A function-based index on `get_age(date_of_birth)` is the obvious way to speed it up, and it cannot be built, because `GET_AGE` is not **deterministic**. Its result is not fully determined by its argument; the same date of birth produces a different age next year. An index can only hold a function whose output is fixed by its input: same argument, same result, forever.

## 2. Why: the result is stored once

The reason is in the mechanics. When a row is inserted, the database calls the function, writes the result into the index, and that is the end of it. Nothing revisits the index entry later. There is no background job that recomputes indexed expressions. The entry changes only when the underlying column changes, that is, when an `UPDATE` sets a new `date_of_birth`. So the age stored in the index is correct on the day of the insert and wrong after the employee's next birthday.

<KeyIdea>An index entry is computed when the row is written and read back as the truth ever after. That is only safe when the computation cannot change its mind.</KeyIdea>

## 3. Declaring determinism

Being deterministic is not enough for Oracle and PostgreSQL; the function also has to say so. Oracle wants the keyword `DETERMINISTIC`, PostgreSQL wants `IMMUTABLE`, and without it `CREATE INDEX` refuses the function.

<Callout kind="warning" title="Caution">Both databases trust the declaration. They do not inspect the function body; they take the developer's word for it.</Callout>

That means you can declare `GET_AGE` deterministic and the index will be created. It still will not do what you want. The ages in the index stay as they were on the day each row was inserted, so in the index nobody ever gets older. The declaration switched off a safety check; it did not change what the function computes.

Other functions that cannot be indexed for the same reason: random number generators, and anything whose result depends on environment variables or session settings.

<Callout kind="note">Db2 for LUW does not allow user-defined functions in an index definition at all, deterministic or not.</Callout>

## 4. Think about it

How can an index still help the query for all 42-year-old employees?

The answer is to move the arithmetic to the other side of the comparison. "Age is 42" is the same question as "date of birth lies in a particular one-year window", and that window can be computed from today's date before the scan starts. The column stays bare, the function-free condition becomes a range on `date_of_birth`, and an ordinary index on that column does the work. The [range lesson](/sql/where-clause/searching-for-ranges/) covers what a range scan costs; here the range is narrow and the index is cheap.
