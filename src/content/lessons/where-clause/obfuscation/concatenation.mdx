This lesson is about a popular obfuscation that defeats [concatenated indexes](/sql/where-clause/the-equals-operator/concatenated-keys/). It starts with [date and time](/sql/where-clause/obfuscation/dates/) again, but the other way round: instead of taking a date apart, the query glues two columns together.

## 1. A range over two columns

A MySQL table keeps the date and the time of day in separate columns. A query for the last 24 hours combines them:

```sql
SELECT ...
  FROM ...
 WHERE ADDTIME(date_column, time_column)
     > DATE_ADD(now(), INTERVAL -1 DAY)
```

The query is correct, and it cannot properly use a concatenated index on `(DATE_COLUMN, TIME_COLUMN)`. The search is not on the indexed columns but on a value derived from them, and that value is in no index.

## 2. Change the type, or index the expression

The cleanest fix is a column type that holds both parts, such as MySQL's `DATETIME`. Then the column stands alone in the condition:

```sql
SELECT ...
  FROM ...
 WHERE datetime_column
     > DATE_ADD(now(), INTERVAL -1 DAY)
```

Changing the table is often not an option when the problem turns up. The next candidate is a [function-based index](/sql/where-clause/functions/) on the combined expression, with all the drawbacks [discussed before](/sql/where-clause/functions/over-indexing/), and not available at all in older MySQL versions.

## 3. The redundant condition

There is a third way that lets the concatenated index on `DATE_COLUMN, TIME_COLUMN` provide an access predicate, at least in part. Add an extra condition on `DATE_COLUMN` alone:

```sql
WHERE ADDTIME(date_column, time_column)
    > DATE_ADD(now(), INTERVAL -1 DAY)
  AND date_column
   >= DATE(DATE_ADD(now(), INTERVAL -1 DAY))
```

The new condition is completely redundant: any row that passes the first one passes the second. But it is a straight comparison on `DATE_COLUMN`, so the index can use it as an access predicate. The scan starts at yesterday's date and the original condition filters out the rows from before the exact moment. The scan still reads yesterday's rows from before the exact cut-off and discards them, so it is an approximation, but a close one: a few extra rows from one day instead of the whole table.

<KeyIdea title="Tip">When the condition glues columns together, add a plain condition on the leading column that the original already implies.</KeyIdea>

For PostgreSQL, the row values syntax is preferable: `(date_column, time_column) > (?, ?)` compares the pair as a whole and uses the concatenated index directly.

The same technique works when date and time are stored as text, provided the format sorts chronologically, as [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) does (`YYYY-MM-DD HH:MM:SS`). This Oracle example builds the comparison values with `TO_CHAR`:

```sql
SELECT ...
  FROM ...
 WHERE date_string || time_string
     > TO_CHAR(sysdate - 1, 'YYYY-MM-DD HH24:MI:SS')
   AND date_string
    >= TO_CHAR(sysdate - 1, 'YYYY-MM-DD')
```

A range condition over several columns comes back in [Paging Through Results](/sql/partial-results/fetch-next-page/), and the same approximation is used there to deal with it.

<Callout kind="warning" title="Common mistake">Adding a condition that is not implied by the original. The extra condition must be true for every row the original condition accepts, or it is not redundant, it is a bug. Derive the bound from the original condition, and leave a comment that says why it is there.</Callout>

## 4. Obfuscating on purpose

Sometimes the aim is the reverse: a condition that the optimizer should *not* use as an access predicate. The [bind parameter](/sql/where-clause/bind-parameters/) problem with `LIKE` is the classic case:

```sql
SELECT last_name, first_name, employee_id
  FROM employees
 WHERE subsidiary_id = ?
   AND last_name LIKE ?
```

With one index on `SUBSIDIARY_ID` and another on `LAST_NAME`, which should the database use? Without knowing where the wildcard sits, there is no sound answer, and the optimizer can only guess. If you know the search term always starts with a wildcard, obfuscate the `LIKE` so that the index on `LAST_NAME` is no longer a candidate:

```sql
SELECT last_name, first_name, employee_id
  FROM employees
 WHERE subsidiary_id = ?
   AND last_name || '' LIKE ?
```

Appending an empty string is all it takes. This is a last resort. Do it only when nothing else works.
