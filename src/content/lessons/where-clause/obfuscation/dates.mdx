Most obfuscated conditions involve dates. Oracle is especially exposed because its `DATE` type always carries a time component, so people reach for a function to get rid of it. The function is what hides the column from its index.

## 1. TRUNC on both sides

The common habit is `TRUNC` to "remove" the time. It does not remove anything; it sets the time to midnight, because Oracle has no pure date type. To ignore the time in a comparison, `TRUNC` is applied to both sides, as in this search for yesterday's sales:

```sql
SELECT ...
  FROM sales
 WHERE TRUNC(sale_date) = TRUNC(sysdate - INTERVAL '1' DAY)
```

The statement is valid and correct, and it cannot make proper use of an index on `SALE_DATE`. The reason is the one from [Case-Insensitive Search](/sql/where-clause/functions/case-insensitive-search/): `TRUNC(sale_date)` is something else entirely than `SALE_DATE`. The database treats the function as an opaque step and cannot map its output onto the order of the index.

## 2. A function-based index, and its catch

The direct fix is a [function-based index](/sql/where-clause/functions/):

```sql
CREATE INDEX index_name
          ON sales (TRUNC(sale_date))
```

The catch is consistency. Every query must now write `TRUNC(sale_date)`. If some do and some do not, you need two indexes.

The problem is not limited to Oracle. Databases with a pure date type run into it as soon as the search covers a longer period, as this MySQL query does:

```sql
SELECT ...
  FROM sales
 WHERE DATE_FORMAT(sale_date, "%Y-%M")
     = DATE_FORMAT(now()    , "%Y-%M")
```

The format keeps only year and month. Again a correct query with the same problem, and MySQL has function-based indexes only since 8.0.13 (5.7 can index a generated column instead), so on older versions the direct fix is not even available.

## 3. The explicit range

The alternative works everywhere: write the period as an explicit range condition.

```sql
SELECT ...
  FROM sales
 WHERE sale_date BETWEEN quarter_begin(?)
                     AND quarter_end(?)
```

If you did the exercise on [employees who are 42 years old](/sql/where-clause/functions/user-defined-functions/), the pattern is familiar. A plain index on `SALE_DATE` serves this query. The functions `QUARTER_BEGIN` and `QUARTER_END` compute the boundary dates. That is slightly fiddly because [BETWEEN includes both boundaries](/sql/where-clause/searching-for-ranges/greater-less-between-tuning-sql-access-filter-predicates/): if `SALE_DATE` has a time component, `QUARTER_END` has to return the last instant before the next quarter begins. The function hides that detail.

  ```sql
  CREATE FUNCTION quarter_begin(dt DATETIME)

  RETURN CONVERT

           CONCAT
           ( CONVERT(YEAR(dt),CHAR(4))
           , '-'
           , CONVERT(QUARTER(dt)*3-2,CHAR(2))
           , '-01'
           )
         , datetime
         )
  ```

  ```sql
  CREATE FUNCTION quarter_end(dt DATETIME)
  RETURNS DATETIME DETERMINISTIC
  RETURN DATE_ADD
         ( DATE_ADD ( quarter_begin(dt), INTERVAL 3 MONTH )
         , INTERVAL -1 MICROSECOND)
  ```

  ```sql
     -- the Oracle DATE type has seconds resolution
  ```

  ```sql
  CREATE FUNCTION quarter_begin (@dt DATETIME )

  END
  ```

  ```sql
  CREATE FUNCTION quarter_end (@dt DATETIME )
  ```

  SQLite has no date type. ISO 8601 strings sort chronologically, so a range on the text column works with a plain index:

Similar helpers work for other periods, and most are simpler than these, especially if you use `>=` and `<` instead of `BETWEEN`, which removes the "one second before" arithmetic. You can also compute the boundaries in the application.

<KeyIdea title="Tip">

A continuous period belongs in the where clause as a range on the bare column. That holds for a single day as much as for a quarter; in Oracle:

```sql
sale_date >= TRUNC(sysdate)
AND sale_date <  TRUNC(sysdate + INTERVAL '1' DAY)
```

</KeyIdea>

## 4. Dates compared as strings

Another frequent obfuscation compares dates as text, as in this PostgreSQL example:

```sql
SELECT ...
  FROM sales
 WHERE TO_CHAR(sale_date, 'YYYY-MM-DD') = '1970-01-01'
```

Once more the problem is the conversion of `SALE_DATE`. Conditions like this are often written in the belief that only numbers and strings can be passed to the database. [Bind parameters](/sql/where-clause/bind-parameters/) support every data type; a `java.util.Date` object, for instance, is a perfectly good parameter. That is one more benefit of using them.

If you cannot pass a date, convert the search term instead of the column:

```sql
SELECT ...
  FROM sales
 WHERE sale_date = TO_DATE('1970-01-01', 'YYYY-MM-DD')
```

This uses a plain index on `SALE_DATE`, and it converts the input once. The first version had to convert every date in the table before it could compare anything.

Either change, bind parameter or converted search term, can introduce a bug if `SALE_DATE` has a time component: the equality then matches only sales at exactly midnight. Use an explicit range in that case:

```sql
SELECT ...
  FROM sales
 WHERE sale_date >= TO_DATE('1970-01-01', 'YYYY-MM-DD')
   AND sale_date <  TO_DATE('1970-01-01', 'YYYY-MM-DD')
                  + INTERVAL '1' DAY
```

Whenever you compare dates, consider the explicit range first.

## 5. LIKE on a date

This one is especially sneaky because it uses no function at all:

```sql
sale_date LIKE SYSDATE
```

`LIKE` is a string operator and forces a string comparison. Depending on the database that is an error or an implicit conversion of both sides. Oracle's predicate information shows what it did:

```
filter( INTERNAL_FUNCTION(SALE_DATE)
        LIKE TO_CHAR(SYSDATE@!))
```

`INTERNAL_FUNCTION` is the type conversion applied to `SALE_DATE`. Like any other function on the column, it rules out a plain index on it.

<Callout kind="warning" title="Common mistake">Thinking that a condition without a visible function is safe. `LIKE` on a date, or any comparison between a date column and a string, can add a conversion you never wrote. If the plan shows `INTERNAL_FUNCTION`, `CAST` or `TO_CHAR` around the column, that is the obfuscation.</Callout>
