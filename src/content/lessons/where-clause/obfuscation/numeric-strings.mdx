A numeric string is a number kept in a text column. It is bad practice, but it does not make an index useless by itself. As long as the column is consistently treated as text, the index works.

## 1. Same column, two comparisons

```sql
SELECT ...
  FROM ...
 WHERE numeric_string = '42'
```

This can use an index on `NUMERIC_STRING`. Drop the quotes and it cannot:

```sql
SELECT ...
  FROM ...
 WHERE numeric_string = 42
```

Some databases, PostgreSQL among them, reject the statement with an error. Many others silently add a type conversion, so the condition they actually execute is this:

```sql
SELECT ...
  FROM ...
 WHERE CAST(numeric_string AS INT) = 42
```

It is the function-on-the-column problem again: the index on `NUMERIC_STRING` holds strings, and the condition is on numbers made from them. The condition cannot be an [access predicate](/sql/where-clause/searching-for-ranges/greater-less-between-tuning-sql-access-filter-predicates/).

## 2. Convert the search term, not the column

The fix is the same as always: leave the column alone and convert the other side.

```sql
SELECT ...
  FROM ...
 WHERE numeric_string = CAST(42 AS VARCHAR(10))
```

Why does the database not do this by itself? Because converting a string to a number has one unambiguous result, while converting a number to a string does not. A number written as text can carry spaces, punctuation and leading zeros. One value, many spellings:

```
42
042
0042
00042
...
```

Since the database has no way of knowing which spelling the `NUMERIC_STRING` column uses, it takes the only safe route and turns the strings into numbers, where every spelling collapses to one value.

That also means the two spellings mean different things. `CAST AS VARCHAR` produces one string and matches only the first spelling in the list. `CAST AS INT` matches all of them. The difference is not only in performance; it is in the result.

## 3. What each database does

<Figure n="2.10" title="How the databases handle numeric_string = 42">

| Behaviour | Databases |
| --- | --- |
| No implicit conversion: type error | BigQuery, PostgreSQL |
| Converts the column: `CAST(numeric_string AS INT) = 42` | Db2 (LUW), MariaDB, MySQL, Oracle, SQL Server |
| Converts the number: `numeric_string = CAST(42 AS VARCHAR)` | SQLite |

<p slot="caption">Only SQLite converts the search term, because its column affinity rules apply the column's type to the literal. The second group loses the index; the first group refuses to run the statement.</p>
</Figure>

Numeric strings are trouble beyond performance. Besides the implicit conversion, there is the risk of conversion errors from invalid numbers: a single bad value in the table can abort even the most innocent query, one with no function anywhere in its where clause.

<KeyIdea title="Tip">Use numeric types to store numbers.</KeyIdea>

## 4. The other way round

The problem does not exist in the opposite direction:

```sql
SELECT ...
  FROM ...
 WHERE numeric_number = '42'
```

Here the string is converted to a number, consistently, and no function lands on the potentially indexed column. A regular index works. You can still get it wrong by hand:

```sql
SELECT ...
  FROM ...
 WHERE TO_CHAR(numeric_number) = '42'
```

<Callout kind="warning" title="Common mistake">Trusting that a condition "without a function" is safe. The function is there; the database added it. If an indexed column shows up inside `CAST`, `TO_NUMBER`, `CONVERT` or `INTERNAL_FUNCTION` in the plan, check the type of the value on the other side, and the type your driver or ORM binds.</Callout>
