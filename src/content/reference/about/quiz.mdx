The original site has a three-minute quiz that most people fail, and the author's point in publishing the results was not that developers are careless but that SQL performance is taught as folklore. The five questions below are this site's own, written against the [example schema](/sql/example-schema/). Each shows an index and a query; decide whether the pair works. The explanations are short because the lessons are not.

  question="Two queries run all day: one by subsidiary_id alone, one by subsidiary_id and last_name. A single index should serve both. Which column order is right?"
  options={[

<Check
  client:visible
  question="An index exists on employees (last_name). The search screen runs WHERE last_name LIKE '%and%' so that users can type any part of a name. Does the index help?"
  options={[
    'Yes. LIKE is a comparison on the indexed column and the database walks the index.',
    'Yes, but only the first few rows come back quickly.',
    'No. A pattern that starts with a wildcard has no leading characters to find in the tree, so every entry has to be checked.',

  answer={2}
  explain="A B-tree can narrow the scan only up to the first wildcard. Needing substring search means needing a different tool: a full-text index or a trigram index. Unit 2, Searching for ranges: Indexing LIKE filters."

<Check
  client:visible
  question="A dashboard shows the ten most recent sales: ORDER BY sale_date DESC FETCH FIRST 10 ROWS ONLY, with no where clause. There is an index on sales (sale_date). Can the database answer this without reading the whole table?"
  options={[
    'No. ORDER BY always sorts, and sorting needs every row before the first one can be returned.',
    'Yes. The index already holds the rows in sale_date order, so it reads the last ten leaf entries, backwards, and stops.',
    'Only if the index was created with DESC.',
  ]}
  answer={1}
  explain="An index is a sorted structure, and leaf nodes are linked in both directions, so a descending walk from the end of the index delivers rows in the required order without a sort. ## Where to start

Count the questions you got right the first time, not after reading the explanation.

**Zero or one.** Start at the beginning. [Unit 1](/sql/anatomy/) is three lessons on what an index physically is, and everything else depends on that picture. Then read [Unit 2](/sql/where-clause/) in order; it is the longest unit and the one that fixes most slow queries.

**Two or three.** You know that indexes exist and roughly how they are used; the gaps are in the where clause. Skim [Unit 1](/sql/anatomy/), then read [Unit 2](/sql/where-clause/) carefully, especially the lessons on [concatenated keys](/sql/where-clause/the-equals-operator/concatenated-keys/), [ranges](/sql/where-clause/searching-for-ranges/) and [obfuscated conditions](/sql/where-clause/obfuscation/). Read [Unit 3](/sql/testing-scalability/) to understand why your test database did not warn you.

**Four.** The where clause is in good shape. Go to [Unit 4](/sql/join/), [Unit 5](/sql/clustering/), [Unit 6](/sql/sorting-grouping/) and [Unit 7](/sql/partial-results/), which are about the second and third things an index can do beyond finding rows: avoiding the table, and delivering order. The question you missed points at the unit to start with.

**Five.** Read [Unit 8](/sql/dml/) for the cost side of indexing, then use the [execution plan reference](/sql/explain-plan/) for your engine and the [myth directory](/sql/myth-directory/) as a checklist against advice you will hear from others. The unit checks at the end of each unit are a faster way through the material than the lessons.
