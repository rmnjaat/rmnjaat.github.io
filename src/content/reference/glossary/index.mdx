Terms are listed in the order the book introduces them, roughly: structure first, then the where clause, then execution and joins, then writes.

## Index

A separate data structure that stores a sorted copy of one or more columns of a table, with each entry pointing back to its row. Indexes exist so the database can find rows without reading the whole table. See [Anatomy of an Index](/sql/anatomy/).

## B-tree

The balanced tree that every mainstream database uses for its indexes. Branch nodes on top of the leaf nodes let a lookup reach any entry in a handful of reads, and the tree stays balanced through every write without manual maintenance. See [The B-Tree](/sql/anatomy/the-tree/).

## Leaf node

A block at the bottom of the index that holds the actual entries, sorted, with a pointer to the row for each one. Leaf nodes are chained to their neighbours in both directions so a scan can walk them in order. See [The Leaf Nodes](/sql/anatomy/the-leaf-nodes/).

## Branch node

A node above the leaves that stores the largest key of each node below it, together with a pointer to that node. A lookup follows the first entry greater than or equal to the search key. See [The B-Tree](/sql/anatomy/the-tree/).

## Root node

The single branch node at the top of the B-tree. Every lookup starts there. See [The B-Tree](/sql/anatomy/the-tree/).

## ROWID, row pointer

The physical address of a row in the table, stored in each index entry so the database can get from the entry to the row. Oracle calls it ROWID, PostgreSQL the tuple id, SQL Server the RID; in a clustered index the clustering key takes its place. See [The Leaf Nodes](/sql/anatomy/the-leaf-nodes/).

## Concatenated index

An index on more than one column, also called a composite or multi-column index. The entries are sorted by the first column, then by the second within equal first values, so only the leading columns can be used by a tree traversal. See [The Where Clause](/sql/where-clause/).

## Access predicate

A condition from the where clause that the database uses to decide where the index scan starts and stops. Access predicates are what make an index range scan small. See [The Where Clause](/sql/where-clause/) and [Execution Plans](/sql/explain-plan/).

## Filter predicate

A condition that is checked on each entry or row as it is read but does not narrow the scanned range. An index filter predicate is evaluated on the index entries during the leaf walk; a table-level filter predicate needs the row and is evaluated after the fetch. A filter predicate on an index column that cannot be an access predicate is the usual reason an indexed query is still slow. Note that access and filter are properties of an operation in a plan, not of the index: the same index serves one query with two access predicates and another with one access predicate and one filter. See [Greater, Less and BETWEEN](/sql/where-clause/searching-for-ranges/greater-less-between-tuning-sql-access-filter-predicates/), [Data Volume](/sql/testing-scalability/data-volume/), [Indexing LIKE](/sql/where-clause/searching-for-ranges/like-performance-tuning/) and, for the deliberate use, [Index Filter Predicates Intentionally Used](/sql/clustering/index-filter-predicates/). How each engine labels them is in [Execution Plans](/sql/explain-plan/).

## Index unique scan

A tree traversal that returns at most one entry, used when the where clause fixes every column of a unique index with equality conditions. The cheapest index access there is. See [The Where Clause](/sql/where-clause/).

## Index range scan

A tree traversal followed by a walk along the leaf chain for as long as entries match the access predicates. Its cost depends on how many entries the range covers. See [The Where Clause](/sql/where-clause/).

## Table access by ROWID, heap fetch

Reading a row from the table using the pointer stored in an index entry. Each fetch is a separate block read, which makes it the most expensive step of an index range scan when many rows match. See [Anatomy of an Index](/sql/anatomy/) and [Clustering Data](/sql/clustering/).

## Full table scan

Reading every block of the table and checking each row against the where clause. Not always wrong: for a condition that matches a large share of the table it is cheaper than an index scan with a table fetch per row. See [The Where Clause](/sql/where-clause/).

## Index-only scan

A query answered entirely from the index because every column it needs is in the index, the columns of the select list included. No table access takes place. Oracle, SQL Server and MySQL have done this for a long time; PostgreSQL added it in release 9.2. How much it saves depends on the number of rows and on the clustering factor of the index. See [Index-Only Scan](/sql/clustering/index-only-scan-covering-index/).

## Covering index

An index that makes an index-only scan possible for a given query because it holds every column the query touches. The term names the index, but whether it covers depends on the query: the same index covers `SUM(eur_value)` and not `SUM(quantity)`. Index-only scan names what the database does, which is the better name for the effect. See [Index-Only Scan](/sql/clustering/index-only-scan-covering-index/).

## Index clustering factor

A measure of how well the order of an index matches the physical order of the table rows. A `sales` table that is only ever appended to is in `sale_date` order, so an index on `sale_date` has a very low clustering factor: neighbouring index entries point to neighbouring rows, and a range scan reads few table blocks. An index on `employee_id` over the same table has a high clustering factor, because consecutive entries point to rows scattered across the whole table. See [Clustering Data](/sql/clustering/).

## Clustered index, non-clustered index

A clustered index is a table stored inside a B-tree rather than as a heap, so the row and the index entry are the same thing and there is no second structure holding the row. A non-clustered index is the ordinary kind: it points to the row somewhere else. SQL Server makes the clustered index optional (a table has at most one, dropping it turns the table back into a heap, and `PRIMARY KEY NONCLUSTERED` creates a table without one); InnoDB in MySQL always clusters, on the primary key or on a generated row id when there is no suitable unique key, while MyISAM never does. See [Index-Organized Table](/sql/clustering/index-organized-clustered-index/).

## Index-organized table

Oracle's name for a clustered index: a table created with `ORGANIZATION INDEX` and stored in the B-tree of its primary key, which is always the clustering key. Reading such a table through one of its secondary indexes is slower than the same query against a heap table. See [Index-Organized Table](/sql/clustering/index-organized-clustered-index/).

## Secondary index

Any index on a table other than the one that stores or orders the table. On a heap it stores rowids like any other index. On a clustered table or index-organized table it cannot, because rows in a B-tree move; it stores the clustering key instead, so every lookup through it is two tree traversals. See [Index-Organized Table](/sql/clustering/index-organized-clustered-index/).

## Heap table

The ordinary table layout, where rows are stored in no particular order wherever there is free space, as opposed to an index-organized table or clustered index where the rows live in B-tree order. Indexes point into the heap by physical address. See [Index-Organized Table](/sql/clustering/index-organized-clustered-index/).

## Function-based index, expression index

An index on the result of an expression, such as `UPPER(last_name)`, rather than on a column. It lets a where clause that applies the same expression use the index. The expression must be deterministic. See [The Where Clause](/sql/where-clause/).

## Partial index, filtered index

An index that covers only the rows matching a condition given in its definition, such as unprocessed orders. Smaller and cheaper to maintain than a full index, usable only by queries whose where clause implies that condition. See [The Where Clause](/sql/where-clause/).

## Bind parameter

A placeholder in a statement, written `?` or `:name` or `$1` depending on the driver, whose value is sent separately from the SQL text. Statements with bind parameters have a stable text, so the database can reuse their plans. See [The Where Clause](/sql/where-clause/).

## Execution plan, explain plan, query plan

The executable form of a SQL statement: the sequence of operations the optimizer chose, which indexes it uses, in what order it joins, where it sorts. Obtained with `EXPLAIN` or equivalent; the three names mean the same thing in different products. Reading plans is the main skill this book teaches. See [Execution Plans](/sql/explain-plan/).

## Optimizer, query optimizer, query planner

The component that turns a SQL statement into an execution plan, as a compiler turns source into an executable. Oracle says optimizer, SQL Server and MySQL say query optimizer, PostgreSQL says query planner. A rule-based optimizer follows fixed rules ("use an index whenever one exists"); a cost-based optimizer generates candidate plans, estimates the cost of each from statistics and picks the cheapest, which is why it may prefer a full table scan over an index when the condition matches most rows. Every engine in this book is cost-based. The optimizer decides the join algorithm, the join order and the index usage; it does not repair obfuscated conditions, create missing indexes or reorganize data. See [Bind Parameters](/sql/where-clause/bind-parameters/).

## Parsing, query planning, compiling

Turning a SQL statement into an execution plan; Oracle calls it parsing, PostgreSQL planning, SQL Server compiling. Engines with a shared plan cache distinguish a **hard parse**, which builds the plan from scratch and considers every index and join order, from a **soft parse**, which finds a cached plan for the identical statement text and reuses it after a few checks. The cache key is the text, so literal values in the statement cause a hard parse every time. See [Bind Parameters](/sql/where-clause/bind-parameters/) and [Dynamic SQL Is Slow](/sql/myth-directory/dynamic-sql-is-slow/).

## Statistics

The optimizer's knowledge about the data: row counts, number of distinct values, value distributions, index sizes. Collected by `ANALYZE` or its equivalent. Stale statistics produce bad plans. See [The Where Clause](/sql/where-clause/).

## Selectivity

The share of rows a condition matches. A highly selective condition matches few rows, which is what makes an index worthwhile for it. See [The Where Clause](/sql/where-clause/).

## Cardinality

The number of rows an operation produces, or the number of distinct values in a column. Plans show the optimizer's estimate of it, and a large gap between the estimate and the real count explains most bad plans. See [Execution Plans](/sql/explain-plan/).

## Nested loops join

A join that takes each row from one table and looks up its matches in the other. Fast when the inner lookup is an index access and the outer side is small; it is also the algorithm behind the N+1 problem. See [The Join Operation](/sql/join/).

## Hash join

A join that loads the smaller side into an in-memory hash table and probes it with each row from the larger side. Indexes on the join columns do not help; indexes on the independent where clause conditions of each side do. See [The Join Operation](/sql/join/).

## Sort-merge join

A join that sorts both sides on the join columns and merges them in one pass. Useful when the inputs are already sorted, for example by an index. See [The Join Operation](/sql/join/).

## Pipelined execution

Producing result rows as they are found instead of after a blocking step such as a sort has consumed all input. A pipelined order by delivers the first row immediately and lets a top-N query stop early. See [Sorting and Grouping](/sql/sorting-grouping/).

## N+1 problem

The pattern where an application runs one query to fetch a list and then one more query per item in it, typically caused by an ORM loading related objects lazily. It is a nested loops join executed from the application, with a network round trip per iteration. See [The Join Operation](/sql/join/).

## Offset paging, seek paging

Two ways to fetch the next page of a sorted result. Offset paging skips a number of rows, which the database must read and discard. Seek paging filters on the values of the last row shown, so the index lands directly on the page. See [Fetching the Next Page](/sql/partial-results/fetch-next-page/).

## Window function

A function such as `ROW_NUMBER()` or `SUM() OVER (...)` that computes a value for each row from a window of related rows without collapsing them as `GROUP BY` would. Used for ranking and, before `FETCH FIRST`, for paging. See [Window Functions for Pagination](/sql/partial-results/window-functions/).

## Index bloat

An index that occupies far more pages than its entries need, usually after mass deletes or, in PostgreSQL, after many updates left dead entries behind. It is the real problem behind the myth that indexes degenerate. See [Indexes Can Degenerate](/sql/myth-directory/indexes-can-degenerate/).

## Deterministic function

A function that always returns the same result for the same input. Only deterministic expressions can be indexed, because the database must be able to recompute the stored value. See [The Where Clause](/sql/where-clause/).
